Why not token IDs?

Token IDs only say which symbol appeared. Hidden states contain context: what the token means in this sentence and what role it may play.

Why a vector?

A vector can store many soft features at once: topic, entity, instruction, variable name, answer anchor, or constraint.

Why learned?

The matrices W_k^I and W_q^I are trained so useful past tokens get high scores when future tokens need them.

Inference benefit

DSA does not beat MLA by shrinking the cache. It beats MLA by reading less during long-context decode.

Decode stageone new token at a time
MLA-only decode at long context

MLA has a small cache per token, but a new token still has to score and read across the full visible history.

DSA decode at long context

The indexer scans lightweight search keys, then the expensive MLA attention reads only the selected top-k content vectors.

This is the key inference distinction: MLA reduces cache bytes per token. DSA reduces the number of content tokens touched by the expensive attention read. The DSA cache can be slightly larger than MLA because of the index keys, but the long-context decode step can be much cheaper.

Keep the dimensions simple: 512 is the MLA latent dimension in DeepSeek V3.2, so each token stores a 512-number compressed content vector. 128 is the index dimension, so each token stores a 128-number lookup vector. Because both are stored in FP8, each number is about 1 byte.

MLA cache

For each token, DeepSeek's MLA content memory stores a 512-number latent vector. This is the latent dimension.

512 latent numbers * 1 byte = 512B

Quantization also needs a few scale numbers, and the implementation keeps a small position part.

512B latent + 16B scales + 128B position = 656B
656 * 128K * 61 ~= 4.77 GiB
DSA cache

The index key is smaller because it is not content memory. It is only a lookup label. In V3.2, the index key has 128 numbers. This is the index dimension.

128 index numbers * 1 byte ~= 128B

Add a tiny scale overhead, and the lookup entry is roughly 132B.

656B MLA content + ~132B index key ~= 788B
(656 + ~132) * 128K * 61 ~= 5.73 GiB

So yes: DSA can use more cache memory than MLA alone. The win is that, at long context, HBM bandwidth and attention compute are dominated by repeatedly reading the history during decode. DSA pays a small lookup-cache cost to avoid reading nearly all content vectors in the heavy attention path.

Why not 62.5x end-to-end?

The indexer still scans the sequence, top-k has overhead, kernels have overhead, and other model layers still run. So the end-to-end speedup is much smaller than the raw content-read reduction.

Which complexity?

O(L^2) -> O(Lk) is the main attention work over a length-L sequence: L query positions times either L past tokens or k selected tokens. In single-token decode, the same statement becomes O(L) -> O(k) for the heavy MLA attention read.

Best workshop wording

Do not say DSA makes the KV cache smaller than MLA. Say: MLA makes the cache compact; DSA makes long-context attention reads sparse.

MLA roofline story

MLA reduces bytes per cached token. For similar attention work, fewer bytes raises arithmetic intensity and moves decode away from the worst memory-bound region.

DSA roofline story

DSA changes the algorithm. In decode, the heavy attention part goes from O(L) to O(k) for the selected content read, plus a cheaper O(L) index scan. Memory-bound time drops because HBM traffic drops.

Classroom wording

For DSA, say: the cache footprint may increase, but per-token HBM traffic in long-context decode decreases. That is why inference can speed up.
