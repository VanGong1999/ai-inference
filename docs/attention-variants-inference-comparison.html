为什么内存与计算都很重要

两种资源，一个瓶颈

在推理（自回归生成）过程中，每一个新的 token 都需要两样东西：

1
内存来存储过去的上下文（KV 缓存或循环状态）。它随着每一个生成的 token 增长，并决定了你能同时服务多少个序列。
2
计算来把新 token 与所有过去的上下文进行处理。这决定了每个 token 生成需要多长时间 — 以及延迟是否在长序列上退化。

在短序列上，两者都不是问题。在长序列（100K+ token）上，两者都成为瓶颈。不同的技术优化不同的维度。有些减少内存，有些减少计算，有些两者都减少。

SSM 无法完全弥合的质量差距。 Mamba 和线性注意力实现了恒定的内存与计算 — 但注意力能够进行精确的 token 到 token 查找（例如「列表里的第 3 项是什么？」）的能力，是有损状态压缩从根本上难以做到的。这就是为什么最好的生产级模型（Jamba、DeepSeek）使用混合架构：少量注意力层用于精确检索 + 大量 SSM/线性层用于高效的长程上下文。

SSM 的短板所在

上下文学习

Transformer 可以从提示中的示例里学习新任务。SSM 在这方面很吃力 — 固定大小的状态无法像在原始 token 上的注意力那样存储任意的输入-输出映射。

精确检索

「复制第 5 个词」或「电话号码是什么？」需要精确的查找。注意力可以轻松做到。SSM 把过去的 token 压缩进一个固定状态 — 单个 token 可能无法恢复。

多跳推理

「A 是 B，B 是 C，所以 A 是 C」需要同时持有多个事实并把它们组合起来。SSM 状态的有损压缩使得链条式推理比完整注意力更难。

硬件生态

Transformer 有多年的 GPU kernel 优化积累（FlashAttention、PagedAttention 等）。SSM kernel 更新、更不成熟，意味着理论上的 FLOPs 优势并不总能转化为实际的墙钟速度提升。

第 1 部分

内存 — KV 缓存问题

1.1 — KV 缓存详解

在解码过程中，每个新 token 的 query 都必须关注所有过去的 key 和 value。每一步都重新计算它们会很浪费，所以我们把之前每一个 token 的 K 和 V 投影缓存起来。

KV 缓存随序列长度线性增长。对于每一层：

每层 KV 缓存 = 2 × N × n_heads × d_head × dtype_bytes

计算 — FLOPs 问题

2.1 — 为什么 FLOPs 对推理很重要

在解码过程中，生成每个新 token 都需要对所有过去的 key计算注意力分数。注意力的逐 token 解码成本为：

每 token FLOPs = 2 × N × d   (与 N 个 key 的点积 + N 个 value 的加权和)

当 N=100K、d=2048 时，每个新 token 仅仅为注意力就要花费 约 4.1 亿 FLOPs。而且随着每一个 token 的生成，情况会越来越糟 — 因为 N 在不断增长。

2.8 — 计算对推理延迟真的重要吗？

重要 — 但真实的故事更加微妙。

在 prefill 阶段，计算在所有 token 上并行进行。在 decode 阶段，计算是串行的：一次一个 token，每个都必须在前一个完成之后才开始。所以每 token 的解码延迟与每 token 的 FLOPs 成正比。

但这里有一个关键洞察。在 N=100K、使用完整注意力时：

计算时间

~4 μs

4.1 亿 FLOPs，100 TFLOPS

内存读取时间

~390 μs

781 MB KV 缓存，2 TB/s

内存读取比计算耗时长约 100 倍。解码本质上是内存带宽受限，而不是计算受限。

关键洞察： 解码是内存带宽受限，而不是计算受限。这就是为什么 MQA/GQA（它们减少了内存读取）比单纯减少 FLOPs 更能加速推理。缩小 KV 缓存意味着从 HBM 读取的字节更少，直接降低了逐 token 延迟。

话虽如此，对于非常长的序列，两者都很重要。而对于吞吐受限的场景（许多并发用户），内存容量决定了你能把多少个请求打包成一批。

DeepSeek-V2 的洞见。 尽管拥有 236B 参数，DeepSeek-V2 的 MLA 把每个 token 的 KV 表示压缩成一个 512 维向量（相比之下 Llama 的 GQA 是 2048 维）。这是一个 4 倍的缩减 — 让一个 236B 模型的 KV 缓存比一个 70B 模型还小。MLA 通过学习 key 和 value 的低秩压缩，然后在解码时即时重建完整的注意力头来实现这一点。

关键要点：内存

在 100K token 时，纯 MHA 模型变得不切实际。GQA、MLA 和滑动窗口让长上下文变得可行。Mamba/混合架构则让它变得轻松。

关键要点：计算

完整注意力的 O(Nd) 解码成本意味着在 N=100K 时约 4.1 亿 FLOPs/token。滑动窗口把它封顶在约 1680 万。SSM/Mamba：约 270 万 — 比完整注意力便宜 150 倍。

内存和计算是同一枚硬币的两面。 最好的推理系统会同时优化两者 — 用 GQA 缩小 KV 缓存，用滑动窗口封顶计算，并且越来越多地使用混合架构，把少量注意力层（用于精确召回）与 Mamba 层（用于高效的长程上下文）结合起来。DeepSeek-V2 的 MLA 表明，巧妙的压缩可以以极小的内存成本给你接近 MHA 的质量。
