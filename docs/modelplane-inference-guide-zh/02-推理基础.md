# 2. 推理基础

本节按照你实际接触这些概念的大致顺序进行介绍。多数概念都围绕两个问题：推理引擎会在 GPU 内存中保存什么，以及什么因素限制了推理速度。

Viktor Farcic 建议思考每个概念从什么时候开始变得重要：有些概念在第一次部署时就必须理解，有些要等到用户数量增加后才会显现，还有一些你可能永远不需要使用。本节末尾的表格给出了相应的信号。

## 什么是推理引擎

推理引擎（例如 [vLLM](https://github.com/vllm-project/vllm) 或 [SGLang](https://github.com/sgl-project/sglang)）是把模型权重转换为 API 服务的服务器。对平台工程师而言，最接近的心智模型是“连接了 GPU 的有状态数据库服务器”：它在启动时将大型数据集加载到内存中，为每个会话保存状态，在内部调度工作，并通过 HTTP 返回结果。[Ollama](https://github.com/ollama/ollama) 在笔记本上的运行方式也是同一个概念，只是规模更小；每个托管模型 API 的背后也都有类似的引擎。

| 你在数据库和服务中熟悉的概念 | 推理引擎中的对应物 |
|---|---|
| 启动时把数据集加载到缓冲池 | 将模型权重加载到 GPU 内存，可能需要数分钟 |
| 会话存储中的每会话状态 | KV 缓存，每个进行中的对话各有一份 |
| 查询规划器和连接池 | 调度器，将请求批处理到每次 GPU 计算中 |
| 客户端已经会使用的网络协议 | 兼容 OpenAI 或 Anthropic 的 HTTP API |
| 重启后预热缓存 | 冷启动：拉取大型镜像并重新加载权重 |

与数据库不同，推理引擎的工作集保存在 GPU 内存而不是 RAM 中。GPU 内存容量小而且昂贵，因此大多数调优工作都在决定每个请求应该分配多少内存。

## 推理技术栈

推理引擎只是四层架构中的一层。最底层是负责执行算术运算的 kernel；你很少直接选择它们。上面是推理引擎，再上面是负责部署和管理引擎的控制平面——因为迟早你会运行多个实例。最上面是网关，用来在不同模型和副本之间路由流量。

请求经过网关到达引擎，引擎在 GPU 上运行 kernel。控制平面负责部署和管理网关及引擎，但请求本身不会经过控制平面。

## Token

Token 是语言模型处理的基本单位，大致相当于一个词或词的一部分。上下文窗口、价格和速度都以 token 计算；当有人说每秒多少 token 时，指的就是这个单位。

## 权重和 KV 缓存

权重是固定占用，KV 缓存则会随负载增长。可以把它们分别理解为数据库的固定存储空间和不断变化的工作集。

**权重是固定占用。** 大多数模型以每个参数 2 字节的形式发布（BF16 或 FP16）。因此，一个 8B 模型大约需要 16 GB，而且必须放在 GPU 内存中，不能依赖系统 RAM。在一块 48 GB 的 L40S 上，剩下大约三分之二的空间供其他内容使用。无论只有一个用户还是一百个用户，这个固定数字都不会改变。

**KV 缓存是工作集。** 每生成一个新 token，都需要对之前的 token 进行计算。为了不重复计算历史，推理引擎会为每个进行中的 token 保存 attention 的 key 和 value。KV 缓存大小与上下文长度和并发会话数相乘增长，类似于一个同时受会话大小和用户数量影响的会话存储。

可以根据模型配置估算每个 token 的 KV 缓存大小：

```text
每 token 的 KV 字节数 = 2 × 层数 × KV 头数 × head dimension × 每个值占用的字节数
```

以 FP16 下的 Llama 3 70B 为例（80 层、8 个 KV 头、head dimension 为 128），每个 token 约占 320 KB 的缓存。一个 128K token 的会话需要约 40 GB 缓存。在这种规模下，KV 缓存通常会成为限制 GPU 可服务用户数的因素。

需要注意几个常见的容量估算错误：

- **MoE 模型会常驻所有权重。** 一个总参数量为 320B、每次只激活 18B 参数的模型，在 FP8 下仍然需要约 320 GB；只有计算量随激活参数量变化。
- **应查看 checkpoint 的实际大小，而不是 dtype 表。** Upbound 在自托管某个 MoE 模型时，根据 dtype 估算约 315 GB，但实际 checkpoint 只有 177.7 GB，因为专家权重采用了 4-bit 格式存储。
- **要为运行时开销留出空间。** CUDA graph、activation 和内存碎片都会占用空间。一个在启动时能装下的模型，运行几天后仍可能因为内存不足而崩溃。

## 两个阶段、两种瓶颈

每个请求都在同一块 GPU 上经历两个阶段，而这两个阶段受不同因素限制：

| 阶段 | 工作内容 | 主要限制 | 决定的指标 |
|---|---|---|---|
| Prefill | 并行读取全部输入，包括系统提示词、工具定义和对话历史；生成第一个 token 和 KV 缓存 | 计算能力 | 首 token 时间（TTFT） |
| Decode | 一次生成一个 token；每个 token 都要从内存读取全部活动权重和 KV 缓存 | 内存带宽 | 每个输出 token 的耗时和每秒 token 数 |

生成一个 token 时，每读取一个字节通常只进行一到两次浮点运算，具体取决于权重精度。H100 需要约 295 次运算/字节才能保持满负载，这意味着单个请求只使用了芯片的一小部分，计算单元大多在等待内存。

峰值计算能力大约每两年增长 3 倍，而内存带宽只增长约 1.6 倍。因此，几乎所有优化要么减少每个 token 需要移动的字节数，要么让更多 token 共享每个字节。由于两个阶段的瓶颈相反，加速其中一个阶段的技术往往对另一个阶段帮助不大，所以基准测试通常会分别报告 TTFT 和每秒 token 数。

## 应跟踪的指标

| 指标 | 衡量内容 | 注意事项 |
|---|---|---|
| 首 token 时间（TTFT） | 排队加 prefill，即用户等待看到任何内容的时间 | 推理模型的第一个 token 可能是隐藏思考过程；应测量用户真正看到的第一个 token |
| 每个输出 token 的耗时 / token 间延迟 | 单条流的 decode 速度 | 推测解码和内存带宽都会反映在这里 |
| 每用户每秒 token 数 | 交互性或模型的输出速度 | 批大小增加时会下降 |
| 吞吐量 | 所有用户合计的每秒 token 数 | 批大小增加时会上升 |
| Goodput | 仍然满足延迟目标的吞吐量 | 容量规划应使用这个指标 |
| 端到端延迟 | 请求总耗时 | 取决于模型生成多少内容；长回答耗时 190 秒也可能是健康的 |
| 百分位数 | 各项延迟的 p50、p90、p99 | 用户感受到的是尾部延迟，而不是平均值 |
| 错误和拒答 | 失败或被拒绝的请求 | 应将拒答计入错误，否则上下文限制可能看起来像速度提升 |
| 每百万 token 成本 | GPU 成本除以服务的 token 数 | 应在实际负载下比较 |

每百万 token 成本的计算公式为：

```text
每百万 token 成本 = GPU 每小时成本 /（每秒 token 数 × 3600）× 1,000,000
```

例如，一块每小时 2.90 美元、可持续达到每秒 1,200 token 的 GPU，每百万 token 的成本约为 0.67 美元。

## 延迟与吞吐量

把更多请求批处理在一起会提高总吞吐量，但会降低每个用户的速度。交互式聊天和编码更重视延迟；夜间批处理任务更重视吞吐量。这与把数据库调优为事务型或分析型负载时的取舍相同。在调优之前，应先写清楚工作负载的约束。

## 何时采用各项概念

| 概念 | 作用 | 表明你需要它的信号 |
|---|---|---|
| 让权重装入 GPU | 选择模型、精度和 GPU，使权重装入后仍留有余量 | 引擎无法启动，或启动后几乎没有 KV 缓存空间 |
| 连续批处理和分页 KV 缓存 | 在请求之间共享每次 GPU 计算，并按小块分配缓存 | vLLM 和 SGLang 默认已启用；应检查，不要自己重写 |
| 量化 | 用更少比特存储权重，并把释放的内存交给 KV 缓存 | 请求在排队，但 GPU 仍有空闲计算能力 |
| 前缀缓存 | 重复打开相同提示词时复用已有计算 | agent 或聊天应用重复发送长历史时，应观察命中率 |
| 推测解码 | 先生成多个候选 token，再一次性验证 | 低负载下单条响应仍然输出过慢 |
| 网关和控制平面 | 在副本间路由，并以声明方式管理引擎 | 增加第二个模型、第二个副本或第二个集群 |
| 多 GPU 分片 | 使用张量、流水线或专家并行拆分模型 | 模型无法放入一块 GPU；应在部署前规划 |
| 自动扩缩容 | 根据队列深度和 KV 缓存使用量增减副本 | 空闲 GPU 产生账单，或高峰期出现队列 |
| Prefill/Decode 解耦 | 在不同 GPU 上运行两个阶段 | 长提示词在大规模场景下阻塞流式输出，且具备 RDMA 级网络 |

大多数团队在第一天只需要前几项。等到相应信号出现后，再逐步增加其余技术。

## Agent 带来的变化

编码 agent 和其他 agent 工作负载会给整个系统的每个部分带来压力。Upbound 在 Project Champagne 第 5 部分中测量了这一点：大约 10 名工程师让 Claude Code 等编码 agent 调用自托管模型，流量呈现出以下特点：

- **提示词很长。** 中位数为 59K token，p90 为 125K token。
- **提示词大多重复。** 由于 agent 每轮都会重新发送对话记录，大约三分之二的提示词 token 命中了前缀缓存。
- **思考过程是隐藏的。** 推理模型可能在第一个可见 token 之前思考超过一分钟，因此 agent 与模型之间的每个超时都必须允许这种情况。
- **负载取决于客户端。** 短提示词会话可能启动子 agent，使同时进行的请求数高于长提示词会话。容量规划应按并发中的请求数，而不是按座位数进行。
- **会话会持续数小时。** 流、工具调用和凭证必须在这么长的时间内持续有效。
