# 5. 从分享实践的团队中学习

运行推理所需的很多知识，来自那些记录了系统如何出问题的团队。应批判性地阅读这些案例，也要记录并分享自己的实践。

## 如何阅读案例研究

- 找到配置：模型、硬件、引擎版本和流量形态，并注意日期，因为数字会迅速过时。
- 找到标准：什么算作足够好，以及由谁决定。
- 跟踪故障：发生了什么、团队如何发现、用了多久才检测到。
- 检查方法：是否一次只改变一个因素，并在自己的流量上测量。
- 区分可迁移经验：超时经验适用于任何系统，但某个参数值只适用于特定硬件和引擎版本。

## Project Champagne（2026）

Upbound 使用 Modelplane 在 AWS 和 Nebius GPU 上自托管聊天、编码 agent 和修复 CVE 的构建 agent，并发布了五篇文章记录故障。

- 服务本身反而是较小的问题，TLS、身份、超时、存储和可观测性耗时更多。
- 配额不代表实际容量：获批的 H100 实例配额并没有真正获得一台实例，计划中的 GPU 只在约一半时间可用；一个模型最终被拆到两个区域的两个节点上。
- 启动时装得下并不够：一个聊天模型四天内 OOM 九次。把显存比例从 0.92 降到 0.88、启用可扩展 segment 并将并发序列限制为 16 后，释放了 4.6 GiB。
- 最昂贵的故障往往是静默的：截断流返回 200，指标 API 报告可用但没有数据，监控任务 pending 了六天。
- 超时会层层叠加：15 秒的路由默认值加上 60 秒的负载均衡器空闲超时，会截断仍在输出的答案。
- Agent 是最难处理的客户端：小时级会话超过了 60 分钟令牌寿命，推理模型在第一个可见 token 前思考超过一分钟。
- 低分不一定是模型问题：测试框架中的假 shell 让 Claude 得到 0 分；提高 60 秒空闲超时后，原本失败的模型完成了所有运行。
- “慢”有多种原因：隐藏的最大努力推理、GPU 计算单元低利用率等，都可能让仪表盘看起来正常。
- 负载取决于客户端：agent 提示词中位数为 59K token，约三分之二命中前缀缓存；短提示词会话因为启动子 agent 而保持更多并发请求。
- 引擎影响比预期更大：在相同的两台 8-GPU 节点上，从 vLLM 换到 SGLang 是最大的单项收益。128K 上下文上限看起来更快，只是因为它拒绝了长对话。

完整系列包括：为什么自托管推理、推理生命周期、构建安全 agent、可观测性，以及如何从试点扩展到团队。
