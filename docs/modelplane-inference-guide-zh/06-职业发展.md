# 6. 转向推理工程职业

你不需要从头开始。把推理概念加入已有的平台技能，并公开展示工作成果。这个领域还很年轻，新人可以较快追上。

## 选择方向

| 方向 | 重点 | 适合人群 |
|---|---|---|
| 推理平台 | 集群、GPU 调度、网关、自动扩缩容、多云容量 | 喜欢 Kubernetes 和分布式系统 |
| 推理可靠性 | SLO、可观测性、容量规划、发布、事故响应 | 有值班和 SRE 经验 |
| 运行时性能 | 引擎调优、量化、推测解码、并行、kernel | 喜欢 profiling 和贴近硬件工作 |

## 学习路径

1. 学习模型本身，而不只是容器：Transformer、attention、KV 缓存、dense 与 MoE，以及如何阅读模型配置。目标是在五分钟内估算模型所需内存。
2. 深入学习一个引擎。可以选择 vLLM，理解每个核心参数牺牲了什么，并亲自测量 TTFT 和逐 token 延迟。
3. 把平台技能迁移到 GPU：设备分配、能维持长流的网关、基于推理指标的自动扩缩容和引擎可观测性。
4. 学习判断质量和成本：构建评估、进行容量扫描，并计算每百万 token 成本。这通常是平台工程师的短板，也是该岗位最能创造价值的地方。

## 能证明能力的项目

- 在一块 GPU 上用 vLLM 服务 8B 模型，扫描 1、10、50 个并发用户，发布配置、负载脚本、图表和每百万 token 成本。
- 预测并测试 GPU 能容纳多少 32K token 会话，发布预测、结果和差异原因。
- 比较 FP16、FP8 和可行的 4-bit 格式，将评估分数与延迟、吞吐量放在一起。
- 将共享内容分别放在提示词开头和结尾，比较缓存命中率和 TTFT。
- 在 Kubernetes 上部署 GPU Operator、带 TLS 和认证的网关、基于队列深度的自动扩缩容和监控面板。
- 在 agent 流量上比较 vLLM 和 SGLang，一次只做一个变化。
- 为一个 agent 任务构建使用确定性评分器的评估框架。
- 复现超时、OOM 或卡住的发布，并写出简短的事后分析和运行手册。

## 公开展示工作

README 应像实验报告：写清问题、配置（模型、GPU、引擎版本和参数）、方法、数字结果、意外发现和复现方式。也要发布失败经历；带版本和成本的结果更容易被信任和复用。可以把每个项目写成短文，向 meetup、CNCF 活动和社区直播投稿。

## 参与开源

推理项目仍然需要大量平台工作，包括可配置负载均衡器、证书签发、独占设备的 Recreate 发布、真实的 Ready 信号、开箱即用的引擎指标采集，以及适合长时间 agent 的认证。可以关注 vLLM、SGLang、llm-d、KServe、NVIDIA Dynamo、Agent Router、Gateway API Inference Extension、Modelplane 和 Crossplane。好的首次贡献包括复现并报告故障、编写运营文档、补充指标和告警、改进清单与 Helm chart，以及为手头硬件贡献基准测试。

## 持续学习

每次升级引擎都要阅读发布说明并重新运行基准测试。应阅读 Orca、PagedAttention、DistServe、推测解码和 FlashAttention 等论文；关注相关实践者和社区；学习为 agent 构建评估；能够向财务伙伴解释每百万 token 和每用户会话成本。

## 查找职位

职位名称还不统一，可以搜索 inference engineer、performance engineer、model serving engineer、ML infrastructure engineer 和 AI platform engineer。你也不一定需要立刻换工作：如果公司计划自托管第一个模型，可以主动承担，因为运行真实系统是最直接的经验。

## 面试准备

应准备回答：prefill 与 decode 的瓶颈差异；计算能力与内存带宽趋势；模型和 KV 缓存的内存计算；goodput 的意义；前缀缓存适合哪些应用；如何在两块 80 GB GPU 上运行 70B 模型；权重量化何时有效；何时不用推测解码；chunked prefill 如何改善流；如何选择并行策略；如何区分计算瓶颈与带宽瓶颈；如何诊断 TTFT、隐藏推理和慢生成；GPU 上一百万 token 的成本；容量如何随用户增长；如何安全发布新模型；以及一个有真实数字的故障故事。
