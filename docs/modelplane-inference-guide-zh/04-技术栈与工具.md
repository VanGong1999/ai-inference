# 4. 技术栈

应深入学习推理引擎。Kubernetes、网关和可观测性已有经验的工程师，需要重点理解它们在推理场景中的变化；对于 kernel，能够阅读 profile 通常就足够。大多数推理工程工作发生在更高层。

| 层 | 应了解的工具 | 优先掌握 |
|---|---|---|
| Kubernetes 上的 GPU | NVIDIA GPU Operator、DRA、NVIDIA DRA driver、DCGM exporter | GPU 如何被声明、请求和放置 |
| Kernel 和库 | CUDA、PyTorch、Triton、FlashAttention、torch.compile | kernel 基础、融合以及 profile 阅读 |
| 推理引擎 | vLLM、SGLang、TensorRT-LLM；本地工作可用 Ollama 和 llama.cpp | vLLM 的显存比例、最大序列数、最大模型长度、张量并行、量化、前缀缓存和 chunked prefill 参数 |
| 分布式服务 | NVIDIA Dynamo、llm-d、KServe、LeaderWorkerSet | 多 GPU、多节点布局以及 prefill/decode 分离 |
| 网关和路由 | Envoy Gateway、Agent Router、Gateway API Inference Extension | 流式传输、超时、认证、按模型名路由和缓存感知路由 |
| 控制平面 | Modelplane、Crossplane | 跨环境声明集群、硬件类别、部署和缓存 |
| 可观测性 | Prometheus、Grafana、OpenTelemetry、Loki、Sloth、Pyrra | 引擎指标、真实 GPU 活跃度和用户延迟 SLO |
| 基准测试 | vLLM benchmark、NVIDIA AIPerf、GuideLLM、SemiAnalysis AgentX | 真实提示词下的并发扫描和延迟百分位数 |
| 评估 | UK AI Security Institute 的 Inspect、Hugging Face upskill | 对任务最终状态使用确定性评分器 |
| 模型 | Hugging Face Hub、safetensors | 读取模型配置和检查实际文件大小 |

## 如何选择引擎

引擎控制批处理、内存管理、kernel 选择和 API 兼容性，往往比升级硬件更能影响成本和吞吐量。

- **vLLM：** 模型覆盖面广，原生支持 OpenAI 和 Anthropic API，通常是首个部署选择。需要固定版本，并在每次升级后重新基准测试。
- **SGLang：** 具有 radix-tree 前缀缓存和偏好共享缓存前缀请求的调度器，适合 agent 和长多轮会话。社区规模较小，新模型可能需要 nightly 构建。
- **TensorRT-LLM：** 针对 NVIDIA 硬件优化，包括 Blackwell 上的 FP4；代价是绑定 NVIDIA 生态。
- **NVIDIA Dynamo：** 位于引擎之上的分布式层，可协调多节点和 prefill/decode 拆分；只有达到多节点规模时才值得引入。
- **Ollama、llama.cpp：** 适合本地学习和原型验证，不适合大量并发用户。

Hugging Face TGI 曾经很常见，目前处于维护模式，选择引擎前应检查发布节奏、维护者和基金会支持。引擎每几周就会增加新参数，升级后要重新跑基准测试。

## Modelplane 的位置

Modelplane 是 Upbound 开源的 Apache 2.0 项目，基于 Crossplane 构建。它通过 Kubernetes 风格的声明式 API，在云、neocloud 和自有 GPU 之间编排模型、推理引擎和 AI 基础设施。它可以创建推理集群，也可以使用已有集群。

Modelplane 将职责分成三层：平台团队负责集群、硬件类别和网关；模型运营者或推理工程师负责部署、服务和权重缓存；Modelplane 负责由两者组合出的端点和副本。ModelDeployment → ModelReplica → ModelService → ModelEndpoint 类似于跨整个 GPU 机群的 Deployment → Pod → Service → Endpoint。用户和 agent 不会创建这些资源，而是按模型名调用 InferenceGateway。

Modelplane 默认把 vLLM 和 SGLang 的指标映射为统一名称，也可以用 MetricMapping 接入其他引擎。

## 建议的学习顺序

1. 在一块 GPU 上运行 vLLM，通过 OpenAI 兼容 API 调用并读取指标端点。
2. 使用 NVIDIA GPU Operator 将它部署到 Kubernetes，并用设备选择器进行放置。
3. 在前面加入配置了 TLS、认证和长流超时的网关。
4. 将引擎和 GPU 指标采集到 Prometheus，构建核心面板。
5. 进行并发扫描，同时运行小型评估套件。
6. 使用 SGLang 服务同一个模型，并在自己的流量上比较。
7. 使用张量和流水线并行将更大模型拆到多块 GPU，再尝试分布式服务层。
8. 学习足够的 CUDA 和 profiling，理解 kernel 或参数为何产生差异。
