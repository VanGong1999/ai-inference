# 3. 在生产环境中运行推理

在生产环境中，每个选择都要在延迟、吞吐量、成本和质量之间做取舍，而且通常 GPU 总是不够。生产系统的设计应从使用场景开始，而不是从硬件开始。

## 3.1 从使用场景开始，而不是硬件

编码 agent 需要长上下文、可靠的工具调用解析、流式输出、可持续数小时的会话，以及兼容 Anthropic 的 API。聊天系统需要较低的首 token 延迟、真实并发能力和兼容 OpenAI 的 API。平台本身则需要真实域名上的 TLS、与公司域名关联的身份、能够区分健康引擎和繁忙引擎的可观测性，以及无需人工盯守的正确 GPU 放置。

应将交互式工作负载与批处理工作负载分开。它们需要不同的目标，通常也应使用不同的部署。在测试之前先写清楚通过标准和失败标准。

## 3.2 有意识地选择模型

- 使用自己的任务进行评估；公开基准测试衡量的是别人的工作负载。
- 先从小模型开始，再逐步扩大。只有几亿到数十亿激活参数的小型 MoE 模型可以更快积累运维经验，也更不容易付出昂贵代价。
- 最新模型不一定是正确选择。模型发布速度可能快于硬件规划；所谓“小型”旗舰模型也可能需要多块最大规格的 GPU。
- 确认推理引擎确实能在你的硬件和构建版本上加载模型。
- 检查模型许可证，部分开放模型限制商业使用。
- 检查 chat template 和解析器。设置错误可能破坏工具调用，即使每个请求仍然返回 HTTP 200。

## 3.3 按运行时而不是启动时进行容量规划

启动时能装下的模型，在真实流量下仍可能因为内存碎片超过已分析的峰值而 OOM。预算必须包含权重、KV 缓存和 CUDA graph、activation 等运行时开销。每个请求都应设置最大输出长度；否则，一个请求就可能拖垮所有用户，客户端放弃后请求仍可能继续生成。

缩短最大上下文可以为更多用户释放 KV 缓存，但也会拒绝所有更长的对话，因此这些拒绝必须计入错误。

## 3.4 主要优化技术

现代引擎通常默认开启连续批处理和分页 KV 缓存。其余技术需要根据模型和工作负载选择：

| 技术 | 改善内容 | 成本或风险 | 适用场景 |
|---|---|---|---|
| 连续批处理 | 提高吞吐量 | 批次变大时单用户速度下降 | 基本总是使用 |
| 分页 KV 缓存 | 提高并发能力 | 实际风险很小 | 基本总是使用，vLLM 默认支持 |
| 前缀缓存 | 降低重复提示词的 TTFT 和 prefill 成本 | 第一个不同 token 之后就无法复用 | 系统提示词、RAG、多轮聊天、agent |
| 权重量化 | 降低 decode 成本；FP8 也能改善 prefill | 可能损失质量，必须评估 | 硬件原生支持且评估可接受的最低精度 |
| KV 缓存量化 | 容纳更多缓存并提高移动速度 | 误差会逐 token 累积 | KV 缓存成为瓶颈时 |
| 推测解码和多 token 预测 | 低批量时提高 token 速度 | 猜测被拒绝时会浪费计算 | 延迟重要且输出较可预测时 |
| 张量并行 | 让大模型装入一台机器并提高单用户速度 | 需要 NVLink 等高速互联 | 单节点内的大模型 |
| 专家并行 | 提高 MoE 吞吐量 | 需要处理专家路由 | MoE 模型 |
| 流水线并行 | 让模型跨节点运行 | 每次计算增加延迟 | 模型无法放入一台机器 |
| Prefill/Decode 解耦 | 消除两个阶段之间的互相干扰 | 需要 RDMA 级网络传输 KV 缓存 | 大规模、长提示词场景 |

实用原则：把共享内容（系统提示词和工具定义）放在前面，把可变用户输入放在最后，以提高前缀缓存命中率；量化时从不敏感部分开始，再逐步处理 activation 和 KV 缓存；监控推测解码接受率；一次只改一个因素并重新测量；长提示词可以使用 chunked prefill，避免阻塞其他流。

## 3.5 获取 GPU 并正确放置

配额不等于容量。每种实例规格都是独立的容量池。应允许多区域 GPU 池，并让模型定义与实例类型和节点数量解耦。使用 Kubernetes DRA 设备选择器将模型固定到指定 GPU 架构或最低显存；放置结果应根据驱动实际发布的信息验证，而不是相信回显声明内容的状态字段。

还要观察云平台本身，而不只是控制器。SXM GPU（H100、H200、B200）通过 NVLink 连接，而 L40S 和 RTX PRO 6000 等 PCIe 卡没有 NVLink，多 GPU 通信需要经过 PCIe 和主机内存，这会改变并行策略的收益。

## 3.6 网关、路由和超时

不要简单轮询。一个副本可能已经缓存了某个会话的前缀，而另一个副本完全没有。应使用缓存感知或前缀感知路由。根据请求中的模型名路由；同时支持 OpenAI API 和 Anthropic Messages API。长生成和推理模型要求提高路径上每一层的超时，包括网关路由、负载均衡器空闲超时、客户端和重试策略。还要检测被截断的流：它可能以 HTTP 200 返回有效 token 后停止，客户端会误以为答案已经完成。

## 3.7 安全和身份

不要暴露开放端点。网关获得地址前就应应用认证策略，并使用真实域名上的 TLS。浏览器登录可在网关使用 OIDC；运行数小时的 agent 不应使用只有 60 分钟寿命且不会刷新的令牌。不要在两个即将过期的会话之上叠加登录。建立拒绝请求探针矩阵，覆盖缺失、伪造、过期、吊销密钥以及伪造调用方请求头的情况。模型权重应像代码一样对待：优先使用 safetensors，不要启用未经审查的远程代码，并固定模型 revision。

## 3.8 可观测性

应采集引擎 Prometheus 指标，核心面板包括：并发上限、排队请求、KV 缓存使用率、TTFT、每个输出 token 的耗时、每请求输出 token 数、前缀缓存命中率、推测解码接受率、按状态码统计的错误和取消。

还应在服务器端统计工具调用解析失败、长度限制截断、空输出、拒答和隐藏推理 token。不要只看 `GPU-Util`；它只说明 GPU 是否运行过，不能说明芯片实际利用程度。应同时观察 SM 活跃度和 tensor 活跃度。设置用户可感知的 SLO：用户看到第一个 token 的时间、每个输出 token 的耗时，以及请求是否成功完成且工具调用可解析。

## 3.9 自动扩缩容和冷启动

根据队列深度、KV 缓存使用量和进行中的请求数扩缩容，CPU 使用率几乎不能说明推理负载。流量指标可以提前扩容，负载指标则会滞后。新 GPU 节点需要启动、拉取镜像和加载权重，大模型仅加载权重就可能需要半小时；应在每个集群使用共享存储缓存权重。谨慎使用 scale-to-zero，因为 GPU 节点准备好时流量峰值可能已经过去，稀缺容量也可能无法重新获得。

## 3.10 变更管理

跟踪模型、硬件和引擎构建版本的三方矩阵。独占 GPU 上的单副本滚动更新可能死锁，应使用 Recreate 策略或允许一个不可用副本，并预算停机时间。

像测试代码一样测试服务变更：每次只改一项，先写清楚标准，逐步提高并发直到错过标准，并用带置信区间的数字报告容量。变更应经过离线、演练、冒烟、带评估的负载测试、金丝雀和全量发布几个阶段。金丝雀阶段要比较 TTFT、每 token 耗时、错误、工具调用解析失败和长度限制停止次数，并在开始前写好回滚触发条件。

## 3.11 质量与评估

开放模型得分低时，先检查三处：测试框架、基础设施和评分器。先让当前托管模型运行；如果它的分数还低于较弱模型，说明框架有问题。超时、凭证过期和路由错误应标为“未测量”，不要算成模型失败。评分器应评估任务最终状态，而不是 agent 对结果的描述。固定正确答案所依赖的数据，为所有模型提供相同上下文，多次运行测试，并优先采用确定性检查。

## 3.12 事故与调试

要预期静默失败：截断流可能返回 200，指标 API 可能报告可用却没有数据，节点组可能显示 ready。整秒数附近的失败通常是超时；其整数倍可能指向重试。可以暂时绕过一层来判断问题是否移动，并用磁盘、实例或路由的真实状态验证控制器状态。修复应采用增量方式，并将临时绕过方案放在平台旁边、标记好拆除方式，最终把修复提交到上游。

## 首批用户上线前检查清单

- [ ] 已定义使用场景和 TTFT、用户速度、错误率标准
- [ ] 使用自己的评估选择模型，并以当前托管模型作为基线
- [ ] 确认引擎构建可以在目标硬件加载模型
- [ ] 内存预算包含权重、KV 缓存和运行时开销，并设置最大输出 token 和并发序列数
- [ ] 根据驱动验证 GPU 放置，并准备备用实例规格或区域
- [ ] 在网关获得地址前应用认证策略，并使用真实域名 TLS
- [ ] 凭证生命周期足够覆盖 agent 会话
- [ ] 路由、负载均衡器、网关重试、客户端和辅助调用的超时都已提高
- [ ] 已采集引擎指标、GPU SM/tensor 活跃度，并在指标停止到达时告警
- [ ] 已在服务端统计工具解析失败、长度截断和空响应
- [ ] 已建立必须拒绝的请求和必须保持开放的路径探针矩阵
- [ ] 已规划独占 GPU 的发布策略并预算停机
- [ ] 崩溃后仍能保留之前的容器日志
- [ ] 服务变更经过分层测试、并发评估和带回滚条件的金丝雀发布
