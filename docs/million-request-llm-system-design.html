第 1 步

先约束问题本身。

不要直接跳到 GPU。正确的架构取决于工作负载形态。

澄清性问题

  1. 我们要服务哪些模型规模：8B、70B、MoE，还是多个层级？
  2. prompt 与输出长度的分布是怎样的（而不只是平均值）？
  3. SLO 是什么：TTFT、ITL、总延迟与可用性？
  4. 流量是流式聊天、agent、工具调用、批量任务，还是混合？
  5. 结构化输出、安全、隐私与审计的要求有多严格？
  6. 有多少流量是突发性的、区域性的，或租户隔离的？
面试官眼里的好信号：表明「数百万请求」这个信息是不够的。tokens/sec、上下文长度、输出长度与 P99 SLO 才真正决定设计。

第 3 步

服务引擎是课程优化技术的汇聚点。

PagedAttention

以块（block）存储 KV Cache，避免连续分配的浪费，支持高并发。

连续批处理（Continuous batching）

每个 decode 步都接纳新请求，使已完成的序列不会让 GPU 空闲。

分块预填充（Chunked prefill）

把长 prompt 拆成小块，使 prefill 不会饿死 decode。

前缀缓存（Prefix caching）

为共享的系统 prompt、历史与文档前缀复用 KV。

量化（Quantization）

降低权重带宽与内存占用，发布前做质量检查。

投机解码（Speculative decoding）

在草稿接受率高时，用小草稿模型减少大模型的前向传播次数。

扩缩容：复制副本（replicate）换吞吐；当单模型副本放不下或需要更多带宽时用张量并行（tensor parallelism）；只在不可避免跨节点时用流水线并行（pipeline parallelism）；当长 prefill 突发干扰 decode SLO 时用分离式服务（disaggregated serving）。

最终脚本

一个完整的面试回答。

我会先通过 prompt 长度、输出长度、请求速率、并发量、流式要求，以及 TTFT、token 间延迟（ITL）、总延迟与可用性的 SLO 来刻画工作负载。「数百万请求」不是规模单位；tokens/sec 与上下文长度分布才是。

架构从一个区域边缘（edge）与 API 网关（gateway）开始，负责认证、配额、限流、请求整形与输入安全检查。之后我会用一个智能推理路由器（router）：选择模型层级、决定在线还是批量、应用金丝雀流量规则，并把缓存敏感的请求路由到已经持有有用前缀 KV 状态的副本。

对在线服务引擎，我会用 vLLM 或 TensorRT-LLM 风格的运行时，具备：PagedAttention 做 KV 内存管理、连续批处理做吞吐、前缀缓存应对重复 prompt、分块预填充保护 decode，并在草稿接受率高的场景用投机解码。只在评测显示质量可维持后才做量化。

对大模型，我会复制模型实例换吞吐，在高带宽 NVLink 域内使用张量并行，只在模型容量迫使时跨节点用流水线并行。如果流量有很多长 prompt，我会拆分 prefill 与 decode 池，使计算密集的 prefill 不干扰内存带宽受限的 decode。在选择分离之前，我会计入 KV 传输税。

我会把批量工作负载与实时流量分开。批量任务可以排队以换取高 GPU 利用率，但在线 decode 不应排在离线摘要或评测工作之后。过载时，我会根据产品需求使用准入控制（admission control）、低层级回退、更短的最大输出，或异步交接。

每次发布都经过离线评测、影子流量、金丝雀发布与回滚门槛。仪表盘跟踪 TTFT、ITL、总延迟、队列深度、GPU 利用率、VRAM、KV Cache 命中率、输出 token 分布、schema 合法性、安全标志与每请求成本。核心取舍是「延迟 vs 利用率」：批处理、缓存与路由，就是我在「每个请求类别」而非「全局统一」地做这个取舍的方式。
