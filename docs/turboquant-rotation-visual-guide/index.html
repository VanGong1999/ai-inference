TurboQuant:
The Rotation Trick

Google's new method squeezes the KV cache from 16 bits down to 2.5 bits per value — with no training and no calibration. The entire idea: rotate before you quantize. Here's why that one line of linear algebra works.

Part 1

The KV cache is eating your GPU

During autoregressive generation, every token the model has seen leaves behind a key vector and a value vector in every attention layer. These vectors get stored so the next token's query can attend back over the whole history. That store is the KV cache, and it grows linearly with sequence length.

Llama 3 70B, 8K context, single request

KV cache = 2 (K + V) × 80 layers × 8192 tokens × 8192 dim × 2 bytes
≈ 21 GB

That's 21 GB of memory just for one user's context. Batch 32 users and the KV cache alone needs more memory than the model weights.

What's actually inside the cache?

For each token, each layer, each attention head, you have two vectors:

Key vector (k)

128-dim per head. Used to compute q · k — the attention score for a future query.

Value vector (v)

128-dim per head. The content the future query retrieves — weighted by attention scores and summed.

The natural question: can we store these vectors with fewer bits? Naive answer: just round each number from 16 bits to 4 bits. That gives you a 4× saving — but the model's quality falls off a cliff. To understand why, we have to look at what these vectors actually look like.
Part 2

K and V vectors are spiky

If keys and values were nice and uniform, quantization would be easy. They aren't. Real attention vectors have a few enormous components and many tiny ones — the outlier phenomenon (Dettmers 2022, Sun 2024). Here's a typical 16-dim key vector from a transformer:

Massive component (the outlier)
Tiny components (the rest)

What happens when we quantize this?

The quantization grid has to span the full range. With 4 bits (16 levels), each bucket covers about 1/16 of the range. The huge component lands in the top bucket. Every tiny component lands in the same bucket as zero. They all collapse to the same value.

before: [0.001, 0.002, 0.98, 0.001, 0.003, ...]
after:  [0,     0,     1.00, 0,     0,     ...]
The vector has been snapped to a cardinal direction: a unit vector pointing along a single coordinate axis. All the subtle directional information — the part the model actually uses to compute attention scores — is gone. We've spent 64 bits to represent something that only carries log₂(2·16) = 5 bits of real information.
Part 3

What TurboQuant actually rotates

TurboQuant inserts one extra step into the attention pipeline. Before a key or value vector is written to the cache, it gets multiplied by a fixed random rotation matrix R. Before it's read back, the rotation is undone. The rotation is shared across all tokens, all layers, all heads — one matrix, generated once.

Read path — computing attention

The query q for the new token gets rotated by the same R. Now the inner product happens entirely in rotated space:

score = (R q) · Q(R k)   ≈   (R q) · (R k) = qᵀ Rᵀ R k = q · k

The last equality uses Rᵀ R = I — the defining property of an orthogonal matrix. The attention score is preserved exactly (up to quantization error), and we never have to actually un-rotate.

Critical detail: R is a square orthogonal matrix. It rotates a vector to a new orientation but never changes its length, never changes any angle between two vectors, and never adds or removes information. It's a perfectly invertible transformation — the kind of operation that sits in the background of so many beautiful results in linear algebra.

Part 4

Watch a spiky vector get rotated

A unit-length spiky vector lives near a coordinate axis — near one of the poles of the sphere. Most of its length is concentrated in a single component. A random rotation lands it almost anywhere on the sphere — and almost everywhere on the sphere is far from any axis.

drag to rotate sphere · click button to rotate vector

Before rotation: spiky

One component dominates. The vector lives at the pole.

After rotation: spread

Energy is shared across all dimensions. No component is special.

The geometric truth: in d dimensions, the area of the sphere is overwhelmingly concentrated in a thin equatorial band — not at the poles. The fraction of the sphere within "spiky distance" of any axis shrinks exponentially with d. After rotation, every component is roughly the same size: ±1/√d. For a 128-dim attention head, that's about ±0.088 per component — remarkably uniform.
Part 5

Why a uniform vector quantizes well

Quantization replaces every component independently with the nearest grid point. The grid has to span the full range of values — so its width is set by the largest component. Every other component pays for that width with crushed precision.

Why a random rotation works

You might wonder: why use a random matrix instead of a learned one? Two reasons:

No data dependence

A learned rotation would need calibration data and could overfit to that specific distribution. Random rotation gives a guarantee that holds for any input vector.

High-dim concentration

In high dimensions, a random rotation almost surely de-spikes any vector. The probability of landing back near a coordinate axis is exponentially small in d.

Free at inference

R can be a Hadamard-like structured matrix — multiplying by it costs O(d log d), not O(d²). For d=128, that's basically free compared to attention itself.

Takeaway

One line of linear algebra

Key and value vectors in transformers cluster near coordinate axes. Quantization grids hate that, because they snap every spiky vector to a cardinal direction and lose all the subtle information. A random rotation moves every vector to a generic place on the sphere where every component is roughly the same size. Now the quantization grid serves every component equally well.

store: Q(R k),   Q(R v)
read:   (R q) · Q(R k) ≈ q · k

That's the entire idea. No training, no calibration, 5–6× smaller cache, and the math is honest: in high dimensions, a random rotation almost always saves you.
