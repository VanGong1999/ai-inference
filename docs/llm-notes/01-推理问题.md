# 第 1 章 · 推理问题（The Inference Problem）

> Efficient LLM Inference — Interview Pocket Notes · 第 1 章

## 1.1 训练 vs. 推理：根本不同的目标

训练（training）一个大型语言模型时，目标是在海量数据集上最小化损失函数。系统以大批量（large batch）处理数据，在多块 GPU 上累积梯度、执行反向传播（backward pass）、更新数十亿参数。**吞吐量（throughput）是最高指标**：我们希望在整个训练周期内，每秒处理尽可能多的 token，摊薄到整个训练过程。单次前向传播的延迟（latency）基本无关紧要——真正重要的是以天或周为单位衡量的总体训练时长。

推理（inference）是训练的反面。此时模型参数已经冻结，任务是对每个独立请求（通常来自正在等待响应的真实用户）尽可能快、尽可能便宜地完成一次前向传播——把输入 prompt 转化为预测输出。

> **定义：推理（Inference）**
>
> 推理是指在不更新模型参数的前提下，把训练好的神经网络模型运行在新的、未见过的输入数据上，以产生预测或输出。

推理与训练的目标在三个关键维度上截然不同：

- **延迟优先于吞吐**：等待响应的用户直接感知延迟。200 ms 的响应感觉是「即时」的；3 秒的响应感觉就很慢。
- **内存效率**：推理时通常不需要存储优化器状态或梯度缓冲，但必须为自回归生成管理 KV Cache。
- **单请求成本**：生产环境要服务数百万请求，单请求成本直接决定盈利能力。

## 1.2 Token 生成循环详解

现代 LLM 是**自回归（autoregressive）**的：一次生成一个 token，每个新 token 都以所有此前生成的 token 为条件。这构成了 LLM 推理的基本循环。

**自回归生成循环**

1. 接收一个 prompt（输入 token 序列）。
2. 对整个 prompt 并行执行一次 **prefill（预填充）前向传播**，为所有输入 token 计算注意力 key 和 value 并缓存起来。
3. **自回归解码（decode）**：每一步把上一个生成的 token 作为输入，对 KV Cache 计算注意力，采样出下一个 token。
4. 重复第 3 步，直到生成停止 token 或达到最大长度。

prefill 阶段是**算力受限（compute-bound）**的：我们并行处理大量 token，充分用满 GPU 的 Tensor Core。而 decode 阶段本质上是**内存带宽受限（memory-bandwidth-bound）**的：一次只处理一个 token，但每一步都要把整个 KV Cache 从 GPU 显存中加载出来。这种不对称性，驱动了推理系统的大部分复杂性。

## 1.3 延迟、吞吐与成本：铁三角（The Iron Triangle）

推理优化处在一个「不可能三角」中。改善一个维度往往要牺牲另一个：

| 指标 | 定义 | 如何改善 |
|---|---|---|
| **延迟（Latency）** | 从请求到完成的时间。关键子指标：**TTFT**（Time to First Token，首 token 时间）和 **TPOT**（Time Per Output Token，每输出 token 时间） | 减小模型尺寸、谨慎增大批大小、使用投机解码、优化 KV Cache |
| **吞吐（Throughput）** | 所有并发用户每秒生成的 token 数 | 增大批大小、使用连续批处理、张量并行 |
| **成本（Cost）** | 每生成 100 万 token 的美元成本 | 量化模型、使用高效服务框架、优化硬件利用率 |

铁三角的具体表现是：最大化吞吐需要大批量，但大批量会增加单请求延迟；最小化延迟往往需要单独服务每个请求，这会浪费 GPU 利用率并推高成本。**推理工程，就是针对你的具体应用需求，聪明地权衡这些取舍的艺术。**

## 1.4 内存带宽：真正的瓶颈

一个常见误解是推理是算力受限的——我们需要更多 FLOPS。实际上，对自回归 LLM 解码而言，瓶颈几乎总是**内存带宽（memory bandwidth）**：即把模型权重从 GPU 显存（HBM）加载到 GPU 计算核心的速度。

考虑一个 70 亿参数、以 16 位精度存储的模型。模型权重约占用：

```
7 × 10⁹ × 2 bytes = 14 GB
```

一块 NVIDIA A100 GPU 提供约 **2 TB/s** 的 HBM 带宽。把所有权重加载一次（即一个 decode 步）的理论延迟下界为：

```
14 GB / 2000 GB/s = 7 ms
```

这还没算任何计算。如果以批大小 1 运行，我们要花这些时间加载权重，却只为生成一个 token。若以批大小 64 运行，同一次权重加载被摊到 64 个请求上，吞吐大幅提升而延迟几乎不变。

## 1.5 Roofline 模型

Roofline 模型为理解某个运算到底是「算力受限」还是「内存受限」提供了一个清晰框架。对任意运算：

```
实际性能 (FLOP/s) = min(峰值 FLOP/s, 算术强度 × 峰值带宽)
```

其中**算术强度（Arithmetic Intensity）**以「每次字节内存访问对应的 FLOP」来衡量。

**实用 Roofline 洞见**

- **矩阵-向量乘（matrix-vector multiply）**是批大小 1 时 decode 步的核心，算术强度很低（约 1–2 FLOP/byte），稳稳落在内存受限区。
- **大矩阵-矩阵乘（matrix-matrix multiply）**对应长 prompt 的 prefill，算术强度高，接近算力上限。

这就是为什么 prefill 与 decode 行为如此不同、又各自受益于不同优化的原因。

## 面试准备 · 模拟问答（Mock Q&A）

### Q1.1 什么是 LLM 推理中的 prefill 与 decode？为什么这对系统设计很重要？

**答**：prefill 阶段在单次并行前向传播中处理整个输入 prompt，因而是**算力受限**的——我们把大的 token 矩阵与权重矩阵相乘。decode 阶段一次自回归地生成一个 token，因而是**内存带宽受限**的——每生成一个 token 都要加载全部模型权重。这一区别对系统设计至关重要：prefill 与 decode 有非常不同的最优批大小、GPU 利用率画像和延迟敏感度。像 Splitwise 和 Mooncake 这类现代系统在物理上把 prefill 与 decode 分到不同的 GPU 池上，让二者能独立扩展与优化。

### Q1.2 解释推理的「铁三角」。为一个延迟敏感的聊天机器人应用做优化时，你会如何决策？

**答**：推理铁三角描述的是延迟、吞吐与成本之间的张力——改善一个通常会牺牲另一个。对于延迟敏感的聊天机器人，我会优先 **TTFT 和 TPOT**。具体做法：(1) 用更小或已量化的模型以减少每步计算；(2) 保持较小的批大小，或用带严格 SLO 感知调度的连续批处理；(3) 使用投机解码，每步生成多个 token；(4) 使用前缀缓存，跳过重复系统 prompt 的 KV Cache 重复计算。作为低延迟的代价，我接受更高的单 token 成本。

### Q1.3 为什么 LLM 解码的瓶颈通常是内存带宽，而不是原始算力（FLOP/s）？

**答**：在小批量的自回归解码中，GPU 每生成一个 token 都必须从 HBM 加载整个模型权重。一个 FP16 的 7B 模型是 14 GB；即使在 2 TB/s 带宽的 A100 上，每步也要约 7 ms。而与此同时，单个 token 上的实际计算量相对 GPU Tensor Core 能处理的能力来说小得微不足道。矩阵-向量乘（decode 的关键运算）的算术强度约为 1–2 FLOP/byte，远低于达到算力受限所需的约 300 FLOP/byte 阈值。只有通过增大批大小，我们才能摊薄权重加载成本、趋近算力受限。

### Q1.4 你如何测量和报告推理性能？在生产服务系统中会埋哪些指标？

**答**：我会跟踪：**TTFT**（首 token 时间，决定用户感知的响应快慢）、**TPOT**（每输出 token 时间，决定流式输出的流畅度）、**吞吐**（所有用户合计 tokens/秒）、**GPU 利用率与显存利用率**、**goodput**（满足 SLO 的请求占比）、**队列深度**（检测过载），以及**每百万 token 成本**。我会用分位数看板（p50、p95、p99）而不是平均值，因为尾延迟才是破坏用户体验的元凶。我还会单独跟踪 prefill 延迟与 decode 延迟，以便独立定位瓶颈。

### Q1.5 有同事认为：既然 FLOP/s 的增长一直快于内存带宽，推理很快会变成算力受限。你如何回应？

**答**：这是经典的**「带宽墙（bandwidth wall）」**论点。我部分同意其观察，但不同意其结论。确实，近几代 GPU 的算力 FLOP/s 增长快于 HBM 带宽。然而，单批量 decode 的算术强度太低（1–2 FLOP/byte），即便 FLOP/s 大幅提升，除非批大小急剧增大或模型架构改变，我们依然内存受限。此外，量化等技术是「刻意用算力换取更少的内存流量」，反而把我们继续留在内存受限区。前进的方向是提升「每加载一个字节所对应的算术强度」的架构与系统——比如 GQA、MLA、高效的 KV 缓存——而不是指望更快的算力。
