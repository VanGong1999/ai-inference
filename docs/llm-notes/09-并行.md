# 第 9 章 · 大模型推理的并行（Parallelism for Large Model Inference）

> Efficient LLM Inference — Interview Pocket Notes · 第 9 章

## 9.1 为什么需要并行

一个 405B 模型在 BF16 下光权重就需要 810 GB 显存。即便是最大的单块 GPU（H100 SXM，80 GB HBM）也装不下。对前沿规模的模型，并行不是可选项——是唯一能服务它们的办法。

## 9.2 张量并行（Tensor Parallelism）

**张量并行**（Shoeybi et al., 2019 — Megatron-LM）把单个权重矩阵切分到多块 GPU。对线性层 `Y = XW`：

- **列并行（Column parallelism）**：沿列切 `W`：`[W₁|W₂]`。每块 GPU 独立计算 `Yᵢ = XWᵢ`，结果用单次 **AllGather** 集合通信拼接。
- **行并行（Row parallelism）**：沿行切 `W`。每块 GPU 算一个部分和，结果用 **AllReduce** 合并。

在 MLP 块中，第一层用列并行、第二层用行并行，每 Transformer 层只需一次 **AllReduce**——在 NVLink 上高效，但在 PCIe/InfiniBand 上昂贵。

**扩展效率**：张量并行最多能很好地扩展到注意力头数（对 8 个 KV 头的模型即 8 块 GPU；超过之后，有些 GPU 上的某些头就没有活干了）。通信开销随张量并行度**二次**增长，实际扩展被限制在单个 NVLink 连接的节点内的 8 块 GPU。

## 9.3 流水线并行（Pipeline Parallelism）

流水线并行把 Transformer 的不同层分到不同 GPU：GPU 0 放第 1–10 层，GPU 1 放第 11–20 层，依此类推。数据像流水线一样流动：GPU 0 计算并把激活传给 GPU 1，GPU 1 再传给 GPU 2，以此类推。

关键挑战是**流水线气泡（pipeline bubbles）**：靠后阶段的 GPU 在等待前面阶段产出激活。微批（micro-batching）能降低气泡占比（流水线深度 `p`、微批数 `m` 时，气泡占比约 `(p−1)/(m+p−1)`）。

流水线并行通信高效（只在阶段边界传激活，无需完整 AllReduce），可跨由慢速 InfiniBand 连接的节点扩展，适合超大模型（>100B 参数）。

## 9.4 混合专家推理（Mixture of Experts Inference）

**混合专家（MoE）**模型（Mixtral、DeepSeek-V2、Grok-1）把密集 FFN 层替换成 `E` 个专家网络的集合。路由器为每个 token 选择 top-K 专家：

```
y = Σ_{k∈Top-K} g_k · Expert_k(x)
```

MoE 模型总参数量高，但**每 token 活跃参数量低**：Mixtral 8×7B 总参数 47B，每 token 只激活 13B。这让推理更快（每 token 计算更少），但更难服务：

- **专家并行（expert parallelism）**：每块 GPU 承载一部分专家，token 通过 **AllToAll** 集合通信跨 GPU 路由。
- **专家负载不均**：某些专家可能收到很多 token 而别的很少，造成 GPU 不均衡。
- **专家卸载（expert offloading）**：对超大 MoE 模型，专家被卸载到 CPU/NVMe，按需加载。

## 面试准备 · 模拟问答（Mock Q&A）

### Q9.1 解释 Transformer MLP 块的张量并行。需要哪些通信集合、在何时？

**答**：在标准 MLP 块 `Y = GeLU(XW₁)W₂` 中，跨 `N` 块 GPU 的张量并行：(1) **列并行第一层**：`W₁` 沿列切，每块 GPU 持 `[W₁]_{:,i:j}`，独立计算 `H = GeLU(XW₁)` 的一个分片。这里不需要通信。(2) **行并行第二层**：`W₂` 沿行切，匹配 `H` 的列分片。每块 GPU 算 `Yᵢ = HᵢW₂,ᵢ`，一个部分和。跨全部 `N` 块 GPU 的 **AllReduce** 把这些部分和合并成完整 `Y`。总计：每 MLP 块一次 AllReduce，每注意力块一次（同样结构）。AllReduce 量：每层 `2 × 批大小 × 序列长度 × d_model`。在 NVLink 上快；跨 PCIe 会主导延迟。

### Q9.2 推理时你何时选张量并行而非流水线并行？

**答**：我会选**张量并行**当：(1) 模型能装进单节点、且 GPU 之间是 NVLink 互连——TP 需要频繁 AllReduce，要求高带宽；(2) 最小化延迟至关重要——TP 按 GPU 数成比例地减少每层计算时间（每块 GPU 每层做 1/N 的活）；(3) 模型有很多可均匀划分的注意力头。我会选**流水线并行**当：(1) 模型太大、单节点装不下——PP 只需在层边界传激活，可在较慢的节点间 InfiniBand 上做；(2) 吞吐比延迟更重要——PP 引入流水线气泡延迟，但能实现高批量吞吐；(3) MoE 模型的专家并行，它天然映射到 PP。实践中生产系统**二者结合**（3D 并行）：节点内 TP、节点间 PP。

### Q9.3 解释 MoE 模型中的专家路由机制。它给推理服务制造了哪些挑战？

**答**：MoE 模型把每个 FFN 层替换成 `E` 个专家网络和一个路由器。路由器（通常是学到的线性投影 + softmax）为每个 token 计算路由权重：`g = softmax(xW_r)`。选出 top-K 专家（通常 K=2），其输出加权求和。对推理服务，挑战是：(1) **动态路由**：哪个专家处理哪个 token 随每次输入变化，负载均衡难。一个批次里某些专家收到的 token 可能比别的多 10×（专家坍缩/负载不均）；(2) **专家并行通信**：分布式设置下需要 **AllToAll** 集合通信把 token 路由到正确的专家 GPU——这个通信可能成为吞吐瓶颈；(3) **内存**：即使每 token 只激活 2 个专家，所有 `E` 个专家的权重都必须被加载。专家缓存策略（预加载可能被访问的专家）可缓解。

### Q9.4 流水线气泡占比如何影响流水线并行效率？如何缓解？

**答**：当流水线并行有 `p` 个阶段、逐个处理请求时，前面的 `p − 1` 个阶段在最后阶段收尾时空闲（「气泡」），而第一阶段在最后阶段处理时空闲。气泡占比是 `(p − 1)/p`：对 `p = 8` 阶段，7/8 的 GPU 时间被浪费。**微批缓解**：把批次分成 `m` 个微批并流水线化。气泡占比变成 `(p−1)/(m+p−1)`。对 `p=8, m=32`：气泡 = `7/39 ≈ 18%`。其它技术：(1) **1F1B 调度**：交替前向和反向；(2) **交错流水线（interleaved pipelines）**（Narayanan 等）：给每块 GPU 分配多个不连续的层块，减少气泡但增加通信；(3) 对纯推理（无反向），气泡没那么严重，因为我们可以直接塞更多请求填满。

### Q9.5 什么是大 MoE 模型的专家卸载？它的性能影响是什么？

**答**：专家卸载把专家权重矩阵从 GPU 显存（HBM）移到 CPU DRAM 或 NVMe 存储。对 DeepSeek-V2 这样总参数 236B（某些 MoE 层约 60 个专家）的模型，每 token 只有约 20B 参数活跃——但所有参数必须存放在某处可及。专家卸载的工作方式：专家感知的调度器根据路由决策预测下一批需要哪些专家，提前把它们的权重从 CPU/NVMe 预取到 GPU。当前不用的专家权重被驱逐。**性能影响**：PCIe 带宽（约 32 GB/s）远慢于 HBM（2–3 TB/s），任何未命中的专家加载都会增加显著延迟（每专家约毫秒级）。这只有在批大小足够大（专家访问模式可预测）、且专家缓存命中率高时才行得通。命中率 70%+ 时，专家卸载能让 200B+ MoE 模型在单个 8-GPU 节点上服务。
