# 第 13 章 · 可观测性与生产工程（Observability and Production Engineering）

> Efficient LLM Inference — Interview Pocket Notes · 第 13 章

## 13.1 生产推理栈

当模型通过离线基准测试时，LLM 的部署还没有完成。生产要求**可观测性（observability）、可靠性、成本管理和持续改进**。生产推理栈在服务引擎之上叠加若干层：

- **日志与追踪（Logging and Tracing）**：每个请求记录 TTFT、TPOT、token 数、模型版本和错误状态。
- **指标与告警（Metrics and Alerting）**：看板跟踪 p50/p95/p99 延迟、吞吐、GPU 利用率、错误率。
- **A/B 测试基础设施**：模型版本之间的流量切分，用于安全发布。
- **容量规划（Capacity Planning）**：预测查询量，据此预配硬件。
- **成本归因（Cost Attribution）**：按团队或特性拆解 token 成本。

## 13.2 关键指标详解

- **TTFT（Time to First Token）**：从请求发出到第一个生成 token 返回给用户的时长。TTFT 主要由 prefill 计算主导。用户把 TTFT 感知为「思考时间」——TTFT > 1s 会让应用感觉慢，即使后续 token 流式得很快。
- **TPOT（Time Per Output Token）**：流式阶段相邻输出 token 之间的平均时间。人类阅读速度约 250 词/分钟（约 5 tokens/s），所以 TPOT < 200 ms 通常感觉流畅。TPOT 主要由 decode 步延迟和 GPU 内存带宽主导。
- **Goodput**：同时满足所有 SLO 目标（TTFT SLO 和 TPOT SLO）的请求占比。若 TTFT SLO 达标率 95%、TPOT SLO 达标率 95%，且二者独立，则 goodput 为 `0.95² ≈ 90%`。Goodput 比单指标达标率更有信息量。
- **模型 FLOP 利用率（MFU, Model FLOP Utilization）**：理论峰值 FLOP/s 中被有效用于模型计算的比例。优化良好的系统在 prefill 阶段达到 30–60% MFU，decode 阶段则低得多（因内存带宽瓶颈）。MFU 是理解硬件效率的关键指标。

## 13.3 故障模式与排查

| 症状 | 可能原因 | 诊断手段 |
|---|---|---|
| TTFT 高峰值 | 排队时间长；prefill 抢占 | 队列深度监控、prefill 延迟分解 |
| TPOT 退化 | KV Cache 驱逐；批大小增加 | KV Cache 命中率、decode 步延迟 |
| OOM（内存溢出） | KV Cache 溢出；请求激增 | 内存监控、PagedAttention 块统计 |
| 吞吐悬崖 | 张量并行通信瓶颈 | GPU 利用率 vs NVLink 带宽 |
| 质量退化 | 模型版本问题；采样参数变更 | 日志中的模型版本标记、在线评估 |

## 13.4 成本建模

理解并最小化每百万输出 token 成本，对商业可行性至关重要。主要成本构成：

```
每 1M token 成本 = (GPU 每小时成本 × 小时数) / 生成的 token 总数
```

**降低成本的杠杆**：

1. **最大化 GPU 利用率**：更多请求批处理、连续批处理。
2. **减少模型计算**：量化、蒸馏、更小的模型。
3. **抢占式/可中断实例（Spot/Preemptible）**：比按需便宜 60–80%，适用于批量负载。
4. **优化硬件选择**：旧代 GPU（A100 vs H100）对内存受限负载可能更划算。
5. **减少输出 token 数**：指令微调模型，让它更简洁。

## 面试准备 · 模拟问答（Mock Q&A）

### Q13.1 你会如何排查生产 LLM 服务系统中突然出现的 TTFT p99 飙升？

**答**：我的排查会走一个结构化漏斗：(1) **网络层**：检查 p99 TTFT 上升是否与请求到达率上升相关——若相关，系统可能在排队。查队列深度指标。(2) **prefill 计算**：把 prefill 延迟从排队等待中隔离出来。若 prefill 在飙升，检查输入 prompt 长度分布是否改变（更长的 prompt 需要更久 prefill）。(3) **资源竞争**：查 GPU 利用率和 NVLink 带宽——若有别的负载被共置部署，可能在抢 GPU 资源。(4) **KV Cache 压力**：若 PagedAttention 块分配率上升，请求吞吐可能增加了，造成计算竞争。(5) **模型版本或配置变更**：对比日志，识别同一时间窗口内的任何部署。(6) **硬件故障**：退化的 GPU 或 NVLink 链路会导致吞吐下降。用 nvidia-smi 查错误计数。我会把所有这些与飙升时间戳做关联，反向定位。

### Q13.2 什么是 goodput，为什么它比原始吞吐或单指标 SLO 达标率更有意义？

**答**：吞吐衡量每秒生成的总 token——但完全不告诉你用户是否获得了可接受的体验。一个系统可以通过批处理许多长请求获得高吞吐，而单个 TTFT 却违反 SLO。**单指标 SLO 达标率**（如「95% 请求满足 TTFT SLO」）更好，但多个 SLO 可能被独立测量，掩盖复合违约。**Goodput** 是同时满足**所有** SLO 要求的请求占比——TTFT SLO **且** TPOT SLO **且**任何其它定义的目标。它捕获了系统实际让用户满意的速率。若 TTFT 达标率 90%、TPOT 达标率 90%，且违约独立，goodput 可能低至 81%。Goodput 是我在调度决策中要优化的指标：SLO 感知调度器应最大化 goodput，而不只是总吞吐。

### Q13.3 你会如何设计一个 A/B 测试框架，在生产中对比两个 LLM 版本？

**答**：我的设计：(1) **流量切分**：用对 userID（非 requestID）的一致性哈希确定性切分流量——同一用户总是命中同一模型变体，减少用户偏好差异带来的混杂。典型切分：初始 90/10，随信心增长加宽。(2) **指标**：跟踪两个变体的延迟（TTFT/TPOT）、质量信号（赞/踩、会话时长、追问数）和每请求成本。(3) **统计显著性**：用序贯 A/B 测试（如 SPRT）确定何时收集了足够数据，预先设定 I/II 类错误边界。(4) **护栏**：自动回滚触发——若测试变体的安全违规、错误率或延迟恶化超过阈值，自动把全部流量重定向到对照。(5) **日志**：给每个请求和响应打上变体 ID、模型版本和完整时间分解标签，便于事后分析。(6) **发布阶段**：影子模式（无用户影响）→ 1% → 10% → 50% → 100%。

### Q13.4 解释你会如何为一个预期 6 个月内用户增长 10× 的 LLM 服务系统做容量规划。

**答**：容量规划步骤：(1) **基线测量**：当前每秒查询数（QPS）、平均输入/输出 token 长度、p95 延迟。(2) **预测 QPS**：投影 10× QPS 增长，考虑季节性（峰/谷）。(3) **吞吐建模**：给定当前 GPU 数和每 GPU 吞吐，计算峰值时所需的 GPU 小时数。加 30–50% 余量应对突发。(4) **成本优化**：水平扩展前先穷尽垂直优化：能否用 4-bit 量化把每 GPU 吞吐翻倍？升级到 H100（内存带宽约 A100 的 2×）？为系统 prompt 启用前缀缓存？(5) **自动扩缩**：实现基于 Kubernetes 或云原生的自动扩缩，把 GPU 配给前置时间算进去（GPU 实例初始化需 2–10 分钟）。(6) **多区域**：规划地理分布以降低延迟、避免单区域容量约束。预算假设：每块 H100 按 $2/小时，满载时可服务约 100 万输出 token/小时。

### Q13.5 你会如何测量和改进模型 FLOP 利用率（MFU）？

**答**：**测量 MFU**：计算每次前向传播的 FLOP 数（对 `N` 参数的 Transformer，每 token 约 `6N`，乘以每秒 token 数），再除以峰值 GPU FLOP/s。用 NVIDIA Nsight Compute 测量「SM 吞吐」占峰值的比例。典型值：prefill 30–45% MFU（GEMM 受限），decode <10%（内存受限）。**改进 MFU**：对 prefill：(1) 用 FlashAttention-3 提升注意力内核利用率；(2) 剖析并融合 layernorm/residual 运算；(3) 大批量时跨多 GPU 用张量并行；(4) 确保批大小对齐 Tensor Core 分块大小（16 的倍数）。对 decode：MFU 天然很低，正确的指标是**内存带宽利用率**——目标 >80% 峰值 HBM 带宽。改进方法：(1) 增大批大小摊薄权重加载成本；(2) 量化权重减少每 token 加载字节数；(3) 用投机解码每步处理多个 token。
