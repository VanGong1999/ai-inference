# 第 10 章 · 长上下文与内存管理（Long-Context and Memory Management）

> Efficient LLM Inference — Interview Pocket Notes · 第 10 章

## 10.1 二次注意力问题

注意力在序列长度 `n` 上的 `O(n²)` 复杂度是长上下文 LLM 推理的核心障碍。对 `n = 1,000,000` token（1M 上下文，如 Gemini 1.5 Pro），天真的注意力矩阵需要 `1,000,000² × 2 bytes = 2 PB`——显然不可行。即使 `n = 128,000`（128K 上下文），注意力矩阵也有 32 GB。

现代长上下文方法从多个角度攻击这一问题。

## 10.2 长上下文的 FlashAttention

如第 7 章所述，FlashAttention 通过分块避免物化完整注意力矩阵。这**并不降低** `O(n²)` 的计算复杂度，但把 `O(n²)` 的 HBM 内存需求降到 `O(n)`，使注意力在当前硬件上计算 128K token 成为可行。

## 10.3 Ring Attention

**Ring Attention**（Liu et al., 2023）把长上下文注意力计算分布到环形排列的多设备上。每个设备持有序列的一段 QKV 张量，设备们沿环传递 KV 块，同时计算局部注意力。关键洞见是 online softmax 技巧允许「设备一次只看一个 KV 块」时仍能做正确的归一化。Ring Attention 把每设备内存从 `O(n²)` 降到 `O(n/p)`（`p` 为设备数），从而跨设备集群实现百万 token 上下文。

## 10.4 上下文压缩（Context Compression）

与其对所有上下文算完整注意力，上下文压缩技术选择性地总结或移除低信息量的 token：

- **LLMLingua**（Jiang et al., 2023）用一个小语言模型给每个 token 打分（给定其上下文的困惑度）；低困惑度（容易预测）的 token 被丢弃。在许多任务上可实现 4–20× 压缩比，性能退化 <5%。
- **AutoCompressor** 微调模型本身，把长上下文总结成固定数量的「摘要向量」，再用作压缩的 KV Cache。

## 10.5 作为线性注意力的状态空间模型

**Mamba**（Gu & Dao, 2023）及其后继是**状态空间模型（SSM, State Space Model）**，它们通过一个学到的循环状态而非注意力来处理序列：

```
h_t = A h_{t−1} + B x_t,   y_t = C h_t
```

在选择性 SSM（S6）中，`A`、`B`、`C` 都是输入相关的。这实现推理的 `O(n)` 时间和 `O(1)` 内存（隐藏状态 `h` 大小固定，与序列长度无关）。推理时 SSM 等价于 RNN：每个新 token 只需更新状态，没有 KV Cache。代价是：对需要精确回忆特定先前上下文的任务，SSM 的上下文内检索能力弱于注意力。

## 面试准备 · 模拟问答（Mock Q&A）

### Q10.1 Ring Attention 如何实现分布式长上下文推理？它的通信成本是多少？

**答**：Ring Attention 把序列分布到 `p` 个设备。设备 `i` 持有 query 块 `Q_i` 和 key-value 块 `(K_i, V_i)`。在 `p` 个通信步的每一步中，设备把它们的 KV 块传给环中的下一台设备，并接收上一台设备的 KV 块。在等待下一个 KV 块时（与计算重叠），每台设备计算其本地 `Q_i` 与当前 KV 块之间的部分注意力分数，累积 online softmax 统计量。`p` 步之后，每台设备都为其 query 块算出了正确的注意力输出。**通信成本**：每步传输 `n/p` 个 token 的 KV Cache（K 和 V 两个张量）。每层总通信：`n × d_head × n_heads × 2 × precision`，与总 KV 数据量相同——没有额外通信开销。通信与计算流水线化。

### Q10.2 对比 Mamba（SSM）与 Transformer 注意力用于长上下文推理。你何时用哪个？

**答**：**Transformer 注意力**：`O(n²)` 计算、`O(n)` KV Cache 内存。擅长需要精确回忆上下文任意位置具体细节的任务（如「文档第 3 页关于 X 说了什么？」）。用 FlashAttention 时，随上下文增长性能优雅退化。**Mamba**：`O(n)` 计算、`O(1)` 状态（固定大小循环状态）。对超长序列极高效——每个 token 计算量恒定，与总上下文长度无关。弱点：选择性 SSM 难以从远处上下文精确检索，在检索密集的基准（RULER、passkey retrieval）上不如注意力。**何时用 Mamba**：超长文档的流式推理、时间序列预测、模型需要跟踪演化状态而非检索特定事实的应用。**混合模型**（Jamba、Zamba、Mamba-2 + 注意力）结合二者——大部分处理用 SSM 层，检索用稀疏注意力层。

### Q10.3 LLMLingua 如何压缩 prompt？prompt 压缩的风险是什么？

**答**：LLMLingua 用一个小型代理 LLM 估计每个 token 在（可能已压缩的）上下文下的困惑度。低困惑度的 token 被视为可预测、因而是低信息量的，成为移除候选。算法：(1) **粗粒度**：决定保留哪些句子或短语；(2) **细粒度**：在保留的片段内，移除低困惑度 token；(3) 目标压缩比决定激进程度。**风险**：(1) 代理模型对「可预测性」的判定可能与目标模型不同，导致重要 token 被丢弃；(2) 移除 token 会改变后续所有 token 的位置上下文——用绝对位置编码的模型可能特别敏感；(3) 对检索密集的任务（精确的名字/数字查找），即使低困惑度 token 也可能至关重要；(4) 压缩不可逆——错误无法恢复。实用准则：生产部署前，在你的特定任务分布上验证 LLMLingua。

### Q10.4 解释 YaRN 与 NTK-aware scaling 在 RoPE 上下文扩展上的区别。

**答**：两者都试图把用 RoPE 在上下文长度 `L` 训练的模型扩展到更长的 `L′ > L`，而无需微调（或只需极少量微调）。**NTK-aware scaling**（bloc97, 2023）重缩放 RoPE 基频：不用基 `b = 10,000`，而用 `b′ = b · (L′/L)^{d/(d−2)}`。这把旋转更均匀地铺到扩展范围上，防止高频维度「绕圈」。但它对所有频率维度应用相同的缩放。**YaRN**（Peng et al., 2023）用更精细的方法：完全**不缩放**低频维度（它们已有很好的远距离覆盖），对中频应用 NTK 风格缩放，对高频做线性插值。这在保留短序列分布内行为的同时支持更长序列。YaRN 还应用注意力温度校正（把注意力分数乘 `√(1/t)`）以补偿注意力分布的变化。在扩展上下文长度上，YaRN 的困惑度和检索基准持续优于 NTK-aware scaling。

### Q10.5 什么是 RAG，它与长上下文推理有什么关系？何时选哪个？

**答**：**RAG（Retrieval-Augmented Generation，检索增强生成）**在查询时从向量数据库选择性地取回相关文档，只把最相关的段落插入 prompt。它用检索系统有效地替代了对超长上下文窗口的需求。**长上下文推理**则把所有潜在相关信息直接放进模型的上下文窗口。**选 RAG 当**：(1) 语料库极大（数百万文档）——远超任何可行的上下文窗口；(2) 检索精确——查询能清晰映射到具体文档；(3) 可接受检索索引带来的延迟；(4) 长上下文计算成本过高。**选长上下文当**：(1) 任务需要在文档的许多部分之间综合或比较（如对整本书的复杂推理）；(2) 检索有噪声——模型受益于访问完整上下文来区分相关与不相关；(3) 文档语料库足够小能装下（<1M token）。理想系统往往二者结合：先用 RAG 缩小候选集，再用长上下文对取回的段落推理。
