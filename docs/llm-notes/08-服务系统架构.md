# 第 8 章 · 服务系统架构（Serving Systems Architecture）

> Efficient LLM Inference — Interview Pocket Notes · 第 8 章

## 8.1 生产推理服务器的解剖

一个生产级 LLM 推理服务器是复杂的分布式系统，核心组件有：

- **前端 / API 网关（Frontend / API Gateway）**：接收 HTTP 请求，做鉴权、限流、入队。
- **调度器（Scheduler）**：服务系统的「大脑」。决定当前批次跑哪些请求，管理 GPU 显存和 SLO 约束。
- **执行引擎（Execution Engine）**：跑实际的 GPU 前向传播，管理 KV Cache 块。
- **分词器（Tokenizer）**：文本与 token ID 互转（通常在 CPU 上跑）。
- **采样器（Sampler）**：对 logits 应用 temperature、top-k、top-p 等采样逻辑。

## 8.2 批处理策略

### 8.2.1 静态批处理（Static Batching）

最简单的方式：收集固定数量的请求，把它们全部填充（pad）到最长序列的长度，处理这个填充后的批次。效率极低：填充浪费的计算和内存与长度方差成正比。

### 8.2.2 连续批处理（Continuous / Iteration-Level Batching）

由 Orca（Yu et al., 2022）首创，vLLM 和 TGI 实现。不是在请求级别批处理，而是在**迭代（decode 步）级别**批处理。每个 decode 步，调度器可以把新请求（已完成 prefill 的）加入运行中的批次，已完成的序列立即移除。这消除了静态批处理的「长尾」问题，让 GPU 利用率保持高位。

### 8.2.3 分块预填充（Chunked Prefill）

Sarathi-Serve（Agrawal et al., 2024）观察到单个长 prefill 请求会独占 GPU 数百毫秒，饿死 decode 阶段的请求（「prefill 抢占 / prefill piracy」）。分块预填充把 prefill 计算分成小块，与 decode 步交错，为所有类型的请求提供更可预测的延迟。

## 8.3 分离式 Prefill 与 Decode

prefill（算力受限）与 decode（内存受限）之间的根本张力，暗示它们应该跑在为各自优化过的不同硬件上。分离式服务（Splitwise、Mooncake）在物理上分离：

- **Prefill 节点**：最大化算力利用率（大批量、长 prompt），可用更便宜、更旧的算力优化 GPU。
- **Decode 节点**：最大化内存带宽，支持高并发，受益于每参数 HBM 带宽更高的新 GPU。

挑战在于 **KV Cache 迁移**：prefill 完成后，KV Cache 必须从 prefill 节点传输到 decode 节点（经 NVLink、InfiniBand 或 RDMA），带来额外延迟。像 Mooncake（来自 Kimi/Moonshot AI）这样的系统用二级存储上的分布式 KV Cache 池来彻底解耦这一点。

## 8.4 SLO 感知调度

生产系统必须遵守服务等级目标（SLO，Service Level Objectives）——通常表达为 p95 或 p99 的 TTFT 和 TPOT 目标。天真的 FIFO 调度器可能让短请求饿死在长请求后面。SLO 感知调度技术包括：

- **优先级队列**：更短/更高优先级的请求插队。
- **抢占（preemption）**：当一个长请求的 SLO 轨迹安全时暂停它，释放其 KV Cache 块，服务更高优先级的请求。
- **请求路由**：根据估计长度和服务器负载，把请求路由到不同的服务器池。
- **准入控制（admission control）**：系统过载时拒绝或排队请求，防止 SLO 违约。

## 面试准备 · 模拟问答（Mock Q&A）

### Q8.1 解释连续批处理。为什么它对 LLM 服务优于静态批处理？

**答**：静态批处理把长度相近的请求分组，填充较短的，处理整批直到所有请求完成。问题在于：一个 32 请求的批次里，只要有一个比其它长 10×，其余 31 个 GPU 就在空等那个请求，填充 token 浪费的算力是永久性的。**连续批处理**（Orca、vLLM）在迭代级别运作：每个 decode 步，调度器检查是否有运行中的请求已完成（发出 `<EOS>`），并立即用队列中新到的请求替换它们。不同长度的请求之间不做填充——每个请求只占它实际需要的 token。GPU 利用率持续保持高位，因为没有对「掉队者」的整批等待。实践中，根据 Orca 论文的基准，连续批处理在相似延迟下比静态批处理吞吐提升 5–23×。

### Q8.2 什么是「prefill 抢占」，分块预填充如何解决它？

**答**：prefill 抢占描述的是：一个 prompt 非常长的请求在其 prefill 阶段独占 GPU——可能长达数百毫秒——而批次中所有 decode 阶段的请求都在停滞。prefill 期间 GPU 在对大 token 矩阵做 GEMM；正在生成 token 的 decode 请求必须等待，导致它们的 TPOT（每输出 token 时间）飙升。**分块预填充**（Sarathi-Serve）把长 prompt 的 prefill 分成小块（如每块 512 token），并与 decode 步交错。这意味着一个 4096-token 的 prefill 在让出给 decode 批次之前只贡献 512 token 的计算，把 decode TPOT 退化降低 5–10×，而对总 prefill 时间只增加极少开销。

### Q8.3 描述 vLLM 的架构。它的关键创新是什么？局限在哪里？

**答**：vLLM（Virtual LLM）是高吞吐服务系统，围绕三大核心创新构建：(1) **PagedAttention**：非连续、基于块的 KV Cache 内存管理，消除碎片；(2) **连续批处理**：迭代级批处理，高 GPU 利用率；(3) **定制注意力内核**：用于分页注意力计算的 CUDA 内核。架构：请求到达 API server、被分词，然后由 **LLMEngine** 调度，它通过 **BlockManager** 管理 KV 块，在 GPU worker 上通过定制执行引擎执行。**局限**：(1) vLLM 当前的调度器不完全 SLO 感知——可能饿死短请求；(2) 小模型的张量并行通信开销可能显著；(3) Python 密集的调度层给极短请求增加延迟；(4) 基础 vLLM 不原生支持分离式 prefill/decode；(5) 非标准架构（MoE、非 Transformer 模型）需要定制插件开发。

### Q8.4 分离式 prefill/decode 服务如何工作？工程挑战是什么？

**答**：分离式服务把 prefill 计算路由到专用 prefill 节点、decode 计算路由到专用 decode 节点。请求到达路由器，被送到 prefill 节点跑 prompt 前向传播并产出 KV Cache，然后 KV Cache 经 RDMA/InfiniBand 传输到 decode 节点，decode 节点生成 token 直到完成。**工程挑战相当大**：(1) **KV Cache 传输延迟**：在 400 Gb/s InfiniBand 链路上传 10 GB KV Cache 要约 200 ms——往往比 prefill 本身还长。优化：逐层传输 KV 块，与 decode 流水线化；(2) **资源配比**：prefill 与 decode 节点的算力/内存比不同，任一池配置过多或过少都会损害整体吞吐；(3) **容错**：如果 decode 节点在生成中途挂掉，KV Cache 必须能恢复；(4) **路由复杂度**：路由器必须估计请求长度以最优均衡负载。

### Q8.5 你会用什么指标来评估和对比两个 LLM 服务系统？

**答**：我会评估：(1) **TTFT p50/p95/p99**：对交互式应用至关重要——首 token 多快出现；(2) **TPOT p50/p95**：流式流畅度——后续 token 多快到达；(3) **吞吐（tokens/s）**：给定硬件配置下的总系统产出；(4) **Goodput**：同时满足所有 SLO 目标（TTFT 和 TPOT）的请求占比；(5) **GPU 利用率（MFU）**：模型 FLOP 利用率——峰值 GPU FLOP/s 中被有效使用的比例；(6) **每百万 token 成本**：总 TCO 按输出归一化；(7) **可扩展性**：并发用户增加时性能如何变化；(8) **过载下的尾延迟行为**：系统是优雅退化还是灾难性崩坏。我会在真实的请求分布（长短 prompt 和输出混合）上跑基准，而不是合成的定长基准。
