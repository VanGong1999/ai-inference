# 第 11 章 · 边缘与端侧推理（Edge and On-Device Inference）

> Efficient LLM Inference — Interview Pocket Notes · 第 11 章

## 11.1 边缘推理的版图

在边缘设备——智能手机、笔记本电脑、嵌入式系统——上运行 LLM，对隐私、延迟和离线能力越来越重要。约束很苛刻：一台旗舰智能手机可能只有 8–16 GB 的统一内存（CPU 与 GPU 共享），功耗预算约 10 瓦。对比之下，一块 H100 GPU 有 80 GB 专用 HBM，功耗 700 瓦。

边缘推理工程，就是在这些约束下榨取尽可能多的智能。

## 11.2 边缘的内存约束与量化

一个 7B 模型在 FP16 下要 14 GB——超出大多数智能手机的内存。4-bit 量化（AWQ/GPTQ）把它降到 3.5 GB，使 7B 模型在高端手机上可行。8 GB RAM 的 Apple iPhone 16 Pro 可通过共享系统内存管理跑 4-bit 的 Llama 3 8B。

更激进的量化（2-bit、QuIP#）降到约 1.8 GB，使 7B 模型可在中端设备上运行，但有一些质量退化。

## 11.3 运行时框架

**llama.cpp**（Gerganov, 2023）是 LLaMA 及兼容模型的纯 C/C++ 实现，具备：

- 通过 AVX-512、NEON（ARM）和 WebAssembly 的 CPU 推理
- 到 Metal（Apple）、CUDA、Vulkan、OpenCL 的 GPU 卸载（部分或完整）
- 自定义 **k-quant** 格式（Q4_K_M、Q5_K_M 等），用分组量化实现质量-大小的帕累托效率
- 基于 mmap 的权重加载，极其省内存的注意力

**Apple MLX** 是 Apple 为 Apple Silicon 打造的本地 ML 框架，利用统一内存架构。MLX 能在 M3 Ultra（192 GB）的 Mac Studio 上以 4-bit 运行 70B 模型，达到约 **30 tokens/s**。

**ONNX Runtime** 提供跨 CPU、GPU 和不同厂商 NPU 的跨平台硬件加速推理。

## 11.4 面向效率的神经架构搜索（NAS）

**神经架构搜索（NAS, Neural Architecture Search）**自动化地为特定硬件约束设计最优模型架构。对边缘部署，NAS 能发现：

- 给定延迟预算下的最优层宽和层深
- 混合精度分配（不同层用不同位宽）
- 注意力头剪枝模式
- 块跳过或早退（early exit）策略

硬件感知 NAS（HAT、OFA）训练一个「超网（supernet）」，推理时无需重新训练即可从中提取不同大小的子网络。

## 面试准备 · 模拟问答（Mock Q&A）

### Q11.1 你被要求在一台 6 GB RAM 的智能手机上部署一个有竞争力的语言模型。你的方案是什么？

**答**：6 GB 可用 RAM 要与操作系统和其它应用共享，给模型大约留 4–4.5 GB。我的方案：(1) 从 3B 或 4B 模型（Llama 3.2 3B、Phi-3 Mini 3.8B、Gemma 2 2B）开始，4-bit 下只需 1.5–2 GB；(2) 用 llama.cpp 或 AWQ 的 **Q4_K_M** 量化——对小模型这是质量-大小的最佳平衡；(3) iOS 上用 **Metal GPU 卸载**（llama.cpp + Metal 后端）加速推理；(4) 实现 prompt 缓存，避免重复计算系统 prompt 的 KV Cache；(5) 若延迟关键，用更小的草稿（如 1B 模型）做投机解码；(6) 目标 10–20 tokens/s，这对聊天界面感觉是流畅的。若 3B 质量不够，考虑 7B 的 Q2_K（约 3.5 GB），接受一些质量退化。

### Q11.2 解释 Apple MLX，以及为什么它很适合 Apple Silicon 上的 LLM 推理。

**答**：MLX 是 Apple 为 Apple Silicon 打造的数组计算库，从设计上就考虑了统一内存架构。与把 CPU 和 GPU 当作需要显式数据拷贝的分离内存空间的 PyTorch 不同，MLX 在 CPU 和 GPU 都能访问的单一共享内存空间上运行，无需拷贝。对 LLM 推理，这是变革性的：模型权重一次载入系统内存，立即可被 GPU（Apple Silicon 的集成 GPU）访问，消除了 PCIe 瓶颈。在 192 GB 统一内存、800 GB/s 带宽的 M3 Ultra 上，4-bit 的 70B 模型（约 40 GB）轻松装下并留出 KV Cache 空间，达到约 30 tokens/s。MLX 还提供 Python 接口、JIT 编译、惰性求值，并通过 mlx-lm 包支持越来越多的模型。它是在消费级硬件上运行前沿规模模型的最实际路径。

### Q11.3 llama.cpp 中的 k-quant 系统是什么？它与标准均匀量化有何不同？

**答**：llama.cpp 实现了「k-quants」——一族混合精度的分块量化格式。与「每个权重独立量化到 k 位、配一个逐张量或逐通道的缩放」不同，k-quants 用层级方案：权重被分成块（通常 32 个权重），每块内部分权重以比其它更高的精度存储。例如 Q4_K_M 中：「K」后缀表示 super-block 量化方案，「M」表示质量档（small/medium/large）。每个 super-block 的 scale 和最小值以更高精度存储，而单个权重用 4-bit 编码。这优于均匀量化，因为：(1) 块级缩放适应当地权重分布，减小量化误差；(2) 重要权重（分布尾部附近的）获得更好的表示；(3) 在相同位预算下，产生的质量/大小比优于天真的 INT4。Q4_K_M 被广泛认为是 llama.cpp 最实用的 4-bit 格式。

### Q11.4 对比 llama.cpp 的 CPU 推理与 GPU 推理。你何时会更偏好 CPU 推理？

**答**：**GPU 推理**（Metal、CUDA、Vulkan）用设备的并行计算单元和高带宽内存获取最大吞吐——同一模型通常比 CPU 快 5–20×。**CPU 推理**用 AVX-512/NEON SIMD 指令、系统 RAM（远慢于 GPU HBM）和顺序处理。CPU 推理更慢，但有优势：(1) **无显存限制**：系统 RAM（桌面 64–512 GB）能容纳比任何 GPU 显存大得多的模型；(2) **散热**：CPU 在被动散热环境下能更持久地推理；(3) **可用性**：CPU 推理在任何无 GPU 的机器上都能跑。我偏好 CPU 当：(1) 模型对 GPU 显存来说太大；(2) 设备无 GPU 或只有很弱的集显；(3) 吞吐不关键、低速批处理可接受。部分 GPU 卸载（llama.cpp 的 `-ngl` 标志）让你把能装进显存的层卸载到 GPU、其余在 CPU 跑，兼顾两者。

### Q11.5 什么是硬件感知 NAS？OFA（Once-For-All）如何实现高效边缘部署？

**答**：**硬件感知 NAS** 搜索在「精度 vs 目标硬件指标（延迟、能耗、内存）」上帕累托最优的模型架构。它不产单一固定模型，而是产出一族具有不同精度-效率权衡、各自为特定硬件优化的模型。**Once-For-All（OFA）**（Han et al., 2020）训练单个大型「超网」，从中无需重训即可提取不同深度、宽度、核大小的子网络。OFA 用渐进收缩（progressive shrinking）：先训完整网络，再从完整网络采样更小的子网络渐进训练，并从完整网络做知识蒸馏。部署时，给定目标设备和延迟约束，用查找表或预测器估计子网络延迟，选预算内精度最高的子网络。对 LLM 推理，OFA 风格方法能产出尺寸相差 2–5× 的模型，全部来自一次训练。
