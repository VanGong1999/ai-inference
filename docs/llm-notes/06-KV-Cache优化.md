# 第 6 章 · KV Cache 优化（KV Cache Optimization）

> Efficient LLM Inference — Interview Pocket Notes · 第 6 章

## 6.1 KV Cache 内存危机

如第 3 章所示，单个长上下文请求的 KV Cache 就能吃掉几十 GB 显存。对于一个有数百并发请求的服务系统，天真地为每个请求预分配「最大长度」的 KV Cache，会浪费大部分已分配内存（因为实际请求长度不可预测），并严重限制批大小。这是 2023 年之前 LLM 服务领域悬而未决的核心问题。

## 6.2 PagedAttention：KV Cache 的虚拟内存

**PagedAttention**（Kwon et al., 2023）是 vLLM 的核心创新，它把操作系统的虚拟内存概念应用到 KV Cache 管理上。

PagedAttention 不为每个请求的 KV Cache 分配连续内存块，而是把 KV Cache 划分为固定大小的**块（block / page）**，每块 `B` 个 token。一张**块表（block table）**把每个请求的逻辑 KV Cache 位置映射到 GPU 显存中的物理块——块无需连续。

**PagedAttention 关键特性**

- **无预分配**：块随生成进行按需分配。
- **无内部碎片**：浪费的内存最多为每请求 `(B − 1)` 个 token。
- **写时复制（copy-on-write）**：共享同一前缀（如系统 prompt）的多个请求可以共享物理块，直到路径分叉。
- **灵活驱逐（eviction）**：一个请求的块可被换到 CPU 或磁盘，为别的请求腾空间。

PagedAttention 需要一个修改过的注意力内核，在注意力计算中收集非连续块——这是 vLLM 通过定制 CUDA 内核实现的一个不小的工程挑战。

## 6.3 前缀缓存（Prefix / Prompt Caching）

许多生产负载在成千上万个请求之间共享一个长的公共前缀——系统 prompt、一篇文档、或 few-shot 示例。不做缓存的话，每个请求都要从头重新计算这个共享前缀的 KV Cache。

**前缀缓存**（也叫 prompt caching，vLLM、SGLang 有实现，Anthropic/OpenAI 也作为功能提供）存储公共前缀的 KV Cache，跨请求复用。当前缀相对用户 prompt 很长时，这可以把 prefill 成本降低 **90%+**。

## 6.4 StreamingLLM：注意力汇（Attention Sink）现象

对于需要无限长上下文的应用（流式对话、长时运行的 agent），我们无法存储所有 token 的 KV Cache——它会无限增长。天真的滑动窗口注意力（只保留最近 `W` 个 token 的 KV Cache）会导致灾难性的性能退化。为什么？LLM 会发展出**「注意力汇（attention sinks）」**：序列最前面的几个 token（无论语义内容如何）在所有层都获得不成比例的高注意力分数。删掉它们会破坏模型的内部表示。

**StreamingLLM**（Xiao et al., 2023）保留一小块「汇」的初始 token（通常 4 个），再加上最近 token 的滑动窗口，从而在有界内存下实现无限长度的 LLM 推理：

```
保留的 KV = 汇 token ∪ 最近窗口
```

## 6.5 KV Cache 量化

KV Cache 可以独立于模型权重进行量化，因为它在每个注意力步只读一次，任何量化误差只影响当前 decode 步，而不会累积。**INT8 KV Cache 量化**现已成为 TensorRT-LLM、vLLM 等框架的标准做法，提供约 **2×** 的 KV 内存缩减。更激进的方案会用 INT4 甚至 FP8 对 KV Cache 量化，配合仔细的逐头或逐通道缩放。

## 面试准备 · 模拟问答（Mock Q&A）

### Q6.1 解释 PagedAttention。它与预分配连续 KV Cache 管理有何不同？

**答**：传统 KV Cache 管理为每个请求预分配一块按「最大可能序列长度」定大小的连续显存。这浪费巨大内存，因为大多数请求远短于最大长度。此外它还会造成内存碎片：一旦块被释放，留下的空隙可能太小而放不下新块，导致外部碎片。**PagedAttention** 把 KV Cache 内存分成固定大小的块（每块约 16 个 token），并为每个请求维护一张块表，把逻辑位置映射到物理块。块随新 token 生成按需分配，请求一完成就立即释放。这消除了预分配浪费、把碎片降到每请求最多 `B − 1` 个 token，并支持跨请求共享公共前缀块的写时复制。结果是相同显存下批大小通常提高 2–4×。

### Q6.2 前缀缓存如何工作？哪类应用受益最大？

**答**：前缀缓存存储某个 token 前缀（如系统 prompt）已算好的 KV Cache，供共享该前缀的后续请求复用。系统维护一张从「前缀 token 序列（或内容哈希）」到「物理 KV Cache 块」的哈希表。新请求到来时，服务系统检查它的前导 token 位置是否命中缓存前缀；若命中，这些 token 的 prefill 步被完全跳过。**受益最大的应用**：(1) **固定系统 prompt 的 API 产品**：比如一个 2000-token 系统 prompt 的客服机器人——每条用户消息都受益于缓存前缀；(2) **多轮对话**：后续轮次可复用之前所有轮的 KV；(3) **批量文档处理**：比如对同一文档的 1000 个问题共享该文档的 KV Cache。实际 prefill 阶段延迟可降低 50–90%。

### Q6.3 什么是注意力汇现象？为什么天真的滑动窗口注意力对 StreamingLLM 会失效？

**答**：当 LLM 在定长序列上训练时，它们学会把大量注意力导向每个序列最前面的几个 token——这些被称为「注意力汇」。前几个 token 充当「聚合器」，吸收 softmax 归一化所需的超额注意力概率质量。这些汇 token 语义上并不重要，它们只是变成了结构性锚点。天真的滑动窗口注意力为维持固定大小 KV Cache 而丢弃最老的 token，当窗口滑过开头时会无意中移除这些汇 token。没有汇之后，注意力归一化就崩了：剩余 token 上的 softmax 分数变得与训练分布大相径庭，输出灾难性退化。StreamingLLM 通过始终在 KV Cache 中保留前 4 个初始汇 token（连同最近窗口）来修复这一点，恢复正常的注意力行为。

### Q6.4 为一个服务「长度差异极大」请求的系统，你会如何设计 KV Cache 驱逐策略？

**答**：我会实现一个基于优先级、结合多种信号的驱逐策略：(1) **最近性（LRU）**：优先驱逐最久未访问的块；(2) **序列完成概率**：用请求当前位置和典型长度分布估计它离完成还有多近——优先驱逐可能很快完成的请求；(3) **块可共享性**：保护被多个请求共享的块（前缀缓存块），因为它们摊薄价值高；(4) **驱逐成本**：优先驱逐能廉价重算 KV Cache 的请求（短 prompt），而不是长且昂贵 prefill 的请求。我还会在彻底驱逐之前，先做「块交换到 CPU DRAM」作为第二层（CPU 内存充裕）。vLLM 的抢占机制是实际例子：显存压力大时暂停并重新调度请求。

### Q6.5 解释 KV Cache 量化。KV Cache 能比模型权重量化得更激进吗？为什么？

**答**：KV Cache 量化把 key 和 value（注意力缓存）以降低的精度（INT8、INT4 或 FP8）存储，而非 FP16。**支持更激进量化的理由**：(1) KV Cache 值每个注意力步只读一次，误差不跨步累积（每个 decode 步从缓存重新读取）；(2) 注意力运算本身有归一化（softmax），对 key 量化误差有一定鲁棒性；(3) KV Cache 相比权重矩阵在头和层之间有更多冗余。**但也有反方论据**：激活（KV Cache 正是从激活派生而来）表现出与激活量化类似的离群值现象，比权重更难量化。实践中，INT8 KV Cache 已很成熟、质量损失极小；INT4 KV Cache 配合逐头或逐 token 缩放可行，但需要仔细实现。
