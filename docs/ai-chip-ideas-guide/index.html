First principles guide

Start with GPU inference. Then imagine better chips.

Most people first encounter AI infrastructure through GPU inference. This guide starts there, explains the important hardware terms in plain English, then turns the bottlenecks into startup ideas.

Start from GPUs Explain the terms
Step 1

What everyone is doing today.

Most serious LLM inference today runs on GPUs. GPUs work very well, but they also carry assumptions from graphics, CUDA, expensive memory, and host-device systems. That creates room for new ideas.

1. Request

A user sends a prompt. The system turns text into tokens.

2. GPU memory

The model weights and KV cache sit in expensive high-bandwidth memory.

3. Matrix math

Most work is matrix multiplication inside attention and feed-forward layers.

4. Scheduling

Kernels, batches, routing, and queues decide whether the GPU stays busy.

5. Cost

The business metric is not just speed. It is useful tokens per dollar.

Simple framing

A GPU is excellent at many kinds of parallel work. But LLM inference is a narrower job: move model data, do matrix multiplication, remember past tokens, and generate new tokens. If we understand that narrower job, we can ask whether a different hardware-software stack would be cheaper or easier to program.

Step 2

The basics before the big ideas.

Each term below appears because it is already part of current GPU inference, or because it attacks a cost in that current path. The goal is not vocabulary for its own sake: it is to see where the money, latency, and complexity go.

basic idea

What is a systolic array?

A systolic array is a grid of tiny multiply-add units. Numbers flow through the grid in a regular rhythm, so the chip can do matrix multiplication with very little wasted movement.

  • LLMs spend most of their math inside matrix multiplication.
  • Modern NVIDIA GPUs already contain this kind of matrix engine inside Tensor Cores, and current LLM inference uses them constantly.
  • TPUs call similar engines Matrix Multiply Units.
  • We mention systolic arrays because an expensive GPU is only productive when these matrix engines are fed, sized, and scheduled well.
basic idea

What is HBM, SRAM, and SSD?

They are different places to store data. The closer and faster the memory is, the more expensive it is. Inference cost often comes from deciding which bytes must be close to the matrix engine and which bytes can live farther away.

  • SRAM: tiny, very fast memory on the chip.
  • HBM: expensive high-bandwidth memory next to the GPU or accelerator.
  • SSD: much cheaper storage, but slower than HBM.
  • We mention memory tiers because many AI chip ideas are not about more math; they are about keeping hot data close and cold data cheap.
basic idea

What is a KV cache?

When an LLM reads or generates tokens, it stores key and value vectors from previous tokens so it does not recompute everything from scratch. That storage is called the KV cache.

  • K means key; V means value.
  • Current GPU inference usually keeps active KV cache in GPU HBM.
  • Long conversations and long documents create large KV caches.
  • We mention KV cache because long-context inference often becomes a memory-management problem before it becomes a raw-compute problem.
basic idea

What is DMA?

DMA means direct memory access. Instead of a CPU manually moving every small piece of data, a DMA engine copies blocks of data between memory locations in the background.

  • Think of it as a data conveyor belt.
  • It can move data between SRAM, HBM, network, or SSD.
  • It can overlap movement with computation, so the matrix engine does not wait.
  • We mention DMA because many proposed improvements are really about better conveyor belts, including compression while data moves.
Step 3

Where GPU inference gets expensive.

These bottlenecks are the bridge from "we use GPUs" to "maybe there are new chip, compiler, runtime, and observability companies to build."

bottleneck

Arrays can sit idle.

During decode, the model often generates one token at a time. That can make the matrix engines underutilized unless batching, GQA, speculative decoding, or other scheduling tricks help.

bottleneck

HBM is costly.

Model weights and KV cache consume expensive memory. Long context makes this worse, especially if old context sits in HBM even when rarely needed.

bottleneck

GPU software is powerful but complex.

CUDA, kernels, warps, and scheduling are mature, but they also create overheads. A CPU-like accelerator could be easier to program if the compiler stack is excellent.

What everyone does vs what we might do.

The key is to avoid treating these as random architecture terms. Each one is a response to a current GPU inference pain.

Plain English dictionary

Terminology without the mystery.

Use this section whenever a term feels unfamiliar. Each definition also explains why the term matters for current GPU inference and why it appears in the product ideas.

GPU inference

Running a trained model on GPUs to answer user requests. No training is happening; the model is serving outputs.

Why it matters: this is the baseline. Every idea here asks what GPUs already do well, then looks for places where serving tokens is still expensive.

Systolic array

A grid of multiply-add units that performs matrix multiplication by flowing numbers through the grid in a steady pattern.

Why it matters: this is already inside current NVIDIA GPUs as part of Tensor Cores, and current LLM inference relies on it. We mention it because keeping this engine busy is the central hardware problem.

Tensor Core

NVIDIA's name for the GPU units that accelerate neural-network matrix operations. Conceptually, this is where the systolic-array style matrix engine lives.

Why it matters: when a GPU is fast at LLM inference, Tensor Cores are doing much of the useful math. Any competing chip must explain how it feeds matrix engines as well or better.

Matrix multiplication

The core operation that combines rows and columns of numbers. Transformers use it in attention layers and feed-forward layers.

Why it matters: LLM inference is expensive largely because it performs enormous amounts of matrix multiplication. That is why matrix engines dominate the hardware discussion.

HBM

High Bandwidth Memory. Very fast memory packaged near the accelerator, but expensive per GB.

Why it matters: current GPU inference depends on HBM for model weights, activations, and active KV cache. Reducing HBM pressure can improve tokens per dollar.

SRAM

Small, very fast memory on the chip. It is much closer to compute than HBM but limited in size.

Why it matters: kernels load tiles into SRAM-like fast memory so Tensor Cores can reuse data instead of repeatedly going back to HBM.

SSD

Cheap large storage. Slower than HBM, but useful for data that is not needed every microsecond.

Why it matters: SSD appears in these ideas because older context or cold KV-cache data might move out of expensive HBM if the software can retrieve it intelligently.

KV cache

Stored key and value vectors from previous tokens. It lets the model refer back to prior context during generation.

Why it matters: long conversations and long documents create large KV caches in GPU memory. That is why memory tiering, compression, and sparse attention matter.

DMA

Direct Memory Access. A hardware copy engine that moves data between memory regions without a CPU doing every copy manually.

Why it matters: inference performance depends on moving the next tile of data while the current tile is computing. DMA is the conveyor belt that can keep compute fed.

DMA compressor

A DMA engine with compression and decompression built in, so less data travels through memory or network links.

Why it matters: if weights, activations, or KV cache compress while moving, the same HBM and network bandwidth can serve more useful tokens.

Prefill

The model reading the prompt or document before generating. Many input tokens can be processed together.

Why it matters: prefill usually uses Tensor Cores efficiently because many known tokens can be batched into large matrix multiplications.

Decode

The model generating output tokens. It often happens one token at a time, which can be harder to utilize efficiently.

Why it matters: decode is where latency, KV-cache reads, and low matrix-engine utilization often appear. Many serving ideas are decode ideas.

GQA

Grouped-query attention. A transformer attention design that shares some key/value work across query heads.

Why it matters: GQA is used because decode can be memory hungry. It reduces KV-cache traffic, which helps current GPU inference and future accelerators.

Speculative decoding

A serving trick where a smaller or cheaper process guesses future tokens, and the main model verifies them.

Why it matters: it can turn one-token-at-a-time decode into larger chunks of work, giving the matrix engines more useful work per step.

CUDA, kernels, and warps

CUDA is NVIDIA's GPU programming platform. A kernel is a GPU function launch. Warps are groups of GPU threads scheduled together.

Why it matters: this is the mature software model behind current GPU inference. New AI CPU ideas matter only if they can make programming easier without losing performance.

Op fusion

Combining multiple model operations into one kernel or pipeline so intermediate results stay close to compute.

Why it matters: fusion reduces trips to HBM. It is one reason compilers and runtimes can change the economics without changing the model.

Software pipelining

Scheduling load, compute, and store work so different parts of the chip are busy at the same time.

Why it matters: if the matrix engine waits for memory, money is being wasted. Pipelining is how software hides movement latency.

MoE

Mixture of Experts. A model design where each token uses only a subset of specialized expert networks.

Why it matters: MoE can reduce compute per token, but it creates routing and networking problems when experts are spread across chips.

Torus network

A layout where chips connect to nearby chips in a ring or grid with wraparound links. It can be cheaper than full routing for some AI communication.

Why it matters: large models often run across many chips. The network decides how expensive all-reduce, routing, and model parallelism become.

AI CPU

A CPU-like accelerator with large caches and matrix engines attached to programmable cores.

Why it matters: the proposal is not to remove matrix engines. It is to keep the LLM math engine, but surround it with a simpler, more CPU-like programming model.
Step 5

Startup ideas, now that the basics are clear.

Each product idea attacks one specific bottleneck. For each one, ask: who pays, what is the first demo, and what metric improves?

Idea 01hardware

Inference-first AI CPU

A CPU-like accelerator with cores for programmability, systolic arrays for matrix math, and a cache-first memory design.

Why: GPUs are powerful but not the only possible shape.
Demo: one model running cheaply.
Idea 02compiler

Compiler backend studio

Help new accelerator teams convert PyTorch/JAX/XLA graphs into efficient kernels for their hardware.

Why: hardware fails without software.
Demo: one fast attention kernel.
Idea 03memory

HBM minimization planner

Analyze a serving workload and recommend quantization, KV policy, sharding, and storage tiers to reduce HBM use.

Why: HBM is expensive.
Demo: cost report from traces.
Idea 04KV cache

SSD-backed long memory

Keep recent KV in HBM and move older context into cheaper storage, using retrieval so quality stays high.

Why: long context is memory-heavy.
Demo: long chat benchmark.
Idea 05data movement

DMA compression engine

Compress and decompress data as it moves through memory or network links, reducing bandwidth pressure.

Why: data movement is costly.
Demo: FPGA or simulator.
Idea 06numerics

Sparsity and low-bit toolkit

Recipes that make models run with fewer bits and structured zeros while preserving output quality.

Why: fewer bits means less memory traffic.
Demo: open model conversion.
Idea 07serving

Prefill/decode scheduler

Balance reading work and generation work so compute and memory bandwidth are both used well.

Why: prefill and decode stress different resources.
Demo: vLLM plugin.
Idea 08networking

Torus-aware cluster kit

Use short local chip-to-chip links for common AI communication patterns, reducing dependence on expensive routers.

Why: networking cost matters at scale.
Demo: 4-chip topology simulator.
Idea 09kernels

Tiled software pipeline library

Let kernel authors declare load, compute, store, and network stages without writing unreadable hand-pipelined code.

Why: fast kernels are hard to write.
Demo: fused matmul example.
Idea 10observability

Tokens-per-dollar dashboard

Show which prompts, models, tenants, and serving choices are increasing cost or hurting latency.

Why: teams need economic visibility.
Demo: trace dashboard.
Idea 11MoE

MoE utilization optimizer

Place experts, route tokens, and queue low-priority work so sparse expert models do not waste accelerators.

Why: expert load is uneven.
Demo: routing simulator.
Idea 12planning

AI chip co-design search

Explore tradeoffs across arrays, memory, networking, compilers, model shapes, and customer workloads.

Why: local optimizations mislead.
Demo: design-space explorer.
Y Combinator questions

Questions a serious startup application should answer.

These questions turn the technical ideas into company-shaped thinking. The answers should be short, concrete, and grounded in one measurable inference pain.

company

What are you building?

Say the product in one plain sentence. Example: "We reduce LLM serving cost by moving cold KV cache out of HBM while preserving answer quality."

customer

Who has the problem?

Name the first buyer precisely: inference platform teams, model labs, cloud providers, GPU cluster operators, or companies with long-context workloads.

pain

What is painful today?

Connect the pain to the current GPU inference path: HBM cost, decode latency, idle Tensor Cores, kernel complexity, KV-cache growth, or network bottlenecks.

insight

What do you know that others miss?

State the technical bet. For example: "The bottleneck is not only FLOPs; it is byte movement between HBM, SRAM, and the matrix engine."

demo

What is the smallest impressive demo?

Pick one narrow proof: a simulator, a vLLM plugin, one compressed KV benchmark, one faster fused kernel, or one FPGA DMA-compression prototype.

metric

What number gets better?

Use a metric buyers understand: tokens per dollar, output-token latency, HBM GB per request, Tensor Core utilization, watts per token, or network bytes per token.

competition

What do customers use instead?

The real competitor is often "buy more GPUs" or "accept lower utilization." Explain why your approach is cheaper, easier, or more available.

timing

Why now?

Use changes in the world: long context, reasoning models, MoE, inference spending, HBM scarcity, new compiler stacks, or demand for non-GPU capacity.

risk

What is the hard technical risk?

Be direct. Examples: sparse attention quality, compression overhead, compiler reliability, customer model changes, hardware validation, or multi-chip scheduling.

traction

How do you know anyone wants it?

Show traces, benchmarks, design partners, letters of intent, paid pilots, or a workload where the current GPU path is visibly wasteful.

team

Why this team?

Point to things already built: kernels, compilers, serving systems, hardware prototypes, infra used by real users, or unusually strong technical execution.

scope

What is the first wedge?

Avoid claiming the whole chip market first. Start with one painful use case, one model family, one serving stack, or one hardware primitive.

A good answer pattern

Start from the current GPU inference workflow, identify one concrete bottleneck, explain the technical reason it exists, show the smallest proof that your approach improves it, and name the buyer who would care.
