为什么内存和计算都很重要

两种资源，一个瓶颈

在推理（自回归生成）过程中，每个新 token 都需要 两样东西：

1
内存，用于存储过去的上下文（KV 缓存或循环状态）。它随着每个 token 的生成而增长，并决定了你可以同时服务多少个序列。
2
计算，用于将新 token 与所有过去的上下文进行处理。这决定了每个 token 生成需要多长时间，以及延迟是否会在长序列下退化。

在短序列下，两者都不是问题。在长序列（100K+ token）下，两者都成为瓶颈。不同的技术优化不同的维度。有些减少内存，有些减少计算，有些两者都减少。

SSM 无法完全弥合的质量差距。 Mamba 和线性注意力实现了恒定的内存和计算 — 但注意力进行 精确的 token 到 token 查找的能力（例如，"列表中的第 3 项是什么？"）是损失性状态压缩从根本上难以做到的。这就是为什么最好的生产级模型（Jamba、DeepSeek）使用 混合架构：少数几个注意力层用于精确检索 + 大量 SSM/线性层用于高效的长程上下文。

SSM 的短板在哪里

上下文学习（In-Context Learning）

Transformer 可以从提示中的示例学习新任务。SSM 在这里很吃力 — 固定大小的状态无法像对原始 token 的注意力那样存储任意的输入-输出映射。

精确检索（Exact Retrieval）

"复制第 5 个词"或"电话号码是多少？"需要精确查找。注意力可以轻松做到这一点。SSM 将过去的 token 压缩成固定状态 — 单个 token 可能无法恢复。

多跳推理（Multi-hop Reasoning）

"A 是 B，B 是 C，因此 A 是 C"需要同时持有多个事实并将它们组合起来。SSM 状态的有损压缩使得链式推理比使用完整注意力更难。

硬件生态（Hardware Ecosystem）

Transformer 拥有多年的 GPU 内核优化（FlashAttention、PagedAttention 等）。SSM 内核更新、更不成熟，意味着理论上的 FLOPs 优势并不总能转化为实际的墙钟加速。

内存 — KV 缓存问题

1.1 — KV 缓存详解

在解码过程中，每个新 token 的查询（query）必须关注 所有过去的键（key）和值（value）。每一步都重新计算它们会很浪费，因此我们 缓存每个先前 token 的 K 和 V 投影。

KV 缓存随序列长度 线性增长。对于每一层：

计算 — FLOPs 问题

2.1 — 为什么 FLOPs 对推理很重要

在解码过程中，生成每个新 token 都需要对 所有过去的键计算注意力分数。每个 token 的注意力解码开销为：

每个 token 的 FLOPs = 2 × N × d   （与 N 个键做点积 + 对 N 个值做加权求和）

在 N=100K、d=2048 时，每个新 token 仅注意力就花费 约 410M FLOPs。而且每生成一个 token 都会让它变得 更糟 — 因为 N 在不断增长。

2.6 — Mamba（选择性 SSM）— 每个 token O(E·n + E·d)

与 S4 相同的递推，但 B、C 和 Δ 是 依赖于输入的。模型现在可以根据内容选择性地记住或遗忘。

训练时：无法使用 FFT（参数随每一步变化）→ 使用并行扫描 O(N log N)。权衡：对过去进行有损压缩，但选择性有助于保留重要信息。

2.8 — 计算对推理延迟真的重要吗？

重要 — 但真实情况更加微妙。

在 预填充（prefill）阶段，计算在所有 token 上并行进行。在 解码（decode）阶段，计算是串行的：一次一个 token，每个都必须完成后下一个才能开始。因此每个 token 的解码延迟与每个 token 的 FLOPs 成正比。

但这里有一个关键洞见。在 N=100K、使用完整注意力时：

计算时间

~4 μs

410M FLOPs，在 100 TFLOPS 下

内存读取时间

~390 μs

781 MB KV 缓存，在 2 TB/s 下

内存读取比计算耗时 长约 100×。解码从根本上说是 内存带宽受限（memory-bound），而不是算力受限。

关键洞见： 解码是内存带宽受限，而不是算力受限。这就是为什么 MQA/GQA（减少内存读取）比单纯减少 FLOPs 更能加速推理。减小 KV 缓存大小意味着从高带宽内存（HBM）读取更少的字节，直接降低每个 token 的延迟。

话虽如此，对于非常长的序列，两者都很重要。而对于吞吐量受限的场景（许多并发用户），内存容量决定了你可以把多少请求批处理在一起。

DeepSeek-V2 的洞见。 尽管拥有 236B 参数，DeepSeek-V2 的 MLA 将每个 token 的 KV 表示压缩成一个 512 维的向量（而 Llama 使用 GQA 时为 2048 维）。这是 4× 的缩减 — 使一个 236B 模型的 KV 缓存比一个 70B 模型更小。MLA 通过学习键和值的低秩压缩，然后在解码过程中即时重建完整的注意力头来实现这一点。

关键要点：内存

在 100K token 时，纯 MHA 模型变得不切实际。GQA、MLA 和滑动窗口让长上下文变得可行。Mamba/混合架构则让它变得 轻而易举。

关键要点：计算

完整注意力的 O(Nd) 解码开销意味着在 N=100K 时约 410M FLOPs/token。滑动窗口将其封顶在约 16.8M。SSM/Mamba：约 2.7M — 比完整注意力 便宜 150×。

内存和计算是同一枚硬币的两面。 最好的推理系统两者都优化 — 用 GQA 缩小 KV 缓存，用滑动窗口封顶计算，并且越来越多地使用混合架构，将少数几个注意力层（用于精确回忆）与 Mamba 层（用于高效的长程上下文）结合起来。DeepSeek-V2 的 MLA 表明，巧妙的压缩可以让你以极小的内存代价获得接近 MHA 的质量。
