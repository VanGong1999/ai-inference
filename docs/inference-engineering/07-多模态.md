# 第 6 章 · 多模态（Modalities）

> Inference Engineering — Philip Kiely · Chapter 6

模型的**模态（modality）**描述它接受什么类型的输入、创造什么类型的输出。第 1 到 5 章聚焦 LLM 的推理工程——LLM 以文本为输入、产生文本输出。本章把讨论扩展到更多模态。

生成式 AI 模型提供丰富的模态阵列，包括：

| 输入 | 输出 | 类别 |
|---|---|---|
| 文本和图像/视频 | 文本 | 视觉语言 |
| 文本或图像/视频 | 向量 | 嵌入 |
| 音频（语音） | 文本 | 转写 |
| 文本 | 音频（语音） | 语音合成 |
| 文本 | 音频（音乐） | 音乐生成 |
| 音频（语音） | 音频（语音） | 语音到语音 |
| 文本和/或图像 | 3D 模型 | 生成式 CAD |
| 文本和/或图像 | 图像/视频 | 图像/视频生成 |
| 图像/视频 | 文本 | 字幕 |
| 图像/视频 | 掩码 | 分割 |
| 文本和图像 | 图像 | 图像编辑 |

幸运的是，虽然模态很多，生成式 AI 模型只有两大类原型（如第 2 章所述）：

- **自回归 token 生成**：从 token 化序列出发，预测最可能的下一个 token。
- **迭代去噪**：从随机噪声出发，向最可能的输出精炼。

LLM 是最著名的自回归 transformer token 生成模型，但远不是唯一。视觉语言模型、文本和多媒体嵌入模型、自动语音识别（ASR）模型、文本转语音（TTS）模型，以及许多其它模型都依赖相似架构。

用于 LLM 的许多推理引擎和技术，也适用于这些相关模态。

图像和视频生成模型则依赖迭代去噪，尽管越来越多混合扩散 transformer 模型正成为质量前沿。虽然从内核选择到参数调优的许多哲学也适用于图像模型优化，细节却大不相同。

对每个新模态，你还需要调整思考和测量延迟、吞吐、质量的方式。例如，TTS 模型输出的单个音频 token 并不特别有用；与其测 TTFT，不如测「到第一个词的时间」或「到第一句话的时间」。

本章讨论 LLM 之外六种常见模态的推理工程，特别关注每种模态的不同考量。

## 6.1 视觉语言模型（Vision Language Models）

视觉语言模型（VLM）接受一张或多张图像或视频，连同文本 prompt，生成文本响应。

> **图 6.1**：VLM 给 LLM 增加图像和视频理解。

一个视觉语言模型通常由两个模块组成：

- **LLM**：一个标准大语言模型。
- **视觉编码器（Vision encoder）**：一个小模型，接受原始图像和视频，把它们转换成图像 token。

语言模型比视觉编码器大得多。例如，在 Mistral Large 3 中，视觉编码器只有 20 亿参数，而 LLM 有 6730 亿参数。

虽然视觉编码器按参数量很小，它对推理却至关重要。VLM 的视觉编码器使用多样的架构和实现，所以视觉语言模型的运行时支持稍显碎片化。这种碎片化提高了 vLLM 和 SGLang 服务视觉语言模型的重要性。

经验法则：给 VLM 发一张高分辨率输入图像，会给输入序列增加约一千个视觉 token。虽然从很高层面看图像 token 与普通 token 相似，它们累加得很快。

跨 VLM，推理优化的主要挑战是处理更长的输入序列和更大的 KV Cache。这在推理两个阶段都增加麻烦：

- **Prefill**：图像被分块、嵌入、分词，作为输入序列的一部分送入 prefill。
- **Decode**：机制相同、上下文更长，有些模型为图像 token 增加注意力变体。

上一章的每种技术都可用于应对这一挑战：

- **量化**：KV Cache 量化降低长序列的内存带宽和存储开销。
- **投机**：VLM 的 decode 与 LLM 一致，可用投机（尤其 EAGLE）加速。
- **前缀缓存**：在多轮聊天和重复查询中复用图像的 KV Cache。
- **并行**：用张量并行快速推理，同时为大模型和长上下文访问更多 VRAM。
- **分离式服务**：把 prefill 移到专门、独立扩缩的 worker 上处理长序列。

除这些技术外，VLM 引入一个新的质量-速度权衡：**下采样（downsampling）**。图像和视频可以以各种分辨率转换成视觉 token。高分辨率表示比低分辨率图像多约四倍的 token，但提供更详细信息。单图像输入通常不需要下采样，但传入多张图像或视频片段时可能需要。

### 6.1.1 视觉语言模型的视频处理

视频不只是帧的加总。视频可能包含音频（尽管许多 VLM 无法处理音频，音频必须单独转写并加进 prompt），而且视频的帧表达了物体在空间中的运动，这在静态图像中会丢失。

VLM 在视频片段上训练以理解时间维度。高质量推理需要在单次模型调用中处理整个视频片段。

一秒电影级视频包含 24 帧。每帧是一张图像。如果一张高清输入图像约需 1,000 token 表示，那么一个四秒视频片段会产生近 100,000 token 的输入序列。

现实中，视频输入不会生成这么长的输入序列——下采样实际上是必须的。

降低分辨率和帧率，使在单次推理请求中评估整个片段成为可能，尽管视频理解模型仍只能接受很短的片段。

视频被分词和编码后，推理就类似处理图像，只是上下文长得多。对这些数万 token 的输入序列，前缀缓存、KV Cache 卸载和优化的注意力实现更为重要。

### 6.1.2 全模态模型（Omni-Modal Models）

视觉语言模型是「omni」模型趋势的重要部分——omni 模型接受多种输入、产生多种输出。Omni 模型有优缺点：它们混合模态提供独特能力，但更小的专用模型在特定领域内往往更快更准。

例如，许多 VLM 在图像输入处理中训练了文本识别能力。然而，这些能力落后于专用光学字符识别（OCR）模型——后者通常只有其几分之一大小。

对 VLM 跑生产推理，常常涉及编排多个模型和预处理步骤的流水线。你可能有单独的预处理器：从 PDF 提取数据、通过 OCR 读图像文本、或从视频转写音频。

流水线中每个组件都必须单独为速度优化，并独立扩缩以避免瓶颈。

## 6.2 嵌入模型（Embedding Models）

嵌入模型把变长的文本块——或图像等其它模态的输入——转换成固定长度的向量表示，捕获输入的语义。

> **图 6.2**：嵌入模型把非结构化输入数据转换成编码语义的向量。

通过把内容编码到这个共享的语义向量空间，你可以用简单数学比较条目之间的距离。嵌入模型（连同向量数据库）用于构建 agent 记忆、RAG、搜索和推荐系统。

为支持这些用例，嵌入模型推理负载有两种不同流量画像：

- **高吞吐回填（backfills）**：批量操作，如索引数百万文档、更新产品目录，甚至为 LLM 预训练准备数据。
- **低延迟查找（lookups）**：面向用户的单个搜索、检索或推荐查询，每一毫秒都影响用户体验。

嵌入模型的推理工程，从澄清你需要服务哪种画像开始。如果两种都要做、且流量足以证明成本，最好为每种使用类型建独立系统。

### 6.2.1 嵌入模型架构

Hugging Face 上有数万个嵌入模型，但它们都用两种基于 transformer 的架构之一：

- **BERT 风格模型**：仅编码器神经网络，通常 <1B 参数，最初为掩码 token 预测而建。
- **基于 LLM 的模型**：现代语言模型，通常 ≤8B 参数，被改造来生成嵌入。

今天，基于 LLM 的嵌入模型提供强得多的能力，尽管 BERT 风格模型仍用于分类等简单延迟敏感任务。

嵌入模型在**嵌入维度（embedding dimensionality）**——即其输出向量的大小——上引入自己的速度/质量权衡。嵌入向量包含几百到几千个值，更长的向量编码更多信息。

现代嵌入模型用 **Matryoshka 表示**解锁嵌入维度与质量之间的动态权衡，同时在更短向量上保留更多信息。维度不实质影响推理时间，但影响系统内的存储、检索和相似度计算时间。

大多数情况下，一个嵌入模型的向量不能与另一个嵌入模型的向量有意义地比较，即便长度相同，因为它们把输入编码进不同的语义空间。

### 6.2.2 嵌入模型推理

对 Qwen 3 Embed 8B 等有 LLM 骨干的嵌入模型，推理优化与其它高量、低延迟的小 LLM 部署共享常用工具和技术。

文本嵌入模型有多种运行时：vLLM、SGLang、Infinity、TEI（Hugging Face 的 Text Embedding Inference）。但最佳性能来自把 TensorRT-LLM 改造来运行这些模型。

> **图 6.3**：高性能嵌入推理流水线，在优化推理引擎之前增加并行分词和批管理。

TensorRT-LLM 带来优化的 XQA 内核用于快速注意力，以及内核融合技术减少内存访问开销。对支持的模型，TensorRT-LLM 是延迟和吞吐都最强的推理引擎。

进一步收益来自量化。虽然小模型更可能因量化损失质量，嵌入模型权重的 FP8 量化在最小质量损失下改善性能。

检查量化后嵌入模型质量的最简单方式，是把相同输入分别跑原始和量化模型，然后检查输出向量的余弦相似度。100% 的余弦相似度意味着向量相同；你要看到至少 99% 的相似度才对量化有信心。

由于嵌入模型并行处理 token，前缀缓存和分离式服务是不相关的优化。且鉴于这些模型尺寸小，跨多 GPU 并行也不有效。相反，高流量部署应水平扩展，每块 GPU 作为自己的副本。

在嵌入模型的高流量部署中，批处理和排队对性能很重要。嵌入模型提供的批大小远高于其它模型。单个请求可能把几十或几百个文本输入批量放在一个列表里，许多请求能在单块 GPU 上并行跑，因为即便最吃资源的嵌入模型也相对小而快。

无论你做大规模回填还是应对使用激增，流量都可能超过嵌入模型提供的大批大小。这些情况下，稳健的排队系统是支持嵌入模型推理的关键基础设施。

## 6.3 ASR 模型

自动语音识别（ASR）模型以音频为输入、产生文本输出，驱动转写和听写应用。最流行的开源 ASR 模型是 OpenAI 发布的 **Whisper**。Whisper 支持数十种语言、转写准确。

> **图 6.4**：ASR 模型把输入音频转写成文本。

Whisper 有多种尺寸，但最大、最高质量的 Whisper 模型只有 15.5 亿参数。Whisper 在 H100 等大 GPU 的切片上（通过多实例 GPU，MIG）运行极快。虽然存在各种其它尺寸、变体、蒸馏和量化，实践中用最高质量模型——Whisper 3 Large 和 Whisper 3 Turbo——就能满足大多数延迟预算。

Whisper 是编码器-解码器模型：

- **编码器**：接受处理过的音频波形（log-Mel 频谱图），编码成音频特征。
- **解码器**：接受这些编码的音频特征，转换成文本 token。

绝大多数推理时间花在解码器上，它是与 LLM 架构非常相似的自回归 transformer 模型。幸运的是，有出色的工具来优化这个主要瓶颈。

解码器侧性能优化的主要工具是 TensorRT-LLM。用 TensorRT-LLM，你获得解码器的 in-flight batching，以及带高效 CUDA 内核的优化 C++ 运行时。TensorRT-LLM 与 Hopper、Blackwell 等近期架构配合特别好，让 MIG 成为 ASR 推理的更好选择。

### 6.3.1 单块延迟优化

Whisper 的一个用例是实时转写，如听写应用或语音 agent。

对实时 Whisper，看单个音频块被转写的往返时间。一个很好的目标是 **200 毫秒**，即人类的平均反应时间。

Whisper 跑在优化的 TensorRT-LLM 推理引擎上时，在运行时层面提升性能的工作不多。相反，实时 Whisper 的大多数收益来自编排和基础设施。

ASR 产品体验的最大升级是**流式（streaming）**，它在 API 服务器层而非模型运行时层实现。通过建立 WebSocket 连接（7.5.3 节）并持续流式传入音频、流出文本，产品能实时转写，而非转写预录音频。

ASR 运行时层不变。相反，流式转写实现用一个**语音活动检测（VAD, Voice Activity Detection）模型**监控进来的流，把它分割成离散块供 ASR 模型处理。推理照常跑在块上，文本结果经 WebSocket 流回。

这个设置能处理多个并发流，且有保持转写顺序的优势。当每块在同一 GPU 上处理时，你可以用上一块的输出序列作为下一块的前缀，提升转写质量。

### 6.3.2 长文件延迟优化

Whisper 模型的一个局限是它只能支持 30 秒的块。转写长文件（如一小时播客）需要另一组优化。

用名字易混淆的**实时因子（RTF, Real-Time Factor）**衡量长文件转写的性能。如果世界最快的打字员能在 30 分钟内手动转写一小时音频，他的 RTF 就是 2X。用为长文件优化的 Whisper 部署，你能在不到四秒内转写一小时音频，RTF 达 1000X。

长文件的快速转写需要多步流水线。第一步又是一个 VAD 模型，这次跑在它自己的专用硬件上。该模型用于移除静音、切出有意义的音频段，而非按时间间隔切——后者有把词切半的风险。

然后，这些块可以并行处理。理想情况下，你用多块 GPU（或多个 MIG）同时处理更多音频块。RTF 随所用 GPU 数大致线性提升。每块 GPU 用 in-flight batching 同时处理多个块以获得高利用率。

最后，分块转写按时间戳拼接回去。

> **图 6.5**：长音频文件转写的两阶段流水线，并行化分块转写以改善端到端请求时间。

并行化分块转写，消除了用前一序列作下一序列前缀的能力。但有其它质量改进技术绰绰有余地弥补。

对 ASR 输出，你可以通过测量输出的压缩比和每分钟词数，自动检测重复词和短语等幻觉。当一块有问题时，你可以：

- 用更高温度重跑该块。这有违直觉——更高温度通常产生更多幻觉——但意图是打破重复词的循环，生成不同输出。
- 把整段音频或其中一段重新切成更小块，重跑转写。

实践中，这些技术让「传前一序列作前缀」变得不必要，解锁长文件的高效、准确并行转写。

### 6.3.3 说话人分离（Diarization）

说话人分离（diarization），即给转写标注「谁在何时说话」，是与转写相邻的问题。说话人分离模型按语音特征对音频分类，然后跨文件分割和聚类，给说话人变化打时间戳。

说话人分离模型是完全不同类别的模型。Whisper 是编码器-解码器 transformers 模型，而 pyannote audio 等说话人分离系统是经典 ML 模型的流水线。

一个说话人分离流水线包含分割、嵌入和聚类模型。要优化说话人分离，你必须让每个模型跑得快，并高效编排整个流水线。

由于说话人分离是 ML 流水线，你可以用 PyTorch、pyannote 等工具，配合 Torch 编译等优化来改善性能。实践中，即便高度优化的说话人分离实现，处理音频文件也至少比转写慢两倍。

## 6.4 TTS 模型

文本转语音（TTS）模型，又称语音合成模型，以文本为输入、产生音频输出，特别是生成语音。2025 年，Orpheus TTS 等开源模型把极其逼真的语音合成带进开源模型生态。许多公司微调 Orpheus 以提升音质和产品专属声线，导致语音 AI 领域对开源模型的高采用。

> **图 6.6**：文本转语音模型把输入文本合成为音频。

现代 TTS 模型是微调过的 LLM。例如，Orpheus TTS 派生自 Llama 3.2 3B。这意味着为 LLM 开发的许多运行时和性能优化都适用于语音合成模型。

TTS 模型参数量小——Orpheus TTS 的 30 亿算是偏大的——意味着和 ASR 模型一样，H100 上的 MIG 是高效高性能的推理选择。

与通常跑在 FP16 的 ASR 模型不同，TTS 模型权重和 KV Cache 可以量化到 FP8 以获得更好性能，此外还有 TensorRT-LLM 推理引擎引入的优化内核和 in-flight batching。

有 LLM 骨干的 TTS 模型，是通过把 LLM 词表扩充数万个编码音频 token 来训练的。然后，模型在「文本输入 + 分词音频输出」的对上训练。这意味着实际使用 TTS 模型时，你还需要一个**音频解码器**，把音频输出 token 转换成波形。

这个音频解码过程给推理增加潜在瓶颈。音频解码器应用 PyTorch 实现、为目标 GPU 编译以高效运行，并用短超时（如 15 毫秒）的动态批处理。音频解码器无法用 in-flight batching。

TTS 模型性能用与 LLM 略不同的指标衡量。关键指标是：

- **TTFB**：Time to first byte（首字节时间），是语音合成的 TTFT 等价物。
- **到第一句话的时间（Time to first sentence）**：相比 TTFB，更面向用户的延迟指标是生成第一个有意义的短语或句子的时间。
- **TPS**：和 LLM 一样，TTS 模型生成 token，所以 decode 速度可用每秒 token 数衡量。

和 LLM 的 TTFT 一样，语音合成的目标是最小化 TTFB。对 Orpheus，单块 H100 上可低至 150 毫秒。

然而，语音合成模型的 TPS 目标不同。模型生成的 token 被转换成音频波形。取决于模型，实时生成音频可能需要每秒 80 到 100 token。超过这个水平，每秒生成更多 token 没有任何好处。

相反，性能增强用于在「模型能创造的并发实时输出数量」上扩展吞吐。如果单块 GPU 能支持许多并发用户，语音合成的每用户成本就大幅下降。

### 6.4.1 流式实时文本转语音

大多数 TTS 任务需要实时语音合成。和 ASR 模型一样，实时系统的性能收益较少来自运行时层——它已经用 TensorRT-LLM、量化和编译过的 SNAC 解码器优化过——而更多来自基础设施。

同样，相比离散块地发文本收音频，通过 WebSocket 流式是性能的最大解锁。在测试推理引擎确定能生成多少并发实时流之后，设置相同的批大小和活跃 WebSocket 数，保持使用率高但稳定。

TTS 模型很少在实时应用之外使用。然而，如果你确实有批量用例（如把大语料文档回填成音频以改善可及性），注意 TTS 模型对长输入表现不佳，语音在 30 秒左右后开始退化。

### 6.4.2 语音到语音模型

一个令人兴奋的研究领域是**语音到语音模型**，即以音频为输入、生成音频输出的模型。

今天，大多数语音系统用**级联（cascading）方法**，ASR 模型、LLM 和 TTS 模型在流水线中协同工作，听、想、回应用户。这些流水线还用 VAD 和嵌入模型等辅助组件，促进自然对话并增加上下文。

> **图 6.7**：大多数基于语音的应用用级联方法配合多模型流水线。

语音到语音模型（如 OpenAI 的 gpt-realtime）给核心 LLM 增加音频消费和生产能力，实际上把流水线统一到单一模型中。这之所以可能，是因为 ASR、LLM、TTS 共享如此相似的架构，尤其是解码器。

截至出版时，没有商业上可行的开源语音到语音模型，gpt-realtime 等闭源选项比级联多模型设置能力更弱、成本更高。然而，这个领域的研究很稳健，这个新兴模态很快将需要它自己的推理工程风格。

## 6.5 图像生成模型

> **图 6.8**：图像生成模型可同时接受文本和参考图像，创建新输出图像。

处理图像和视频生成模型，在几个轴上都与处理大语言模型完全不同。

首先是**架构**。虽然 HunyuanImage-3.0 等近期模型更像 LLM，大多数图像和视频生成模型是迭代去噪器，而非自回归 token 生成器。图像生成模型是多个小模型在潜在空间中协同工作的流水线，而非 LLM 的统一解码器架构。

因此，**工具**也不同。截至出版时，SGLang Diffusion 和 vLLM Omni 都是全新的。大多数图像和视频生成模型推理在栈的更低层实现，直接用 PyTorch 或 TensorRT。

**约束**也不同。图像生成模型比前沿语言模型小十到二十倍，推理受算力而非带宽约束。

但也许最显著的差异是：图像和视频生成模型提供更直接的质量-速度权衡。

程序化评估图像模型输出质量很难。用视觉语言模型的自动流水线最多给方向性信号，且可能与人类偏好分歧。人眼是神秘的，大多数图像质量 eval 靠让人类在数千张图像中挑选，把「感觉」和偏好聚合成质量基准。

### 6.5.1 图像生成内核优化

当你从仓库读图像生成模型的模型卡时，推理示例通常用 diffusers 库、几乎不做优化。

事实上，虽然图像生成理论上算力受限，你常常需要选择内存高效的内核、用内核融合，才能达到那个瓶颈。

高性能图像模型推理用三个库之一：

- **SGLang Diffusion**：为流行图像和视频生成架构打造的高性能推理引擎。
- **TensorRT**：用 NVIDIA 内部内核的流行模型高质量黑盒实现。
- **PyTorch**：仔细的内核选择和融合，带来控制力、灵活性和改进的高端性能。

如果你想要现在就能用且效果好的东西，就用模型的 SGLang Diffusion 或 TensorRT 实现。但用 PyTorch，高级推理工程师有机会做深度定制。

最关键的内核是**注意力内核**。许多图像生成模型开箱即用 FlashAttention 2，但 FlashAttention 3 和 4 分别在 Hopper 和 Blackwell GPU 上性能更好。

还有一整批更小的内核，尤其是 RMSNorm 等归一化函数，是融合的好候选，以确保高效内存使用。

然后，GEMM 内核对算力受限推理很重要。GEMM 内核应用于线性层，通常可以安全量化到 8 位浮点格式，以在 Tensor Core 上获得两倍 FLOPS。CuTe、CUTLASS 或 DeepGEMM 的内核可能逐模型证明最高效。

Torch 编译包含自动内核融合，带插件系统插入手动选择的内核，产生的引擎可缓存以加快节点启动加载时间（这很重要，因为编译要几分钟）。

和大多数高性能引擎一样，Torch 编译针对执行编译的特定 GPU 型号和架构——如果你想在 B200 上跑模型，就在 B200 上编译。

### 6.5.2 加速图像生成的一个怪招

内核选择和 Torch 编译都是货真价实的推理优化技术。但推理优化的世界也有有趣的招数，这里有一个。

> **图 6.9**：回忆扩散是逐步过程，图像的大致轮廓在早期步骤就已确立。

图像生成时间随步数线性跟踪。这就是少步模型和潜在一致性模型比完整 50 步模型快得多的原因。但减少步数可能把图像质量降到不可接受阈值以下。

每次通过去噪模型都以批大小 2 运行，因为每步包含一次带 prompt 引导、一次不带引导的通过。

复习一下：引导参数控制每步生成两次迭代合并时，prompt 引导图像占多大权重。如果引导为零，就不需要生成 prompt 引导图像。

前几步之后，图像的基本轮廓已就位，剩余步骤用于填充细节。因此，prompt 遵循度在影响图像大轮廓的早期步骤更重要——模型不会在后几步改变主意，在生成猫的半途生成一只狗。

如果你在图像生成中途关掉引导，就能在不减少步数的情况下省去通过去噪器的次数。如果 50 步运行的最后 20 步跳过引导，就只有 80 次通过模型而非 100 次，质量通常保持高位。

## 6.6 视频生成模型

> **图 6.10**：视频生成模型接受文本 prompt，也可能接受关键帧或其它图像、音频和视频输入。

视频生成是最吃资源的模态。只要可能，这些模型应跑在 Blackwell GPU（或 Rubin，一旦可用）上。这些 GPU 提供高内存容量用于上下文并行、快速 Tensor Core 用于注意力计算，以及微缩放数据格式用于更精确的量化。

架构上，视频生成与图像生成相似，只是从潜在空间渲染完整视频而非单帧。遵循「更大规模解锁更多技术」的原则，视频生成用图像生成的全部技术，外加额外优化。

和图像生成一样，视频生成是算力受限的，通过在潜在空间上迭代去噪工作。视频生成模型通常与图像生成模型步数大致相同（约 50 步），但每步处理的数据多得多。

由于视频生成模型算力受限，批处理不像文本生成那样有用。视频生成模型通常以批大小 1 跑在八块 GPU 的完整节点上：全部八块 GPU 协同工作，一次创建一个视频。

与可通过调整批大小做延迟-吞吐权衡的批量负载不同，改善视频生成吞吐和成本的唯一方式，是让模型本身更快。

早期视频生成模型是逐帧的，一次生成一帧，降低了视频输出的质量和连贯性。今天，视频生成模型在潜在空间中对视频整体跑去噪步。图像生成的潜在空间表示两个维度（宽、高），视频模型则表示三个（宽、高、时间）。

这意味着每次注意力计算都要传海量数据。对视频模型，注意力占计算时间的 70–80%，使注意力成为最需要优化的东西。

### 6.6.1 注意力优化与量化

注意力优化从内核选择开始。测试 FlashAttention、DeepGemm、CuTe 和 CUTLASS 内核，看哪些对你的模型表现最好。

语言模型用 KV Cache 加速注意力，视频生成模型则用其它缓存模式尝试复用模型输出。复用部分注意力计算，实践中能让视频生成快 30–40%。

精确方法随新研究不断变化，但缓存有两种基本方法：

- **基于时间步的缓存**：缓存并复用某些时间步的输出，跳过整步。
- **基于 transformer 的缓存**：缓存并复用隐藏状态，跳过 transformer 内的层。

算法和实现从「质量退化可忽略」到「输出不可用」不等——生产使用前要仔细测试这些策略。

除内核和缓存外，加速注意力的主要工具是量化。

对带宽受限的语言模型推理，量化的好处是你要通过内存加载的数据更少。对视频模型，它意味着切换到低精度 Tensor Core 获得两倍 FLOPS。

然而，语言模型量化聚焦**权重**——量化影响可忽略的大线性层。对视频模型，量化权重仍有帮助，但这些层虽占语言模型大部分内存带宽，对视频模型却只是计算时间的一小部分。

相反，视频模型的量化聚焦**注意力**。注意力是任何模型量化风险最高的部分，因为误差在推理过程中累积。对视频模型，只有约 50 步而非 token 生成的数千次自回归迭代，风险略低但仍重要。

降低质量影响的第一种方法，是用块级量化和微缩放数据格式（MXFP8），二者 Hopper 和 Blackwell 上都有。微缩放数据格式更好地保留离群值，而离群值对注意力精度影响重大。

注意力量化最精细的方法，是在模型内选择性量化，按：

- **步（Step）**：早期步保留 FP16，量化后期步。
- **层（Layer）**：保留首层和末层，量化隐藏层。

按步量化遵循图像生成模型无分类器引导招数一样的洞见：早期步确立图像轮廓，后期步精炼细节。早期步对 prompt 遵循度和准确性更重要。

对层而言，首层和末层更重要，因为它们接受输入、产生最终输出。隐藏层只做中间计算，受近似影响没那么大。

只量化视频生成过程中较不重要的部分，就能保留质量。这些招数见于 SageAttention 等内核——一个 8 位注意力内核，可用于视频生成模型的高质量低精度注意力。

### 6.6.2 上下文并行（Context Parallelism）

虽然视频生成模型通常跑在八块 GPU 的完整节点上，它们用**上下文并行**而非张量并行。

上下文并行把权重复制到每块 GPU。视频模型小到复制权重八次会占可观内存，但在 B200 上可行。

上下文并行不是把模型拆到 GPU，而是把**注意力计算**拆到 GPU。这通过 ring attention 等机制协调：每块 GPU 持有一段上下文，把中间结果传给环中的下一块 GPU。

> **图 6.11**：上下文并行复制模型权重，但共享潜在空间以在视频模型推理中计算注意力。

transformer 模型的注意力是多头的，通常八个或更多头。注意力头是独立的，所以可以分开运行，之后合并结果。

注意力不是唯一可并行的。例如，用变分自编码器的潜在解码步占总推理时间的 3–5%，可跨 GPU 运行。

这些并行技术让 AI 视频可行。随着视频序列变长、视频模型变大，并行将继续是视频生成模型推理最关键的技术。
