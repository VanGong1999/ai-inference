# 第 4 章 · 软件（Software）

> Inference Engineering — Philip Kiely · Chapter 4

NVIDIA 在推理领域的主导地位，很大程度上归功于其硬件周围稳健而成熟的软件生态。

硬件迭代周期很慢。Apple、NVIDIA 等一流硬件公司最多每年发布一次新架构和新世代，两年发布周期更常见。

但软件迭代很快。通常，要在第零天运行一个新发布的开源模型，你需要安装每个软件依赖的 nightly 构建或其它预发布版本，只为获得对新模型的支持。

软件快速的迭代周期和更低的门槛，极大地扩展了推理工程的版图。硬件以 NVIDIA 和少数竞争者为中心，而有无数的公司在推理栈的各个层级构建软件。

对推理工程师而言，这些是关键玩家：

- **NVIDIA**：大力投资自己有时是专有的软件生态，从 CUDA 直到 Dynamo。
- **Hugging Face**：维护所有开源模型的模型仓库，以及 transformers 和 diffusers。
- **Linux Foundation**：维护 PyTorch、vLLM 等硬件无关项目。
- **LMSYS Org**：开发推理和评估的关键工具，最著名的是 SGLang。

还有数千家公司、大学和研究机构，为推理做出关键的开源贡献。

软件领域太大、太快，任何一本书（更不用说一个章节）都无法穷尽记录。因此，本章只呈现具有长期相关性的基础技术。

贯穿本章，技术以递增的抽象层级呈现：

- **CUDA**：与 GPU 直接通信，显式控制计算和内存（4.1 节）。
- **深度学习框架**：CUDA 之上的抽象，用 Python 训练、导出和运行神经网络（4.2 节）。
- **推理引擎**：为常见架构提供高度可配置的、PyTorch 支撑的推理（4.3 节）。
- **NVIDIA Dynamo**：位于推理引擎之上，驱动大规模部署（4.4 节）。

今天大多数推理工程发生在较高抽象层级：配置和部署推理引擎、跨多 GPU 编排推理。无论你在栈的哪一层工作，对相邻抽象层级有强健的心智模型来指导工作，都是必不可少的。

## 4.1 CUDA

CUDA 是你在 NVIDIA GPU 上写运行代码的方式。

更正式地说，CUDA 是 NVIDIA 的专有计算平台和编程模型，用于在 GPU 上执行并行任务。「平台」和「编程模型」都是宽泛定义；更容易从组成部分看 CUDA：

- **CUDA kernel（内核）**：在 GPU 上执行并行化代码的用户自定义函数。
- **CUDA graph（图）**：内核和其它 GPU 操作的有向无环图（DAG），用于优化重复工作流。
- **CUDA driver（驱动）**：应用与 GPU 硬件之间的低层接口，管理内存和执行。
- **CUDA runtime（运行时）**：面向开发者的 API，用于启动内核和管理内存。

CUDA 代表 Compute Unified Device Architecture（统一计算设备架构），尽管这个缩写如今很少被展开——它是 NVIDIA GPU 上整个生成式 AI 生态的基础。

CUDA 不是一门编程语言。相反，CUDA 程序用一门编程语言（最常见是 C++）指定，然后由 nvcc 等编译器分别编译成 CPU 代码和 GPU 代码。

一个 kernel 只是一个做并行计算的函数。每当你看到「CUDA kernel」这个词，你可以把它替换成「一段为 NVIDIA GPU 写的代码」。

以一个「Hello, World!」内核为例，考虑这六行 C++ 代码：接收一个长度为 n 的数组，把数组中每个元素翻倍。

> **图 4.1**：示例 CUDA 内核把数组中每个值翻倍。

通常，在 CPU 上，这个函数会以线性时间运行，数组中每个元素被顺序翻倍。但在 GPU 上，数千个元素能被同时处理，使这个函数高效得多。

写 CUDA 内核把推理工程从「思考算法」转向「思考实现」。例如，生成式 AI 核心的传统注意力算法，用几十行代码就能表达。然而，FlashAttention 是同样的数学运算，却要用数万行代码，为特定 GPU 以更高内存效率的方式实现这个算法。

### 4.1.1 推理用的 CUDA 内核

写 CUDA 内核并不意味着从零构建。

可以借鉴的既有成果比 CUDA 早几十年。**BLAS（Basic Linear Algebra Subprograms，基础线性代数子程序）**最早于 1970 年代为 Fortran 实现，是从点积到矩阵乘法等常见线性代数运算的规范。

**cuBLAS** 是 BLAS 的 CUDA 实现，以预构建内核的形式把该规范带到 CUDA，用于基础线性代数运算。类似地，**cuDNN（CUDA Deep Neural Network）**提供神经网络的原语。

在 BLAS 内，推理中最常使用的运算是 **GEMM（General Matrix-Matrix Multiplication，通用矩阵-矩阵乘）**。模型中每个线性层都用矩阵乘法，cuBLAS 提供了一个强起点。

但你并不局限于 cuBLAS 的实现。由于 GEMM 等运算对推理如此关键，你可能需要更细粒度的控制。你可能为不同形状的矩阵、或为更好地运行在特定 GPU 架构上而写不同的 GEMM 内核。

**CUTLASS** 是一个模板库，提供写高性能内核的构建块。例如，FlashAttention 3 用了 CUTLASS。**CuTe** 是另一个模板库，为近期架构引入分块张量运算的抽象。用 CUTLASS、CuTe 等工具，内核可以在更高抽象层级编写，同时保持强劲性能。

内核的另一个来源是 **FlashInfer**，一个库，提供 LLM 推理内核的高性能实现，包括许多优化过的注意力内核和融合采样函数。

### 4.1.2 CUDA 内核选择

大多数推理工程师永远不需要写自己的内核。然而，**内核选择**——从一系列选项中挑出最好的内核——是推理优化的重要部分。

内核实现是高度专门化的。CUDA 暴露内存管理和并行计算的低层 API，内核工程师基于他们所针对硬件的精确规格做实现决策。

理解内核实现与特定硬件细节绑定得有多紧，很重要。内核常有基于给定 GPU 内存带宽、或 Tensor Core 数量与布局的硬编码值。

为 H100 写的内核，很可能无法利用 B200 的架构和额外内存；而为 B200 写的内核，可能与上一代 Hopper 架构向后不兼容。每一代 GPU，把手写内核移植到新架构上优化运行，都需要大量工程工作。

大多数内核选择是自动的。深度学习框架和推理引擎为各种架构预配置了内核，而 PyTorch 和 TensorRT-LLM 在编译步骤中包含自动内核选择。

不过，你可能为关键算法手动选几个内核来加速推理。

例如，大多数生产级 GEMM 内核来自 cuBLAS。但当 DeepSeek 实验室发布 DeepSeek-V3 的更新版时，他们也发布了 **DeepGEMM**，提供在 Hopper GPU 架构上跑 FP8 矩阵乘法的更高效 GEMM 内核。

手动内核选择让你把 DeepGEMM 内核作为插件插入，加速推理中特定的一步，比如乘两个精确维度的矩阵。只是要小心确保兼容性。例如，如果你升级到 B200 GPU，你要么把内核换回来、要么等 DeepGEMM 的 Blackwell 支持（截至出版时已支持）、要么自己移植内核。

### 4.1.3 用内核融合减少内存访问

在同一数据上背靠背运行两个不同内核，会导致对内存的浪费读写。

举个简单例子，想象两个内核：`multiply_by_2` 和 `multiply_by_3`。如果背靠背运行，序列会是：

- 从内存读输入向量 `[1, 2, 3]`。
- 对向量运行 `multiply_by_2`。
- 把输出向量 `[2, 4, 6]` 存回内存。
- 从内存读新输入向量 `[2, 4, 6]`。
- 对向量运行 `multiply_by_3`。
- 把最终输出向量 `[6, 12, 18]` 存回内存。

低效很明显：第三、四步构成一次不必要的内存往返。在 LLM 推理的内存受限阶段 decode 期间，推理引擎承担不起对内存的不必要读写。

**内核融合（kernel fusion）**是把两个或更多内核重写成一个处理所有运算的单一内核的过程。在这个例子里，融合后的内核会是 `multiply_by_6`，新的操作顺序是：

- 从内存读输入向量 `[1, 2, 3]`。
- 对向量运行 `multiply_by_6`。
- 把最终输出向量 `[6, 12, 18]` 存回内存。

实践中，内核融合复杂得多——函数更复杂，数据重叠也没那么干净。但推理的内核融合有常见模式，比如把矩阵乘法、加偏置和激活组合在一起。

> **图 4.2**：内核融合减少 GPU 内内存与算力之间的读写。

内核融合可以是自动或手动过程。编译器能识别直接的融合机会并自动创建融合内核。但 FlashAttention 等更复杂的算法需要手写融合内核，在推理时通过插件使用。

## 4.2 深度学习框架与库

深度学习框架和库，是「直接写 CUDA」与「用 vLLM 等现成推理引擎」之间的桥梁。这些库在训练和推理中都用。

过去几年，**PyTorch** 已在这一层栈中成为明显领导者。另外两个框架，为简洁起见，我只简要提及：

- **TensorFlow**：Google 官方支持的端到端机器学习平台，在 2010 年代 ML 时代很显赫，但今天已失宠。
- **JAX**：与 Google 非官方关联的研究项目，呈现更简单的接口，没有那么多遗留特性和操作。不过，正如文档警告的那样，做好被尖锐边缘割到的准备。

本节其余部分聚焦 PyTorch 及栈中它周围和之上的技术。

### 4.2.1 PyTorch

PyTorch 是一个描述张量运算的 Python 包。它最初在 Meta 创建，现属 Linux Foundation 的一部分，是生成式 AI 模型训练和推理背后的行业标准技术。

就我个人而言，我整个职业生涯都是 Python 程序员，写底层 C++ 对我很难。用 PyTorch，我能用 Python 为 CPU 和 GPU 写高性能推理代码，但必要时总有选项通过插入特定内核下沉到 CUDA。

PyTorch 能训练任意类型的神经网络。PyTorch 文档展示了一个基础神经网络示例：

> **图 4.3**：PyTorch 中的基础神经网络，改编自 PyTorch 文档。

虽然这是个非常简单的例子，你可能认出第 2 章讨论的线性层和 ReLU 激活函数是神经网络的关键部件。

PyTorch 通过其 autograd 模块，为任意可微函数自动计算梯度。这正是 PyTorch 对训练如此强大的原因——你定义一个计算图，就能得到可训练的梯度。

但 PyTorch 特别之处在于：它不只擅长训练，对推理也很强大。PyTorch 在内置函数和自动性能优化之间，与你需要的手动控制之间取得平衡。

把模型从训练转到推理的那一步是**编译（compilation）**。PyTorch 编译（`torch.compile`）针对特定 GPU，执行自动内核选择和内核融合，以确保最优性能。

`torch.compile` 无法融合 DeepGEMM、FlashAttention 或自定义内核等插件内核。这限制了它对 LLM 推理的效用，因为 LLM 的大多数内核是定制的。然而，PyTorch 编译对优化不太常见的模型架构、编译长序列的轻量内核很有用。当你优化一个有定制或罕见架构的模型时，你可能不得不把函数重写得更抽象——尤其针对 Python 特有的语言特性——编译才能成功。

单独用 PyTorch，是为常见模型架构构建高性能推理服务的强大灵活工具。但 PyTorch 之上有一个丰富生态，能更快地实现、编译和执行优化代码。

### 4.2.2 模型文件格式

序列化模型权重的主导文件格式是 **safetensors**，由 Hugging Face 创建。

Safetensors 是 bin 等通用格式的替代品，专为存放模型权重而设计。safetensors 中的「safe」来自：与能在反序列化时执行任意 Python 代码的通用格式不同，safetensors 只存放张量数据，不存放可执行代码。

生成式 AI 模型有几百 GB 权重。这些权重被拆分到几十个 safetensors 文件里。safetensors 格式用内存映射（memory mapping）确保文件无需分配完整内存即可加载，这让加载模型权重更快、更安全。

另一个主流格式 **ONNX（Open Neural Network Exchange，开放神经网络交换）**，把权重与模型的执行图一起存储。safetensors 格式把权重与架构分离，ONNX 则把它们打包在一起。

ONNX 文件高度可移植。凭借与 PyTorch 的深度集成和对多种硬件的支持，当你想存储模型图而不只是权重时，ONNX 是 safetensors 的绝佳替代。

### 4.2.3 ONNX Runtime 与 TensorRT

ONNX Runtime 和 TensorRT 是高性能推理运行时。PyTorch 模型可以导出到 ONNX 格式，ONNX Runtime 能直接执行，或 TensorRT 能编译成高度优化的引擎。

| ONNX Runtime | TensorRT |
|---|---|
| 开源，与 Linux Foundation 关联 | 专有与开源组件混合，NVIDIA 打造 |
| PyTorch 生态的一等导出器 | 通过 Torch-TensorRT 与 PyTorch 集成 |
| 支持多种 GPU | 仅 NVIDIA GPU |

ONNX Runtime 是开放的社区标准，而 TensorRT 专用于 NVIDIA GPU。

导出过程看起来有点像 Torch 编译。然而，这些标准不支持 PyTorch 内的每种数据结构、类型和运算。导出过程能识别 PyTorch 代码中的这些问题，但对更复杂的模型就棘手了。

一个例子是 DeepSeek V3，它引入了多头潜在注意力（MLA）。MLA 在 PyTorch 中的实现难以导出，但 transformers 架构整体足够简单，手工融合内核是可行的。

今天，对这些引擎支持的模型，越来越流行直接从 PyTorch 跳到 vLLM、TensorRT-LLM 等推理引擎，绕过中间表示步骤，只用 safetensors 导出权重。ONNX Runtime 和 TensorRT 仍被广泛使用——TensorRT 尤其因为其图像和视频模型的强大开箱即用运行时——但行业正在分叉：要么用手写 PyTorch 代码的控制力，要么用预构建推理引擎的便利。

### 4.2.4 Transformers 与 Diffusers

Hugging Face 的 transformers 和 diffusers 库构建在 PyTorch 之上，但**不是为运行大规模生产推理而设计**。相反，这些库提供模型的参考实现，供推理工程师学习和改编。

虽然这些库是「折腾」的工具箱，它们确实包含关于模型的关键信息，以及构建模型推理服务器的有用工具。为 transformers 和 diffusers 实现的模型所附带的 `config.json` 文件包含关键信息，而这些库用于 Hugging Face 操作（如下载模型权重）的工具被广泛使用。

你会在 Hugging Face 上大多数流行开源模型的模型卡（model card）里找到 transformers 或 diffusers 的示例代码。这个示例代码很适合理解模型的精确输入输出规格，或运行本地推理和 notebook。但对生产，你要么直接写并编译 PyTorch 代码，要么用生产级推理引擎。

## 4.3 推理引擎（Inference Engines）

市场上有三个有竞争力的推理引擎：**vLLM、SGLang 和 TensorRT-LLM**。

这些框架为 LLM 和架构相似的其它模态提供良好的开箱即用性能（第 6 章）。

2025 年末，vLLM 和 SGLang 也分别通过 vLLM Omni 和 SGLang Diffusion 开始支持一些图像和视频生成模型。TensorRT-LLM 不支持图像或视频生成模型。推理工程师也可以直接用 TensorRT 或 PyTorch 运行这些模型（6.5 节）。

推理引擎之所以强大，是因为它们是**可配置的**。在更高抽象层级处理预优化组件，推理工程师可以把时间花在测试技术组合上，而不是重复常规实现。

在很高层面，vLLM 和 SGLang 是更通用的工具，更容易采用、对更多模型有第零天支持；而 TensorRT-LLM 学习曲线更陡，但通常性能最好。

| 引擎 | vLLM | SGLang | TensorRT-LLM |
|---|---|---|---|
| 性能 | 好 | 好 | 最好 |
| 易用性 | 易 | 易 | 难 |
| 模型支持 | 最多 | 最多 | 部分 |
| 硬件 | GPU、TPU | NVIDIA、AMD | 仅 NVIDIA |
| 许可证 | Apache 2.0 | Apache 2.0 | Apache 2.0 |

每个框架开箱即用就支持连续批处理等核心特性，并支持主要性能优化技术——训练后量化、投机解码、前缀缓存、并行、分离式服务。

在 Baseten，我们三个框架都用，尽管用 TensorRT-LLM 最多。推理工程师应熟悉所有三个，并按部署逐个选择。

### 4.3.1 vLLM

vLLM 在推理引擎中市场份额最大。GitHub star 是流行度的粗略衡量，但截至出版时，vLLM 的 star 数是 SGLang 和 TensorRT-LLM 之和的两倍。

vLLM 于 2023 年夏首发，是这些推理引擎中最早几个月的。它最初在 UC Berkeley 创建，现在由 Linux Foundation 内的 PyTorch Project 托管。

vLLM 的最大卖点是它的广泛支持。它支持的硬件选项最多——NVIDIA、AMD、Intel GPU 以及 Google TPU——也支持最多的模型和架构。几乎每个开源 LLM 都从第零天就与 vLLM 集成。vLLM 还通过 vLLM Omni 支持多模态推理，扩展引擎以支持图像、音频和视频输入输出。

推理工程的核心原则之一是：能引入的约束越多，能达到的性能越好。vLLM 的宽平台在正确配置时能实现令人印象深刻的性能，但以我的经验，它达不到 TensorRT-LLM 等窄框架可能的最高端性能。

vLLM 的开发者体验围绕 `vllm serve` 命令构建，服务器配置以 flag 传入。

> **图 4.4**：八 GPU 上的 vLLM 推理示例。

vLLM 可 pip 安装，并提供官方 Docker 镜像，预打包依赖、支持多种硬件架构。

**你应该用 vLLM 当：**

- 你想快速搭起一个模型服务器，几乎任何开源模型开箱即用就有扎实性能。
- 你想跑有多个输入输出模态的「Omni」模型。
- 你在用较小的 GPU 或较旧架构，TensorRT-LLM 提供不了多少性能收益。

### 4.3.2 SGLang

SGLang 是另一个主要的社区驱动快速推理框架。它于 2023 年 12 月首发，随 DeepSeek、Qwen 等中国开源模型一起声名鹊起，是 xAI 推理的首选引擎。

SGLang 对模型服务问题的独特角度体现在它的开发者体验上：把一个快速后端运行时与一个灵活的前端语言配对。实践中，这意味着你可以为深度定制选择引擎的单个组件，而无需从头重写其余部分。

SGLang 同时支持 NVIDIA 和 AMD GPU，并对广泛模型有强大的第零天支持。SGLang 与 DeepSeek、Qwen、Kimi、Z AI 等实验室密切合作，为 DeepSeek 的多头潜在注意力等新架构特性发布优化实现。

SGLang 大力投资支持 MoE LLM 的大规模部署，特别是 GB200 NVL72 等系统上的多节点部署，以获得高吞吐。这些系统为流量巨大的大模型提供极划算的推理。

SGLang 的开发者体验围绕 `sglang.launch_server` 命令构建，服务器配置以 flag 传入。

> **图 4.5**：八 GPU 上的 SGLang 推理示例。

SGLang 还通过 SGLang Diffusion 支持图像和视频生成模型推理。

SGLang Diffusion 引入了一个流水线抽象，编排若干阶段。这种灵活的方法紧密映射到图像和视频生成模型的架构。性能上，SGLang Diffusion 增加了对各种扩散专用并行方法的支持，并复用主 SGLang 包中的调度器和优化内核。

**你应该用 SGLang 当：**

- 你想在 DeepSeek、Kimi 等大 MoE 模型上获得出色的开箱即用吞吐和不错的延迟。
- 你想要图像和视频生成模型的推理引擎体验。
- 你想要控制力和定制化，并乐于参与 SGLang 社区。

### 4.3.3 TensorRT-LLM

TensorRT-LLM 是 NVIDIA 的开源推理引擎。三个主要选项中，TensorRT-LLM 提供最高性能和给专家用户最多的灵活性。

关于命名：TensorRT-LLM 有两个主要版本。只有旧版本才真正与 TensorRT 相关：

- **TensorRT-LLM V0（0.X.Y）**：以零开头的主版本是 NVIDIA TensorRT 的插件。
- **TensorRT-LLM V1（1.X.Y）**：以一开头的主版本是基于 PyTorch 的独立包，不依赖 TensorRT。

最初，TensorRT-LLM 构建 TensorRT 引擎来服务语言模型。用现代的 PyTorch 版本，TensorRT-LLM 绕过 TensorRT 的中间表示，直接用 PyTorch。

TensorRT-LLM V1 于 2025 年夏发布。上一主版本的部署仍很常见——务必始终检查你在用哪个版本。

TensorRT-LLM 之所以性能最好，很大程度上是因为它能访问 NVIDIA 工程师写的内核，包括一些闭源内核。这些手写、手工融合的内核，对 Hopper、Blackwell 等最新硬件架构、以及 NVFP4 等 NVIDIA 特有数值格式提供出色支持。

TensorRT-LLM 提供 in-flight batching（token 级连续批处理）的稳健实现，有助于吞吐。它还支持几乎所有你能想到的模型性能优化设置，包括量化、投机算法、前缀缓存、分块预填充、灵活并行和分离式服务。

V1 的 TensorRT-LLM 引入了一种很像 vLLM 和 SGLang 的开发者体验。不过，除了 `trtllm-serve` 命令上的 flag 参数，它还期望一个 `config.yaml` 文件做更深定制。

> **图 4.6**：八 GPU 上的 TensorRT-LLM 推理示例。

安装 TensorRT-LLM 的最佳方式，是通过 NVIDIA 的某个官方 Docker 容器运行它。

**用 TensorRT-LLM 当：**

- 你在 Hopper 或更新 GPU 上跑一个支持良好的模型架构。
- 你愿意做额外工程工作以获得最佳性能。
- 可选地，你计划用 NVIDIA Dynamo 服务，想要集成最深的引擎。

## 4.4 NVIDIA Dynamo

NVIDIA Dynamo 是一个用于模型服务的分布式系统，2025 年 3 月在 NVIDIA GTC 首次公布。

Dynamo 与每个推理引擎——vLLM、SGLang、TensorRT-LLM——作为后端协同工作，Dynamo 本身为大规模部署提供一个编排层。

Dynamo 为关键模型性能技术提供支持：

- **KV Cache 复用**：在请求之间保留 KV 信息，并基于前缀匹配路由请求。
- **分离式服务**：把 prefill 和 decode 分离到各自优化、独立扩缩的引擎上。
- **多节点并行**：可选地在单个副本中用两个或更多节点的 GPU，通常配合专家并行。

这些技术将在第 5 章详述。和推理引擎一样，推理工程师要为他们的用例配置 Dynamo 以获得最大性能，有很多工作要做。

Dynamo 对分布式 KV 路由、分离式服务和多节点模型并行的深思熟虑抽象，在运行时提供高性能的信息聚合，允许随流量波动实时调整配置。例如，你可以用基于 SLA 的规划器，在用户定义的 TTFT 和 TPS 约束上自动扩缩 prefill 和 decode worker。

作为一般原则，你的规模越大，可用的推理优化工具和技术就越多。

Dynamo 为规模而生：大模型、大流量。它擅长把 Kimi 家族等万亿参数基础模型服务给大量并发用户。对更小的模型，Dynamo 在大规模部署上仍能提供适度性能改进。

如果你在为一个从零构建的基础模型建推理 API，或在高使用量产品中服务开源模型，Dynamo 是很好的选择。

但许多部署不需要 Dynamo 的额外复杂度。除非你的量足够大、分离式服务和 KV 感知路由才值得，否则 Dynamo 是不必要的工作和多余开销。这些情况下，你可以直接用推理引擎。

Dynamo 是本章覆盖的最新项目，特性仍在构建中。Dynamo 在 Apache 2.0 许可证下开源。Dynamo 周围的社区很活跃，项目有公开 CI 和 NVIDIA 工程师的支持，欢迎贡献。

## 4.5 性能基准与负载测试

基准测试（benchmarking）是模型性能优化的重要组成部分。没有精确、准确的性能基准，就无从知道你的优化是否真的奏效。

一个高质量的基准尽可能逼真地模拟现实。最好的基准是把真实的生产流量**影子（shadow）**到你要测试的系统上。影子是复制进来的请求到测试系统的过程，这样你能在不影响原始请求的情况下基准它的性能。

如果你不能影子真实使用，就需要模拟它。LLM 性能受多种因素影响。模拟流量时，你需要在多个维度匹配你预期的生产负载：

- **序列长度**：首 token 时间和内存使用依赖输入序列长度（ISL）和输出序列长度（OSL），即 prompt 和响应中的 token 数。
- **流量规模与模式**：批处理和服务器负载取决于并发请求数。抖动流量以模拟真实使用。
- **请求内容**：每个请求内的实际 prompt 影响缓存命中率、草稿 token 接受率等性能因素。
- **输入参数**：temperature、推理努力程度等影响推理的设置，应设为其预期的生产值。

记住，优化关乎权衡和约束。如果你针对糟糕的输入最大化基准性能，生产中的性能就不会符合预期。

### 4.5.1 性能基准工具

由于性能基准应紧密反映生产流量，每个人的基准设置都该略有不同。但有几个常用工具：

- **SGLang Genai-bench**：SGLang 团队的 CLI 和看板，用于基准任何推理框架部署的模型。
- **NVIDIA GenAI-Perf**：NVIDIA 的客户端工具，用于在多样流量上测量延迟和吞吐。
- **Locust**：开源负载测试工具，不专用于生成式 AI 系统，能模拟多达数百万并发用户。

基准的另一个好工具是开源 evals 数据集——从 MMLU、gsm8k 等通用 evals 到 SWE-bench 等领域专用 evals。

虽然基准工作的目的是测量性能而非模型输出质量，这些 eval 数据集有两个用途：作为一组多样且真实的输入，以及抽查性能优化是否影响了模型输出质量。

可能的话，选一个匹配你生产系统预期用途的 eval 数据集，比如为代码补全系统降低延迟时用 HumanEval。

### 4.5.2 性能基准建议

除了真实，好的基准还要**一致**。确保你的基准发出足够流量以获得良好的性能读数，而不被离群值左右。拿不准时，多跑几次基准取平均。

在做任何性能优化工作前，先有一个扎实的基线基准。测试优化时，保持基准设置中配置一致，并单独以及整体测试每个优化，以充分理解是什么驱动了性能改进。有些情况下，优化会相互打架，比如在大批量下跑投机解码。

「一次只改一个东西」的原则也适用于你的基准配置。常常需要测试各种流量模式或序列形状，但和任何实验一样，一次只改一个变量，以确保得到清晰结果。

### 4.5.3 性能剖析（Profiling）

剖析（profiling）比基准深入一层。基准给出一个单一数字（如 P90 TTFT 是 350 ms），剖析工具则展示这每一毫秒花在推理过程的哪里。基准告诉你系统表现如何；剖析告诉你它为什么这样表现。

> **图 4.7**：内核剖析器展示内核内每个运算执行多久，揭示瓶颈。

大多数推理工程师在日常工作中不需要做剖析。用 TensorRT-LLM 等已经高性能的工具时，你的工作流是配置与基准的循环——剖析是多余的。

然而，如果你在给 vLLM、SGLang 等推理框架做贡献、自己用 PyTorch 写推理服务、或在视频生成等新模态的前沿工作，性能剖析应该是你工具包的一部分。

推理最流行的剖析工具是：

- **PyTorch Profiler**：易用的剖析库，捕获推理期间的逐步性能指标（CPU 时间、GPU 时间、内存使用）。
- **NVIDIA Nsight Systems（NSys）**：功能多但复杂的 GPU 和 CPU 采样追踪工具，提供跨多 GPU 及其互连的全系统分析。
- **NVIDIA Nsight Compute（NCU）**：剖析工具和 CLI，深入分析单个 CUDA 内核的算力和内存使用。

此外，TensorFlow、TensorRT 等框架自带内置剖析器。

剖析器很有价值，因为它们给你关于算力和内存使用的细粒度信息，引导你的优化工作去改进推理流水线中最昂贵的步骤。

例如，用 PyTorch Profiler 你可能发现激活函数因过多内存读取而异常耗时，然后想出写一个融合内核、把激活与注意力一起运行以防过多读取。接着，你把新内核插入 PyTorch 代码，重跑系统级基准，看是否达成延迟目标。

剖析和基准一起，给你改进系统性能所需的信息，并最终给你把优化部署到生产的信心。
