# 第 5 章 · 技术（Techniques）

> Inference Engineering — Philip Kiely · Chapter 5

在推理工程工作最酷的一点是：与许多新学术研究要花几年甚至几十年才被工业界采用不同，新论文里的技术几个月甚至几周内就在生产中上线了。

研究与生产之间有一道需要跨越的鸿沟，而行业内一些最引人注目的推理工程工作，正来自跨越这道鸿沟。

推理工程的一个核心原则是：你在推理系统中能引入的约束越多，能达到的性能就越好。这一原则贯穿本章，比如分离式服务（disaggregation），它让你把单个引擎约束到 prefill 或 decode 上。

有了这些模型性能技术，还有一条新原则要记住：**你的流量越多，能做的性能优化就越多（同时保持单位经济性合理）。** 跨更多 GPU 的更高模型并行、KV 感知路由、动态分离式服务，只有当你有很多 GPU（常常是多个节点）、以垂直扩展加水平复制服务同一个模型时才有意义。

真实世界的流量无视约束。但有量之后，你可以随时间的推移调整系统，去匹配不断变化的使用性质。调优推理引擎、投机算法和模型服务器的参数，不是一次性任务。相反，通过迭代部署或动态运行时调整，你可以持续改进推理系统的性能。

找到正确的技术和配置组合，需要耐心实验。我记得一次内部黑客松，Baseten 的一位推理工程师在做代码自动补全模型，最后用手写脚本试了 77 种不同配置，才找到一个不明显的方案，让客户模型的 TPS 翻倍。

让推理优化更复杂的是：有时技术是共生的，有时是互斥的。例如，量化 KV Cache 缓解了分离式服务的瓶颈，但增大批大小会减少投机可用的算力。推理工程师的目标，永远是创造一组「一加一大于二」的平衡优化。

本章介绍推理加速的五类关键应用研究：**量化、投机、缓存、并行、分离式服务**。在每一节，特别注意每种技术的推荐使用场景，以及每种技术引入的潜在瓶颈或权衡。

## 5.1 量化（Quantization）

量化改善延迟（TTFT 和 TPS 都改善）、提高系统吞吐，并为分离式服务、投机、前缀缓存等其它优化腾出空间，让它们更有效。但量化出错时，会实质性地降低模型输出质量。

模型在训练时，权重、激活和其它组件以某种原生数值格式表示。通常是 BF16 或 FP16，尽管 8 位和 4 位原生精度在训练中正变得越来越流行。

训练后量化（post-training quantization）把模型权重和其它值从原生数值格式改成更低精度的格式。精度减半在推理两个阶段都改善性能：

- **Prefill**：算力受限的 prefill 现在跑在 FLOPS 翻倍的低精度 Tensor Core 上。
- **Decode**：内存受限的 decode 现在每个值加载一半的数据，实际上让内存带宽翻倍。

处理量化数据确实会引入开销，所以从 16 位到 8 位并不是线性地快两倍。实践中，降一级精度的量化通常给 LLM 带来 30–50% 的性能提升。

量化的难点在于它有降低模型输出质量的风险。量化有可能在驱动推理的计算中引入精度误差。

精度误差会随时间复合。考虑对 π 的不同精度做平方和立方会发生什么：

| π 精度 | π² | π³ |
|---|---|---|
| 3.14159 | 9.869588 | 31.006198 |
| 3.14 | 9.8596 | 30.959144 |
| 3 | 9 | 27 |

量化的大部分工作，都围绕着**防止精度误差**和**最小化它们对最终模型输出的影响**。

### 5.1.1 数值格式（Number Formats）

量化引入了一批新的关键术语和缩写。最需要知道的是常见数值格式：

| 名称 | 缩写 | 首个架构 |
|---|---|---|
| 64 位浮点 | FP64 | Fermi (2010) |
| 32 位浮点 | FP32 | Kepler (2012) |
| 16 位浮点 | FP16 | Pascal (2016) |
| Brain 浮点 16 | BF16 | Ampere (2020) |
| 8 位浮点 | FP8 | Hopper (2022) |
| 混合精度 FP8 | MXFP8 | Blackwell (2024) |
| 8 位整数 | INT8 | Pascal (2016) |
| 6 位浮点 | FP6 | Blackwell (2024, 实验) |
| 4 位浮点 | FP4 | Blackwell (2024) |
| 混合精度 FP4 | MXFP4 | Blackwell (2024) |
| NVIDIA FP4 | NVFP4 | Blackwell (2024, 专有) |
| 4 位整数 | INT4 | Turing (2018) |

最大的数值格式 FP64（「双精度」）只用于高精度科学计算，不用 AI 训练或推理。FP32 有时用于训练，但几乎从不用推理。FP6 截至出版时更偏实验，尽管 AMD GPU 正快速采用该格式。

剩下的 16、8、4 位精度是推理的主要格式。数值格式有：

- **精度（Precision）**：格式中表达单个值所用的位数。例如 FP16 用 16 位。
- **类型（Type）**：这些位是被解释为整数（无小数）还是浮点数（有小数）。
- **缩放因子（Scale factor）**：把值从低精度格式映射回高精度格式的乘数。

这些属性一起决定了数值格式表达推理所用值的好坏，背后有两个因素：

- **动态范围（Dynamic range）**：格式能表示的最低值与最高值之间的差。
- **粒度（Granularity）**：沿单一缩放因子被量化的参数或其它值的数量。

动态范围对无损的低精度推理至关重要。16 位能表示 65,536 个不同的值，而 8 位只能表示 256 个不同值。动态范围是这些值的分布——最小可用值与最大可用值之间的差。

动态范围解释了为什么浮点格式对推理优于整数格式。浮点格式有三个属性：

- **符号（Sign）**：一位，表示数字是正还是负。
- **指数（Exponent）**：一组位，合起来表示一个指数因子。
- **尾数（Mantissa）**：一组位，合起来表示「底数乘以二的指数次方」。

一个 E4M3 数据格式的 FP8 数，意味着它有 4 位指数、3 位尾数，剩下一位给符号。整数格式只有符号和值位。

> **图 5.1**：浮点数值格式除了符号位，还有指数位和尾数位。

浮点数中的指数给它更高的动态范围，意味着它能更好地表达非常大和非常小的数。这很重要，因为离群值在推理中很关键，而浮点数值格式在量化后能更好地表示离群值。

在浮点格式内，每个精度有多个选项，如 FP4、MXFP4、NVFP4。这些格式的差异在于**粒度**，即单一缩放因子所量化的值的数量。

量化可以应用于：

- **张量级（Tensor level）**：为整个 QKV 张量计算单一缩放因子。
- **通道级（Channel level）**：为张量内每个特征向量计算不同缩放因子。
- **块级（Block level）**：在每个特征向量内，把向量分成 N 个值的块，为每块计算缩放因子。

更细粒度的量化抹平离群值的机会更低，能保留质量。然而，更高粒度带来存储和应用缩放因子的更多开销。

MXFP8 和 MXFP4——Blackwell 支持的新数值格式——是「微缩放（microscaling）」格式，对每 32 个参数计算块级缩放因子，减少这些数值格式较低动态范围的影响。

NVFP4（NVIDIA 的 4 位格式）提供比 MX 格式更高的粒度，块大小 16，外加一个 32 位全局缩放因子，进一步对抗 4 位格式引入的质量损失。

微缩放格式的权衡是：小块缩放因子也必须存储在内存中，略微减少量化的性能收益。此外，张量和块缩放因子都需要被应用，引入一点计算开销。Blackwell GPU 通过在 Tensor Core 中应用缩放因子来抵消这一开销。

虽然本书聚焦数据中心推理工程，量化对本地和边缘推理（尤其大模型）也是关键主题。**GGUF**（存储模型的二进制格式）是在 Hugging Face 上分发高度量化模型最流行的选择，个人研究者和公司用它把 DeepSeek 等巨型模型塞进 Apple 电脑等消费级硬件。

这些量化策略通过**动态量化（dynamic quantization）**对抗质量损失：模型的某些层或组件保留原始精度，其它层量化到低至 1 位精度的整数。动态格式用「平均精度」来表示，这就是为什么你会看到微调实验室 Unsloth 流行的 1.58-bit 量化。

虽然这些动态量化是令人印象深刻的工程壮举、很适合本地推理，但生产系统的推理工程师应坚持用浮点格式——整数格式因缺乏动态范围，不适合质量敏感的负载。

相反，8 位浮点格式（FP8、MXFP8）通常是「提升性能而不牺牲质量」的甜点。FP4 有前景，尤其是引入更高粒度以提升精度的 NVFP4 格式，但 FP8 和 MXFP8 提供最大灵活性，尤其在量化 KV Cache 时。

### 5.1.2 量化方法（Quantization Approaches）

模型参数越多，对量化越不敏感，因为每个单独参数不那么重要。然而，即便对非常大的模型，谨慎量化也至关重要。

量化可以在训练期间或训练后发生：

- **量化感知训练（Quantization-aware training, QAT）**：一起训练权重和计算缩放因子，确保最终收敛的权重在给定精度下准确。
- **训练后量化（Post-training quantization, PTQ）**：通过计算缩放因子、经校准保留精度，把完成的模型权重转换成新精度。

虽然一些实验室发布用量化感知训练创建的模型（如 MXFP4 的 GPT-OSS、INT4 的 Kimi K2 Thinking），但处理开源模型的推理工程师只能做训练后量化，因为他们处理的是已完成权重。

训练后量化的一个领先工具是 **NVIDIA TensorRT Model Optimizer（ModelOpt）**，一个也支持剪枝、蒸馏和稀疏的开源库。ModelOpt 的输出兼容所有推理引擎（vLLM、SGLang、TensorRT-LLM）。

选定精度后，做训练后量化前有两个决定：

- 模型的哪些部分（权重、激活、KV Cache、注意力）应该被量化？
- 什么数值格式提供合适的动态范围和粒度？

这些决定把量化从一个二元选择变成一个围绕性能和质量的权衡谱系。

模型的不同组件对量化的敏感度不同。降低更敏感组件的精度，质量退化的风险更高。从最不敏感到最敏感：

- **权重（Weights）**：特别是线性层，对量化最不敏感。
- **激活（Activations）**：激活函数的中间输出，只对量化有点敏感。注意，激活函数本身很少被量化，因为它们只占模型权重的极小一部分。
- **KV Cache**：注意力计算缓存的值，对量化中等敏感。
- **注意力（Attention）**：模型的注意力层对量化高度敏感，尤其是 softmax 等方程。

在每个组件内，你可以对量化更有选择性。

即使在因体量大而对量化最不敏感的线性层和激活中，神经网络的输入层和输出层等早期和晚期层也可能保留原始精度，因为这些层更敏感。

量化权重和激活直接帮助性能，而 KV Cache 量化给前缀缓存和分离式服务等技术额外助推。KV Cache 是宝贵资源。量化它让推理引擎能在内存中存更多、读得更快。

然而，每个 token 的 KV Cache 被每个后续 token 使用。这意味着量化引入的精度误差会在 token 之间复合。

复合误差正是注意力层量化风险最高的原因。注意力不仅对动态范围很敏感，而且每次注意力计算都依赖每次先前注意力计算的结果。在数千 token 的序列上，这些误差迅速累积。

除了最激进的量化方案，所有方案都以原始精度运行 softmax 等函数。

> **图 5.2**：权重和激活量化风险低，KV Cache 中等，注意力高。

低精度推理的一种温和做法是：用 FP8 这种高动态范围格式——如果可能，用 MXFP8 这类微缩放格式——谨慎地量化选定的线性层、激活，常常还有 KV Cache 值。即便用这些高动态范围格式，注意力层的组件也很少被量化。

### 5.1.3 测量质量影响（Measuring Quality Impact）

生产级量化的标准是**零可感知质量损失**。量化模型后，关键是彻底测试其输出质量对比原始精度。

量化后检查模型质量有三种方法：

- **困惑度（Perplexity）**：计算量化模型的困惑度分数，与原始对比。
- **智能基准（Intelligence benchmarks）**：跑 MMLU 或 SWE-bench 等标准智能基准，与原始分数对比。
- **定制 evals**：在量化模型上跑产品特定的评估套件，与原始权重对比。

每种情况下，你都在找「与噪声无法区分」的分数差异。LLM 是非确定性的，所以分数在每次运行间略有波动。

最简单的质量检查是困惑度。困惑度不让模型生成输出，而是给模型期望的输出序列，计算模型预测这些 token 的似然。

更高的困惑度意味着模型对序列更「惊讶」——这不是一个应该预测 token 的模型所期望的。量化后，你要找的是困惑度的最小增加。

更全面的质量检查依赖公开智能基准，或者更好的是匹配你预期真实使用的领域专用 eval。在 evals 上，你要找的是质量分数的最小下降。

获得量化影响全貌的最好方式，是跑全部三种检查，并与原始模型权重做同口径对比。

记住：量化是一个尺度，而非二元决策。你可以通过量化到 FP8 而非 FP4、或量化更少组件（如仅权重量化），在更低质量损失风险下仍获得一些性能提升。

如果你在一个高度敏感的领域工作、不能冒险损失模型质量，别担心：本章其它所有技术在质量上都是**无损的**。

## 5.2 投机解码（Speculative Decoding）

LLM 推理的 decode 阶段是自回归过程，token 一次生成一个。decode 的瓶颈是内存带宽，在中低批大小下，算力在权重从内存读取时闲置。

投机解码利用这些闲置算力，试图让目标模型每次前向传播生成多个 token。如果推理引擎每次权重往返内存能生成两个、三个甚至更多 token，它每秒生成的 token 就多得多。投机解码只改善 TPS/ITL，不改善 TTFT。

投机解码有多种算法。它们共享一个共同机制：

- **投机器（speculator）**生成一个或多个草稿 token。
- **目标模型（target model）**，即你试图加速的底层模型，对这些 token 做验证，检查它们是否匹配模型本会生成的结果。
- 目标模型接受任何有效的草稿 token，并自己再生成一个 token，完成这次前向传播。

这样每次前向传播（或每次 decode 循环迭代）生成 N+1 个 token，其中 N 是接受的草稿 token 数。

生成草稿 token 不是免费的，它既要算力也要内存。然而，目标模型验证一个草稿 token 比生成一个原始 token 快得多。想象一个数独：求解很难，但检查解是否正确很容易。对目标模型而言，生成 token 就像解数独，验证草稿 token 就像检查已完成的数独。

任何投机解码策略的性能提升，取决于三个因素：

- **草稿 token 成本**：生成一个草稿 token 的时间。
- **草稿序列长度**：每次前向传播生成的草稿 token 数。
- **token 接受率**：被目标模型接受的草稿 token 百分比。

token 接受率在草稿序列早期很高，但草稿 token 在序列深处变得不那么可靠。

> **图 5.3**：投机解码，从草稿 token 生成与验证，到前缀接受及后续 token 生成。

目标是短而高百分比的序列，因为生成和验证 token 虽相对原始模型生成 token 便宜，仍有可观开销。此外，一旦单个草稿 token 被判定错误，序列中所有后续 token 也一并被拒绝。

投机解码有趣之处在于，有太多因素影响 token 接受率。最大的是**温度**——更高的温度产生更难预测的 token 分布，降低投机解码的有效性。但即便是主题这样简单的因素，也会影响接受率——如果草稿模型或投机头更擅长数学而非历史的话。

投机解码的另一个局限是：它在有闲置算力周期的低批大小下最有用。在更高批大小下，投机解码必须被动态禁用，因为算力太饱和，负担不起验证。

每种投机算法以不同方式导航这些权衡，为场景仔细实现正确的算法，能带来 TPS 的重大改进。

### 5.2.1 草稿-目标投机解码（Draft-Target Speculative Decoding）

投机解码的原始方法用两个模型：

- **草稿模型（Draft model）**：生成投机草稿 token 的额外模型。
- **目标模型（Target model）**：原始模型，现在除普通 decode 外还验证草稿 token。

配置草稿-目标投机解码时最重要的决定，是用哪个草稿模型。好的草稿模型有高 token 接受率，同时运行所需资源最少。

草稿模型通常是目标模型同族中较小的成员，因为它们共享分词器和行为。经验法则是：草稿模型参数量至少比目标模型小十倍。微调或蒸馏可以教这些小模型行为更像目标模型，从而提高 token 接受率。

草稿-目标投机解码是个好选择，当你想开箱即用地快速搭起、而不用做任何训练或微调时。

然而，其它投机算法通常性能更好。草稿-目标在所有投机解码方法中引入的开销最大。草稿模型虽小，推理引擎必须在内存中存草稿模型的权重、激活和 KV Cache，并投入算力周期给草稿模型 prefill。此外，草稿和目标模型必须协调运行以免争抢资源，尽管 TensorRT-LLM 等推理引擎处理了这种模型编排。

### 5.2.2 Medusa

Medusa 是草稿-目标投机最早的替代方案之一。Medusa 解决「运行草稿模型做投机」的复杂性和开销，方法是微调目标模型，让它在每次前向传播生成额外 token。

为 Medusa 微调模型，意味着给模型嫁接额外的解码头。LLM 的普通架构包含一个单一解码头，Medusa 则额外加两到四个头，生成顺序的草稿 token。

与草稿-目标投机一样，草稿 token 在下一次前向传播中被验证。

Medusa 在草稿 token 数和草稿 token 接受率上仍受限，今天在生产中不被广泛使用。然而，Medusa 启发了 EAGLE 等更流行的技术。

### 5.2.3 EAGLE

用现成预训练模型做草稿模型的主要问题是：Qwen 0.5B 这样的模型被设计成在廉价硬件上做好的独立 LLM，而不是在 B200 上投机草稿 token。这些草稿模型运行低效、接受率也相对低。

EAGLE 提供替代方案：一个**从零训练、专为投机构建的草稿模型**，能生成最多八个草稿 token（比 Medusa 多两倍）且接受率很高。

推理期间，LLM 以层间隐藏状态的形式积累了大量关于预测 token 的上下文。传统草稿模型无法访问这些信息。

EAGLE 是一个被训练来「接受隐藏状态为输入、生成投机 token 为输出」的草稿模型。具体说，它在一组三个隐藏状态上训练：一个来自早期层、一个来自中间层、一个来自晚期层。EAGLE 通常不到十亿参数，且给额外训练数据时扩展良好。

> **图 5.5**：EAGLE 投机模型以隐藏状态为输入，产出草稿 token 为输出。

实践中，用 TensorRT-LLM 等推理引擎使用 EAGLE 时，实现往往直接：训练后创建 EAGLE、单序列投机。

EAGLE 可以附加到与目标模型相同的模块（PyTorch 类）上，所以每次前向传播同时跑目标模型和 EAGLE 投机器的推理。这个统一流水线解决了草稿-目标解码的另一个问题——编排草稿和目标模型需要多次往返 CPU。

EAGLE 是有知识和能力训练 EAGLE 头的推理工程师通用的首选投机算法，推理引擎支持良好。和其它投机技术一样，为改善延迟而采用 EAGLE 需要减小批大小，从而降低吞吐、增加成本。

### 5.2.4 N-gram 投机与 Lookahead 解码

N-gram 投机用的机制与其它投机不同。**没有草稿模型**。

相反，推理引擎在生成 KV Cache 的同时，构建一个 **n-gram 字典**。n-gram 字典把单个起始 token 映射到一个观察到的 N token 序列（n-gram）。

> **图 5.6**：n-gram 字典把前缀匹配到可能的后续，对代码等受限语言尤其有用。

这个 n-gram 字典包含输入文本中的常见序列，在 prefill 期间首次构建。decode 期间，生成的 token 被喂进字典，任何可用的后续被选为草稿 token。在下一次前向传播中，目标模型照常验证这些草稿 token。

n-gram 投机相对 EAGLE 的优势是序列可以长得多。EAGLE 能以不错的接受率生成八个左右的草稿 token，而 n-gram 序列可以超过十个 token。

然而，只有当模型输出内容与模型输入相似时，n-gram 的接受率才高。n-gram 投机主要用于代码补全和代码修订，那里语法可预测、输出与输入紧密匹配。但在这个特定领域内，它轻松胜过 EAGLE。

与 n-gram 投机类似的方法是 **Lookahead Decoding**，它在推理期间生成 n-gram 来填充字典。Lookahead Decoding 比 n-gram 投机更通用，因为它不那么依赖高度重复的上下文，但需要额外算力来生成 n-gram。

每个投机解码算法都旨在减少生成完整输出序列所需的总前向传播次数，改善整体延迟，特别是 decode 期间每用户每秒 token 数。n-gram 投机擅长代码补全和类似任务，Lookahead Decoding 在有多余算力的系统中更通用。

## 5.3 缓存（Caching）

prefill 期间，推理引擎在输入序列上构建 KV Cache（每个 token 的 key 和 value 存储）。然后它在 decode 期间为每个 token 更新 KV Cache。由于推理是自回归的，每个新 token 的值依赖序列中每个先前 token 的值。

每个推理引擎默认按请求使用 KV Cache。没有 KV Cache，LLM 推理会慢得无法忍受，因为每个后续 token 都需要重新计算整个序列中每个先前的值。

然而，工程师可以通过**在请求之间复用 KV Cache**，而非只在每个推理序列内使用，从 KV Cache 获得更多效用。

### 5.3.1 前缀缓存与 KV Cache 复用

考虑下面两个 prompt，在大多数分词器上各四个 token，见图 5.7。

> **图 5.7**：一对四 token 序列，有两个 token 的匹配前缀。

默认情况下，推理引擎必须对每个 prompt 的全部四个 token 跑 prefill。但每个 prompt 的前几个 token——「Weather in」——在这对之间构成共享前缀。

用前缀缓存，你可以复用第一个请求的 KV Cache 来改善第二个请求的 TTFT：跳过前两个 token 的 prefill，改为读入现有 KV Cache。

当你看到按 token 付费的 API 对「缓存命中（cache hit）」输入 token 收费低于「缓存未命中（cache miss）」token 时，原因就在此——复用缓存 token 只花很少算力和时间。作为推理工程师，你可以在自己的部署上应用同样原理来降低延迟、提高吞吐（从而省钱）。

省两个 token 对 TTFT 影响不大，但前缀缓存在某些领域能跳过数千 token 的 prefill：

- **复杂系统 prompt**：Agent、面向客户的聊天机器人、RAG 脚手架、工具调用，每次调用都常有长而复杂的系统 prompt。
- **代码补全**：代码补全、代码生成及其它编程功能需要传同样数千行代码作为共享上下文。
- **文档与检索**：文档摘要、问答和检索都在用户 prompt 之前加重复上下文。
- **多轮对话**：普通对话在聊天模板中重复回放每条消息，每轮都增加前缀缓存的节省。

前缀缓存从输入序列开头一直工作到第一个非重复 token。天气例子中的第四个 token（问号）在两个输入序列间是共享的。然而，前缀在第一个非重复 token 处结束，所以第四个 token 不从缓存读。

因为前缀在第一个独特 token 处结束，你的**上下文工程（context engineering）**决定了你的 TTFT 节省。考虑对同一 prompt 的不同方法：

> **图 5.8**：一对没有前缀匹配的四 token 序列，第一个 token 不同，所以接下来三个相同也无济于事。

这里，前缀缓存没有任何节省，因为两个序列的第一个 token 就不同，即便之后每个 token 都相同。

要利用前缀缓存，确保新颖 token 在你的上下文中**尽可能靠后**。

前缀缓存是 KV Cache 复用的主导形式，因为 LLM 是自回归的。每个 token 影响每个后续 token，所以单个新颖 token 就改变了模型对序列其余部分的内部表示方式，即便这些序列在人眼看来一样。

然而，围绕其它种类的 KV Cache 复用有活跃研究，以克服这一局限。缓存 prompt 中间的任意序列，需要同时修正位置嵌入、选择性重算 KV 条目以维持输出质量。CacheBlend、LMCache 等工具支持非前缀序列，扩展了 KV Cache 复用的可能。

### 5.3.2 KV Cache 存在哪里

KV Cache 非常有价值。但 KV Cache 占用大量内存，GPU 只有有限的 VRAM。

你可以配置推理引擎为 KV Cache 分配多少内存。例如，在 TensorRT-LLM 中，你会设置：

> **图 5.9**：把空闲 GPU 内存分配给 KV Cache，是运行推理引擎时的关键配置决定。

如果你在 180 GB VRAM 的 B200 GPU 上，用 100 GB 放模型权重和缓冲，这会分配剩余 VRAM 的 80%，即 64 GB 给 KV Cache。

一旦这个分配被填满——它会很快填满——你就得开始删除已存的 KV Cache，增加未来请求缓存未命中的几率。

要给 KV Cache 更多空间，从 VRAM 卸载到附近其它存储。有四个地方可以存 KV Cache，按到 GPU 的带宽降序：

| 层级 | 内存类型 | 大致速度 | 大致大小 |
|---|---|---|---|
| G1 | 设备内存（GPU VRAM） | 每秒 TB 级 | 几十到几百 GB |
| G2 | 主机内存（CPU RAM） | 每秒几十到几百 GB | 几百 GB 到 TB |
| G3 | 本地 SSD | 每秒 5–10 GB | TB 级 |
| G4 | 网络化 SSD | 每秒 GB 级 | 几十 TB |

某些 SKU（如 GB200）配备的 CPU 和互连提供快得多的 G2 存储，使它们很适合 KV Cache 卸载。

NVIDIA Dynamo 通过 **KVBM（KV Block Manager）**提供 KV Cache 卸载支持。KVBM 提供在不同内存层级间移动 KV Cache 块的 API。一般规则是：把最常使用的块放在更高带宽内存，较少使用的块可以降级到较慢存储直到需要。

### 5.3.3 缓存感知路由

在生产环境中，你的推理服务器会有多个副本，进来的流量被分到各副本上。通常，流量基于每个副本多忙来路由。

如果你的推理服务器重度使用前缀缓存，你的路由逻辑需要更新以考虑这点。一个与聊天机器人长对话的用户、或对代码库问多个问题的用户，其请求应尽可能路由到同一个副本，这样他们能缓存命中，获得更快、更便宜的请求。

> **图 5.10**：缓存感知路由基于 KV Cache 分配流量，而非简单把请求均分到副本。

另一个选项是用 G4 网络化存储，跨副本构建全局 KV Cache。路由在这里仍然重要——有热 G1 缓存的副本会比从 G4 读的副本更快服务请求——但全局缓存确保所有副本最终能访问任何预先计算好的序列，且缓存序列在节点轮换或自动扩缩停机时不会丢失。

### 5.3.4 长上下文处理

「长上下文」有点循环定义：当序列生成的 KV Cache 大到在推理中引发问题时，它就成了「长上下文」。

取决于模型、硬件、引擎和流量，这些问题可能在 32K、64K 或 128K token 等常见阈值之后开始出现。在你的性能基准中，务必发送非常大的输入序列，测试你的推理服务对长上下文请求的表现。

基础模型实验室一直用 RoPE 等扩展技术解锁更长、更准确的上下文窗口。但支持这些升级的上下文窗口，在推理中引入新挑战。

算上 KV Cache，注意力方程随序列长度线性扩展。长序列下，注意力可能成为 VRAM 的主要消耗者——而 VRAM 正是 decode 受限于的资源。

虽然滑动窗口注意力、压缩注意力、稀疏注意力等方法在逐模型基础上提供方案，优化标准注意力算法还有通用方法：

- **FlashAttention**：一系列优化过的注意力内核，以减少对内存读写次数的方式计算注意力。
- **PagedAttention**：一种内存管理技术，把 KV Cache 存在固定大小的页中，减少碎片和重复。
- **分块预填充（Chunked Prefill）**：把大输入序列拆成块的策略，在资源允许时与 decode 一起运行，避免长序列压垮推理引擎。

但如果这些优化之后，你仍需要比单块 GPU 提供的更多 VRAM 来存 KV Cache 呢？你就需要跨多 GPU 并行化推理。

## 5.4 模型并行（Model Parallelism）

市场上每个前沿 LLM 对批量推理来说都太大、单块 GPU 装不下。GPU 变大了，模型也变大了，这个趋势没有逆转迹象。

在 FP8 下，加载十亿参数的模型权重约需 1 GB VRAM。对 DeepSeek-V3.1 这样 6710 亿参数的模型，光模型权重就会让单块 B200 GPU 立即抛内存不足（OOM）错误。

只是勉强把模型权重塞进 VRAM 还不够。在 4×B200 GPU（720 GB VRAM）上，你理论上能加载 DeepSeek 的权重。但没有任何剩余空间给 KV Cache——而 KV Cache 在权重之后常占剩余 VRAM 的 80% 或更多——四块 B200 GPU 无法以任何合理的序列长度或批大小服务 DeepSeek。

相反，服务 DeepSeek 这么大的模型的真实生产流量，需要**八块 B200 GPU 的完整节点**。你可以通过把精度、参数量和预期 KV Cache 分配相乘，估算一个模型所需的最小 GPU 数。

> **图 5.11**：算清推理需要多少 VRAM 后，向上取整到下一个可用实例大小，以确定最小 GPU 数。

许多情况下，即便对 GPT OSS 等中型模型，你也想用超过最小所需数量的 GPU，以启用更大 KV Cache、解锁更好的每用户延迟。

然而，这一切都要求推理能高效地从一块 GPU 扩展到多块。扩展并行推理的局限，是 GPU 之间的通信开销。

第 3 章详述了 GPU 之间的不同互连：节点内 NVLink 和 NVSwitch，节点间 InfiniBand。

虽然 NVLink 和 InfiniBand 提供高带宽，它们只是 VRAM 速度的一小部分。decode 受内存带宽限制，多 GPU 推理需要仔细设计以避免 GPU 间通信瓶颈。这个研究领域称为**拓扑感知并行（topology-aware parallelism）**。

推理中有三种主要的模型并行形式：

- **流水线并行（Pipeline Parallelism, PP）**：把模型的层拆分到 GPU。
- **张量并行（Tensor Parallelism, TP）**：把每层内的张量拆分到 GPU。
- **专家并行（Expert Parallelism, EP）**：把 MoE 模型的整个专家分片到不同 GPU。

每种并行形式有各自的权衡：

| 方法 | 机制 | 缺点 |
|---|---|---|
| PP | 每块 GPU 处理前向/反向传播的一个阶段 | 因逐步流水线导致延迟和利用率差，不推荐 |
| TP | 把 matmul 等计算密集运算拆分到 GPU | 需要跨 GPU 同步，不适合多节点 |
| EP | 每个专家住在一块 GPU 内，专家内推理快 | 需要 GPU 间路由以到达多个专家，更适合吞吐 |

张量并行通常是单节点内低延迟模型推理的最佳选择，专家并行改善 MoE LLM 的吞吐。流水线并行只用于多节点推理。

此外，上下文并行（Context Parallelism）等数据并行策略跨设备拆分计算。这些策略在 LLM 推理中罕见，但对视频生成至关重要（6.6 节）。

### 5.4.1 张量并行以降低延迟

张量并行应是你多 GPU 模型推理的默认策略。它既支持 Llama 405B 等稠密模型，也支持当前主导开源模型版图的 MoE 模型。

> **图 5.12**：张量并行跨 GPU 拆分权重，有效共享 VRAM 资源以快速运行大模型。

TP 的工作原理是：把模型的每一层拆开（与保持层完整的流水线并行相反），把层碎片分布到分配的 GPU 上。对每一层，从权重内存读取和执行矩阵乘法的开销在 GPU 间共享。

> **图 5.13**：对混合专家模型，每个专家用张量并行跨多 GPU 运行。

然而，每层的结果需要以 all-reduce 方式通信成单一输出，然后才能计算下一层。在有高带宽节点内 NVLink 和 NVSwitch 的节点中，这种通信开销被最小化。

提高张量并行度改善每用户 TPS（假设模型足够大、序列足够长，使通信开销不盖过更快的前向传播——对大多数前沿模型都是如此）。

### 5.4.2 专家并行以提高吞吐

专家并行把专家整齐地分到 GPU。一个有 128 个专家、以 EP8 在八块 GPU 上服务的模型，每块 GPU 承载 16 个完整专家。

> **图 5.14**：专家并行让每个专家在一块 GPU 内运行，每块 GPU 承载多个专家。

EP 改善总系统吞吐，让推理更可扩展、更便宜。各个专家分别处理 token，每个 token 耗时一样，但系统整体能处理更多同时的 token。

许多部署混合使用 TP 和 EP 以获得两种收益。

> **图 5.15**：这个部署对注意力用 TP、对稀疏 MoE 层用 EP。

专家并行需要的 GPU 间通信比张量并行少。**专家路由器（Expert Router）**——决定每个 token 激活哪些专家——被复制到每块 GPU 上，因为它是模型相对小的组件。GPU 间通信对在专家之间传 token 是必要的，但与 TP 不同，它不需要收集每层的结果。

由于这种更低的通信开销，EP 能很好地扩展到多节点部署和互连带宽有限的系统。

### 5.4.3 多节点推理

如果你以高精度服务一个超大模型、支持数百万 token 的输入序列、或只是想尽可能快地跑推理，你可能需要超过八块 GPU。

GPU 被设计为跨节点协同工作，多节点训练多年来一直是开发前沿模型的标准。但多节点推理引入新挑战：

- **基础设施**：如何可靠地配给两个或更多互连的 GPU 节点，并跨云提供商构建抽象（第 7 章）？
- **并行**：如何通过比 NVLink 慢得多的 InfiniBand 有效通信？

> **图 5.16**：InfiniBand 通过高带宽节点间互连，实现超过八块 GPU 的多节点推理。

InfiniBand 给拓扑感知并行引入了新难题。张量并行通常需要太多跨 GPU 通信，不适合多节点推理。相反，你有两个在 InfiniBand 上表现良好的选项：

- 对稠密模型：每个节点内用张量并行，节点间用流水线并行（如 TP8PP2）。
- 对 MoE 模型：你也可以试专家并行（如 EP16），因为它比张量并行通信开销更低。

对 MoE 模型，TP8PP2 通常提供更低每用户延迟，EP16 则产生更高整体系统吞吐。

除非你的模型和 KV Cache 大到必须多节点推理，否则这可能不是对额外硬件的最佳利用。你往往最好用额外节点做跨副本水平扩展，或做分离式服务。

## 5.5 分离式服务（Disaggregation）

分离式服务结合了推理工程的三个重要思想：

- **Prefill 是算力受限过程**，决定你的 TTFT；**decode 是内存受限过程**，决定你的 TPS。
- **专业化提升性能**，从内核选择到推理引擎参数调优无不如此。
- 如果能避免低带宽互连的瓶颈，你可以有效跨多 GPU 甚至多节点并行化模型服务。

当 prefill 和 decode 在重流量下跑在同一节点，它们互相干扰的几率更高。理想情况下，prefill 用更多算力资源，decode 用更多内存，二者能高效共存。然而，更大批次和更多计算密集优化下，prefill 和 decode 开始争夺资源。

### 5.5.1 分离式服务如何工作

分离式服务（disaggregation，即 disaggregated serving）是把 prefill 和 decode 分离到不同 GPU 或节点上的不同引擎的想法。

分离式服务把 LLM 推理变成一个三步过程：

- **Prefill 引擎**接受输入序列，生成 KV Cache，同时计算第一个 token。
- **Prefill 引擎**通过硬件互连把 KV Cache 发给 decode 引擎。
- **Decode 引擎**计算所有后续 token。

在**条件分离式（conditional disaggregation）**中，请求先发到 decode 引擎，它检查输入序列是否已缓存、或是否短到能本地处理：

> **图 5.17**：分离式服务分配 prefill worker 生成首 token、decode worker 生成后续 token。

- 如果是，decode 引擎本地处理 prefill，跳过分离式服务。
- 如果不是，decode 引擎把请求转给 prefill 引擎做分离式服务。

条件分离式对真实流量更好。

分离式服务的另一个好处是：有了分开的 prefill 和 decode 引擎，你可以单独优化每个引擎，以及系统整体。例如，算力受限的 prefill 引擎比内存受限的 decode 引擎需要更低的 TP。

### 5.5.2 何时用分离式服务

分离式服务非常强大，但需要多 GPU 和额外工程工作。你应仅在以下情况使用分离式服务：

- 你服务的流量很大，起步约每天一亿到十亿 token（取决于模型大小）。
- 你服务的模型较大，至少一千亿参数。
- 你的流量偏 prefill 密集，输入序列长。

如果第 1 或第 2 点不成立，你很可能在花额外硬件的钱换最小性能收益。如果第 3 点不成立，你最好用额外 GPU 水平扩展副本，因为对短序列或前缀缓存命中，decode 引擎会更高效。

分离式服务的一个好用例：在代码编辑器中服务前沿 LLM，许多开发者同时传入大而多样的代码块作为上下文。海量 token、大部分是 prefill、在万亿参数 LLM 上——这是分离式服务的教科书负载。

### 5.5.3 用 NVIDIA Dynamo 做动态分离式服务

Dynamo 为分离式服务提供生产级支持，能灵活处理异质的真实流量。

Dynamo 提供开发者工具和预构建优化来启用分离式服务：

- 一个 **prefill 队列**，在所有 prefill 引擎饱和时持有请求。
- 对**条件分离式**的稳健支持，基于可配置的「前缀缓存后 ISL」和「prefill 队列大小」阈值做 prefill 路由。
- 基于 NIXL 的从 prefill 到 decode 引擎的高效 KV 传输，带一个内核在引擎有不同 TP 配置时转置 KV 块布局。

综合起来，这些特性实现**动态分离式服务**：prefill 和 decode 引擎的数量在运行时可配置，可随时间的推移调整以匹配进来的流量变化。

分离式服务不一定要 prefill 与 decode 引擎一对一。虽然用单个 prefill 引擎和单个 decode 引擎解释分离式服务很简单，真实系统每种都有多个。

prefill 和 decode 引擎的数量写作 **xPyD**，例如 5P3D 意味着五个 prefill 引擎和三个 decode 引擎协同服务一个模型部署。

随着系统变得更复杂，更多潜在瓶颈出现。分离式服务下，新瓶颈是 **prefill 队列大小**。重要的是别让队列太长：既给 decode 引擎的本地 prefill 设合理阈值，也在运行时重配 xPyD 以在需要时给 prefill 分配更多资源。

分离式服务的另一个潜在瓶颈是：高负载下 decode 引擎的 KV Cache 耗尽。通过量化和 KV Cache 卸载来提高 KV Cache 可用性。
