# 第 7 章 · 生产（Production）

> Inference Engineering — Philip Kiely · Chapter 7

推理工程的目的，是让生成式 AI 模型更快、更便宜、更可靠地运行，这反过来让你能构建更好的产品。

这个承诺只有在你的推理工程工作进入生产、并随成功 AI 产品产生的超高速增长和病毒式激增而扩展时，才会兑现。

当你扩展生产流量时，你的假设会被严格检验。从序列形状到流量模式，再到用户决定聊什么话题，一切都影响你在生产中观察到的性能。而维护安全、稳健的基础设施，与在 GPU 上优化模型推理是完全不同的技能组合。

无论单个实例服务模型多快多高效，只要有足够流量，服务就会被压垮。那不是 PyTorch 问题，也不是 CUDA 问题，而是**基础设施问题**，需要不同的思维和不同的技术。

生产扩展引入了新的复杂性：在哪里、如何获得 GPU，如何均衡地跨 GPU 分配流量，以及如何防止宕机。此外，从「按每百万 token 付费」转向「直接为基础设施付费」，成本核算变得混乱。

生产中的延迟不只来自 prefill 和 decode。你需要端到端评估系统，在你能拥有或影响客户端代码的情况下，消除服务器、网络、甚至客户端的低效。

本章介绍在低延迟、高吞吐生产中扩展推理的关键考量。最后，我会邀请你试试 Baseten 来部署关键任务级推理负载。

## 7.1 容器化（Containerization）

容器化是把应用与其依赖打包在一起、以标准化生产部署的实践。容器把程序变成可在任何地方运行的打包产物——再也不会有「在我机器上能跑」。

容器是轻量的，因为它们共享底层主机操作系统内核（在这个语境中，kernel 指 Linux 内核，不是 CUDA 内核）。这让容器很适合打包推理服务。

对大多数开发者，容器化就是 Docker 的同义词。处理容器会引入更具体的术语：

- **容器（Container）**：隔离应用及其依赖的活跃运行环境。
- **镜像（Image）**：包含运行某软件所需一切的可执行包。
- **Dockerfile**：人类可读的文件，带明确指定、机器可解释的镜像创建指令。
- **仓库（Registry）**：管理、存储、共享和分发镜像的中央存储库。

NVIDIA、几个云提供商和 Docker 自己都运营容器仓库。AI 领域流行的仓库是 **Docker Hub**——Docker Hub 之于镜像，就像 Hugging Face 之于模型权重、PyPi 之于 Python 包。

Docker 容器由**层（layers）**组成。你可以取一个预配置的基础镜像，在其上叠加额外层做进一步文件系统更改。

层有三种类型：

- **基础镜像（Base image）**：要么是 Ubuntu 等操作系统发行版，要么是从仓库取的更复杂镜像。基础镜像本身由多层组成。
- **额外层（Additional layers）**：文件系统更改，包括依赖、应用代码和配置文件，由 Dockerfile 指令指定。
- **容器层（Container layer）**：运行时创建的薄而短暂的层。对运行中容器的任何更改（创建、更新、删除文件）都写到此层，容器终止时丢失。

> **图 7.1**：Docker 容器由层组成，从基础镜像到短暂、可写的顶层。

vLLM、SGLang 等推理引擎为活跃版本提供官方基础镜像。通常最好从这些经过验证的镜像开始，而非从零自己构建。

### 7.1.1 依赖管理

推理的依赖链又长又脆弱。搞出一个能用的构建很难，这使容器化在「破坏性更改太常见」的生态中，对保留「已知良好构建」至关重要。

镜像是为特定 GPU 架构和模型构建的。容器包含许多运行时组件：

- **CUDA 工具包版本**：与栈其余部分兼容的 CUDA、cuDNN、驱动的具体版本。
- **Python 包**：torch、transformers、diffusers 等依赖。
- **推理引擎**：所用 vLLM、SGLang、TensorRT-LLM 或其它推理引擎的版本。
- **系统包**：ffmpeg 等 Linux 包，处理音频、图像或视频模型时尤其常见。

像背包客一样，你要轻装。为推理构建的镜像常有好几 GB。为快速部署和高效运行，只包含严格必要的依赖。

另一个最佳实践是**锁定版本（pinning versions）**。锁定依赖树让系统运行时行为在不同环境间一致，并能以同样结果重复构建镜像。精确指定每个依赖应包含在镜像中的版本。

> **图 7.2**：依赖应锁定到精确版本，以防未来更改破坏推理容器。

uv、poetry、pip 等工具会在构建镜像时标记任何版本不兼容并抛错。锁定版本后，镜像一旦成功构建一次，就会始终把依赖解析到相同版本，保护你免受破坏性更改。

处理新发布模型时，破坏性更改尤其常见。当 DeepSeek 等模型的新版本公布时，整个推理生态都在竞相提供第零天支持。

为全新模型构建镜像时，推理工程师常依赖 nightly 构建或其它开发者预发布版本，而非稳定版本。这些早期版本更易出 bug，常常需要在模型发布后的几天到几周内，在稳定版本上重建。

### 7.1.2 NIM

NVIDIA 推理微服务（NIM, NVIDIA Inference Microservices）是流行开源模型的预构建 Docker 容器。

容器让推理服务实现可移植。NVIDIA 创建了两类 NIM：

- **多 LLM NIM（Multi-LLM NIM）**：在支持的 GPU 架构上运行一族模型的灵活容器。
- **LLM 专用 NIM（LLM-specific NIM）**：为特定模型、在特定 GPU 上配置为最大性能的优化引擎。

NIM 可用于各种常见的模型、GPU 架构、GPU 数和配置组合。

NIM 和任何其它容器一样。你可以用 NIM 作为构建起点、学习用的参考架构，或开箱即用的推理服务。

然而，如果你要最大控制力而非「替你做好」的配置，通常最好从更少预设的基础镜像自己构建容器，而非改编 NIM。

## 7.2 自动扩缩（Autoscaling）

自动扩缩的目标是：确保你始终有足够资源服务所有进来的请求，同时维持延迟 SLA，且不把钱浪费在闲置 GPU 上。

> **图 7.3**：没有自动扩缩，推理系统在流量低谷浪费资源、在流量高峰错过 SLA。

> **图 7.4**：强大的推理自动扩缩系统让资源匹配需求。

自动扩缩系统用 **Kubernetes**（开源容器编排系统），配一个集群级系统来配给和回收计算。Kubernetes 能跑一个模型容器的多个副本，各自在自己的实例上。实例包括容器所需的 GPU 和其它硬件资源。

Kubernetes 把一组硬件资源组合成一个集群。集群有两类组件：

- **控制面（Control plane）**：做路由和扩缩决策。
- **工作面（Worker plane）**：跑实际的容器化应用。

> **图 7.5**：Kubernetes 集群有单一控制面，编排多个 worker。

一个 Kubernetes 集群能跑多个模型的多个副本。但你如何决定每个模型跑多少副本？除非你的流量异常稳定，否则可能没有一个完美匹配你需求的副本数。

自动扩缩是在集群内动态调整分配给给定模型的副本数的实践。做自动扩缩决策有两种方式：

- **利用率（Utilization）**：基于内存使用或算力使用等 GPU 利用率信号扩缩。
- **流量（Traffic）**：基于系统中正在处理的请求数扩缩。

利用率和流量不总是一致。例如，在 LLM prefill 中，几个带数十万未缓存输入 token 的请求，可能比许多高缓存命中率的小请求产生高得多的利用率。

基于流量的扩缩决策可以主动做出，而利用率是滞后指标。两者结合使用，让系统资源匹配需求。

设计基于流量的自动扩缩系统时，你要配置五个因素：

- **最小副本数（Min replicas）**：无论流量如何，保持运行的最小副本数是多少？
- **最大副本数（Max replicas）**：流量高时，你能分配的最大副本数是多少？
- **扩缩窗口（Autoscaling window）**：你用来测量流量、做扩缩决策的滑动时间窗多长？
- **缩容延迟（Scale down delay）**：建议缩容后，你要等多久以防又出现流量高峰？
- **并发目标（Concurrency target）**：每个副本一次能处理多少请求？

精确配置决定自动扩缩系统在「维持延迟 SLA 而不浪费资源」上做得多好。例如，增大缩容延迟能防止尖峰流量下的过早缩容，但可能在流量真正冷却后导致不必要开支。

### 7.2.1 并发与批大小

要正确运行基于流量的自动扩缩系统，你需要强理解每个实例能处理多少并发流量。

大多数模型推理服务通过批处理一次处理多个请求。批处理有几种方法：

- **静态批处理（Static batching）**：服务器等到批次填满才开始推理。
- **动态批处理（Dynamic batching）**：服务器等到批次填满或配置的时间过了才开始推理。
- **连续批处理（Continuous batching）**：服务器持续跑推理，在槽位可用时换入请求。

vLLM、SGLang、TensorRT-LLM 等推理引擎实现稳健的连续批处理（TensorRT-LLM 称之为 in-flight batching），在 token 级别批处理请求。这相对静态批处理最小化了延迟。

> **图 7.6**：静态批处理设固定批大小，等批次填满才开始推理，导致早期请求长时间等待。

> **图 7.7**：动态批处理加一个截止时间，过了就运行批次，无论是否填满。

> **图 7.8**：连续批处理在 token 级运作，旧请求完成时换入新请求。

批大小在延迟和吞吐之间权衡。增大批大小产生更多总吞吐，但每个用户的延迟变差。跨多个批大小测试性能，为你的模型、实例、延迟目标和预算找到合适的。

这在自动扩缩配置层通过并发目标控制，在副本层通过批大小控制，二者应匹配。

一旦每个活跃副本达到最大并发，自动扩缩系统就知道要启动更多副本。如果有足够副本在跑半满的批次，就该缩回去了。

### 7.2.2 冷启动

**冷启动（cold start）**是启动模型新副本所需的时间。

自动扩缩系统的整体性能取决于其冷启动速度。如果你不能快速启动副本，就很难自信地缩容，导致过度配给。

影响冷启动时间的几个因素：

- **GPU 采购**：你能多快给集群添加必要 GPU 并分配给模型？
- **镜像加载**：你能多快把容器镜像加载到新采购的实例？
- **模型加载**：你能多快把模型权重加载进容器？
- **引擎启动**：你能多快启动推理引擎，包括任何编译时间？

每个因素都需要单独优化。

> **图 7.9**：冷启动过程的每一步都增加总时间线。

除非你有一个在模型间灵活调度的暖节点池，GPU 采购速度主要取决于你的云提供商。7.3.1 节覆盖采购 GPU，节点启动时间是合同里可谈判的因素之一。

然而，工程师在加载镜像和权重、启动容器和引擎上能做很多。

加载镜像和模型权重，取决于你能多快把 GB 级（常常几百 GB）数据写进实例。有两种更快加载镜像和权重的方法：让它们更小，或获得更多带宽。

只包含必要步骤和依赖让镜像更小、构建容器更快，而量化模型权重的额外好处是冷启动时加载更快。

对小模型，策略曾经是把权重烘焙进镜像，以简化缓存和加载。但现在大多数模型有几百亿到几千亿参数，权重远大于镜像，最好分开加载。

你从哪里加载权重，对带宽影响巨大。如果你从 Hugging Face 等第三方加载，受限于他们的出口速度。把权重存在 S3 桶里会引入网络延迟和数据传输成本。

加载数千亿参数模型，你需要每秒 GB 级的带宽。获得这个的最佳方式，是在同一数据中心内、物理上靠近 GPU 实例的缓存源，通过节点内网络加载。

vLLM、SGLang 等推理引擎启动快。但 TensorRT-LLM 等引擎和 PyTorch 优化模型有编译步骤，针对特定硬件资源构建模型推理引擎。这些编译常要几分钟。

这些情况下，缓存构建好的引擎能大幅改善冷启动时间。TensorRT-LLM 和 PyTorch 都有镜像缓存机制使之可行，尽管你始终需要把缓存引擎加载到 GPU 类型、CUDA 版本、软件依赖与构建引擎环境完全一致的实例中，它才能正常运行。

### 7.2.3 路由、负载均衡与排队

一旦多个副本上线，系统需要决定把哪些请求发到哪些副本。有两类组件做这些决定：

- **路由器（Routers）**：在请求级工作，决定发送给定请求的理想位置。路由器回答「这个请求该去哪？」
- **负载均衡器（Load balancers）**：在系统级工作，在多个选项间均衡请求。负载均衡器回答「这个请求能去哪？」

在复杂系统中，不只有一个路由器和一个负载均衡器。路由贯穿整个栈，负载均衡器在关键点注入，以保持系统级性能稳定。

总的来说，你要跨副本均分负载。然而，路由和负载均衡不像说「我有 3 个副本、12 个请求，那就每个副本放 4 个请求」那么简单。

每个请求可能有不同数量的输入 token。如果大多数请求有 100 输入 token，一个 10,000 的请求就会让简单系统失衡。有些请求也由特定副本更好处理。例子包括：

- **KV Cache 感知路由**：把请求定向到 KV Cache 中已有匹配前缀的副本。
- **LoRA 感知路由**：把请求定向到内存中已有所需 LoRA 微调权重的副本。

智能请求路由用推理引擎和 NVIDIA Dynamo 等编排器的信息，基于序列长度、前缀和 LoRA 需求路由请求。

负载均衡和路由还不够。当自动扩缩系统收到超出处理能力的流量时，它需要一种方式在扩展更多资源、或等待现有资源可用时持有请求。

**队列（queue）**是处理这种情况的基础设施原语。标准队列是多余请求的先进先出系统，尽管你可以做更复杂的实现，如优先级队列——例如高流量场景下让付费用户优先于免费用户。

新副本上线时，确保队列能看到它们、请求不继续等待现有副本。每个新副本一旦活跃，应立即被分配最多到其并发限制的排队流量。

### 7.2.4 缩放到零

高级自动扩缩系统实现**缩放到零（scale to zero）**机制：如果没流量，系统能缩到零活跃副本，收到流量时自动扩起来。

缩放到零依赖两个前提：

- **快速冷启动**：因为用户可能在线等待，冷启动必须尽可能快。
- **稳健排队**：系统需要能持有进来的请求，直到副本上线。

即便有这些能力，缩放到零也不适合所有负载。

缩放到零很适合开发阶段（测试是突发性的、首个请求的延迟不重要）。生产上，缩放到零对只周期性收到流量的应用有用，比如只在一个国家工作时段被访问的 agent，或为每日批量处理任务设计的离线系统。

然而，如果你靠缩放到零来给「收到零星、非计划流量的延迟敏感应用」压低成本，这可能是你的 AI 应用还没准备好专用基础设施的信号，应该用按 token 付费 API，直到达到更大规模。

### 7.2.5 独立组件扩缩

AI 应用越来越多地构建在多模型、多阶段的**复合 AI 负载（compound AI workloads）**上，推理工程师需要协调多步来满足单个请求。

这些步骤可能有不同的硬件需求。语音活动检测模型比它切数据的转写模型需要弱得多的 GPU，而处理转写的 LLM 可能需要一个多 GPU 的完整节点。流水线中每步的扩缩参数也不同。

> **图 7.10**：独立组件扩缩给每个模型合适的资源和单独扩缩。

对这些流水线，你需要分解自动扩缩决策，逐步单独扩缩，为每步配置合适的资源，避免瓶颈和过度配给。

然而，流水线中每个模型应跑在同一集群。如果集群内发消息要 10 毫秒、集群间要 50 毫秒，那 40 毫秒的差异在 5 步流水线上，就是一秒延迟 SLA 的 20%。

## 7.3 多云容量管理

单集群内的自动扩缩到某一点为止是有效的。但服务全球用户的高量部署需要分布在世界各地的数千 GPU。

把多云推理构建成跨不同云提供商的孤岛计算集合，是很直接的。但在这些设置里，无法流畅地使用云间计算，跨云移动负载是乏味、易错的过程。

真正的多云推理需要构建一个多区域、多提供商的**装箱工具（bin packing tool）**，把不同的计算池视为彼此可替换。和单集群内的 Kubernetes 一样，多云容量管理必须采取全局视角，实现自愈和全局调度。

> **图 7.11**：多云方法把控制面和工作面的思想扩展到多集群、多区域系统。

运行真正的多云推理解锁：

- **容量**：汇集多提供商容量，获得更多、更灵活的 GPU 访问。
- **冗余**：跨提供商拆分推理，抵御宕机。
- **延迟**：把推理跑到离终端用户近的地方，减少网络延迟开销。
- **合规**：在符合数据主权和其它监管要求的地方跑推理。

从一个云的一个集群扩展到许多云的许多集群，需要一个新的协调层。多云架构包含：

- **控制面（Control plane）**：处理模型部署和全局扩缩决策，接收实时事件流。
- **工作面（Workload planes）**：处理直接推理流量和集群内扩缩决策，上报利用率和需求。

这种职责分离确保单个工作面能独立服务流量。如果控制面或任何给定工作面出问题，其它负载应不受影响。

### 7.3.1 GPU 采购

有不少公司做提供 GPU 访问的生意。三种主要类型是：

- **超大规模云（Hyperscalers）**：AWS、GCP 等大型云提供商。
- **新云（Neoclouds）**：Coreweave、Nebius 等聚焦 GPU 的云。
- **转售商（Resellers）**：SF Compute Company 等二级市场。

这个领域的玩家在容量、可用性和可靠性上各不相同。你通常为超大规模云付溢价，跨所有提供商，成本与「可用性 SLA、支持、区域可用性、实例配置、集群大小」等因素之间有权衡。

第一个挑战是**确保容量**。常常很难拿到你需要的 GPU，尤其是最新硬件。大集群也很难拿到，相对少的玩家提供数百节点的块。

许多云提供商把大部分紧俏 GPU 以长期预留分给最大客户。你可能需要跨多个云提供商，才能在正确的区域拿到你需要的 GPU。

云 GPU 可通过三种机制采购：

- **预留（Reserved）**：数百或数千 GPU 的块，按月或年以折扣价预留。
- **按需（On-demand）**：单个实例在给定配额内按需可用，每小时成本相对高。
- **竞价（Spot）**：折扣的按需实例，可在约定的通知期（常几分钟）内被抢占。

大规模推理通常混合 GPU 来源：低成本预留实例打底，按需和竞价混合应对流量高峰。这些 GPU 分布在全球多个集群，靠近终端用户。

### 7.3.2 地理感知负载均衡

成功的 AI 应用在世界各地都有用户。就像单个集群有负载均衡器确保集群内每块 GPU 收到合适流量，多集群系统需要一个**全局负载均衡器**。

你不想要用户请求在某队列里干等，而别处有闲置容量；但你也不想养成把新加坡的请求发到旧金山服务器的习惯。

经验法则：请求穿过一个时区要 5 毫秒。所以，从纽约发数据到旧金山单程要 15 毫秒。鉴于延迟预算如此之小，把负载跑到离终端用户尽可能近的地方很重要。

### 7.3.3 为可靠性构建

GPU 在生产中的高故障率是出了名的。每个做过大规模训练跑的工程师都知道，要为硬件故障的必然性做预案。

例如，在 Llama 3 论文中，Grattafiori 及同事揭示：在 54 天内运行 16,000 块 GPU，Llama 团队经历了 419 次意外中断，主要因硬件故障。这大约是每 50,000 GPU-小时一次故障。

50,000 小时听起来很长，但一个八块 GPU 的节点跑一整年推理，就是 70,000+ GPU-小时。推理工程师应预期硬件故障。

> **图 7.12**：训练 Llama 3 时的故障根因，改编自「The Llama 3 Herd of Models」（Grattafiori et al., 2024）。

GPU 健康是节点级关切。单块 GPU 故障时，节点上其它 GPU 常接着故障，或需下线维护。主动记录故障、隔离节点（cordoning）、轮换 pod，保持单个集群健康。

GPU 故障不是唯一能搞垮推理的。云提供商有计划的维护和自己的非计划宕机。基础设施每一层都必须加固以提供高可靠性。

多云推理带来两种高可靠性新方法：

- **双活（Active-active）**：高可用姿态，多个区域或集群同时活跃服务实时流量。任一面故障，流量在其它面无缝继续。
- **主备（Active-passive）**：故障切换姿态，一个「热备」集群或区域保持就绪但闲置。活跃面故障时，流量切到备面。

当单个集群、区域或云提供商宕机时，无缝切换到另一个工作面，保持高可靠性和低延迟。

### 7.3.4 安全与合规

二十多年来，云基础设施一直是安全和合规部门的热门话题。要让 AI 模型驱动关键任务应用，推理必须既安全又合规。

安全和合规对话通常围绕三个领域：

- **用户数据**：安全和合规部门想确保所有数据（包括用户输入和模型输出）受到保护。
- **模型权重**：对有微调或专有模型的公司，权重是无价的商业机密。
- **基础设施**：GPU 本身和对智能的访问，都是被滥用的目标。

改善安全最容易的决定之一，是干脆**不存储用户输入或模型输出**。这可能做不到——你可能有日志要求、或用户协议要求保留使用数据用于未来模型训练——但如果你不需要保留用户数据，就能减少攻击面。

保护 AI 推理负载和相关数据，与保护任何其它容器化负载类似。数据加密、容器安全、网络和访问控制、负载隔离，都经大量第三方渗透测试验证，仍是黄金标准。

越来越多地，推理工程师需要支持在受监管行业和合规密集区域运行的应用。多云基础设施有帮助的一点是：为了让你的应用符合 SOC 2 Type II 等认证或 HIPAA 等法规，你的提供商通常也必须合规。这种情况下，能把负载移到合规提供商是很有用的。

多集群基础设施的另一个好处，是跨多区域运行一个模型。某些行业和国家有数据驻留要求：来自其国家的用户数据不能在不同国家的服务器上处理。

例如，在靠近多伦多的提供商有一个集群、靠近纽约的另一个提供商有一个集群，让你能把加拿大数据留在加拿大、美国数据留在美国，同时给整个地理区域的用户最小延迟开销。

## 7.4 测试与部署

除了配置推理引擎时做的副本级测试和基准，部署前端到端测试系统也很重要。

测试推理有几种策略：

- **手动测试**：写脚本（或点按钮）给推理服务发合成流量。
- **负载测试**：自动发大量流量，测试系统扩展和维持性能的能力。
- **影子流量**：复制实时流量到测试部署，在真实条件下测量性能。

测试推理服务很贵。配置测试、测量结果要工程时间，为测试流量跑推理要 GPU。在某种程度上，这只是做生意的成本，但要仔细想如何最小化测试开支。例如，影子流量测试可以从复制生产流量的随机样本开始，接着做较短时长的负载测试。

测试时，记住 AI 产品使用通常在日周期和周周期上波动。

一旦你对更新后推理系统的性能和稳定性有信心，就该部署到生产了。

### 7.4.1 零停机部署

推理工程师用高可用部署策略避免停机。

传统高可用设计是**蓝绿部署（blue-green deployment）**。这个设置里有两个相同环境：原始蓝部署，和运行更新服务的新绿部署。绿环境就绪后，全部流量从蓝切到绿，蓝环境保持就绪以便出问题时回滚。

然而，蓝绿不太适合大规模推理负载，原因与让大规模测试困难的 GPU 容量和成本问题相同。如果蓝部署用 100 块 GPU，绿部署在切流量前还需要另 100 块 GPU。

相反，推理工程师可用**金丝雀部署（canary deployment）**以更低 GPU 开销获得类似收益。灵感来自煤矿里用来检测瓦斯的金丝雀，金丝雀部署在影响大量用户前抓住错误。

> **图 7.13**：迭代地把流量切到新部署，防止推理服务更新期间的多种问题。

金丝雀部署是四步过程：

- 构建推理服务的新部署，准备处理进来的请求。
- 把一小部分进来的实时流量导向新服务。
- 监控新服务，确保它正确处理流量。有问题就回滚。
- 逐步增加流量，同时监控问题，直到新部署处理 100% 流量。

这些金丝雀部署可以快速推出，只用几分钟流量爬坡，或缓慢爬坡以确保每阶段稳定。配合自动扩缩，金丝雀部署在规模化时不会太增加成本，因为减少生产系统流量会让它缩掉一些副本。

配合自动扩缩，新部署在无流量时默认最小副本数。整个金丝雀部署过程中，确保新部署有足够活跃副本来正确处理请求。否则，用户会看到延迟尖峰，因为他们的请求在自动扩缩完成前排队。

### 7.4.2 成本估算

从公共 API 消费 token 转向在专用 GPU 上自己做推理，需要改变你对成本的思考方式。

公共 API 上的成本很简单：每百万 token 价格乘以你用的 token 数。有几个变量——输入 token 的缓存命中 vs 未命中、高量用户的折扣——但成本仍是使用的线性函数。

投资时间和精力做推理工程的动机之一，是掌控你的单位经济性、摆脱按 token 定价。但这是艰难的思维转变。

专用推理的福与祸，在于成本现在是许多变量的函数。这好，因为它给你控制力，但也让估算困难。影响成本的因素包括：

- **批大小**：部署是为低批大小的延迟优化，还是高批大小的吞吐优化？
- **流量模式**：流量是持续打满活跃 GPU，还是容量闲置？
- **序列长度**：请求平均和离群情况下有多少输入和输出 token？

鉴于这种复杂度以及输入输出 token 成本差异，通常更有效的是把 token 价格换算成总成本、与专用对比，而非从 GPU 支出反推每 token 价格。

> **图 7.14**：估算产品使用按 token API 总成本的方程。

> **图 7.15**：估算产品使用专用部署总成本的方程。

成本估算应使用长的时间范围，理想至少一周，以平滑使用波动。

专用部署要考虑的另一个因素是：构建和维护推理系统所花工程时间的成本。这项投资虽以提升可靠性、安全性和控制力证明合理，也应加到 GPU 成本上，形成推理总拥有成本（TCO）的完整图景。

### 7.4.3 可观测性

推理是关键任务，所以必须像应用其它关键任务组件一样监控，在正确的抽象层级构建告警、日志和可观测性。

第一个问题是监控什么。推理可观测性包括测量：

- **总量**：模型部署收到的请求数。
- **请求和响应大小**：正在处理请求的输入和输出序列长度。
- **响应码**：模型服务器发出的 2XX、4XX、5XX 响应码计数。
- **延迟**：首 token 时间、每秒 token 数、端到端延迟等指标，按 P50、P90、P99。
- **副本数**：活跃服务流量的实例数，以及正在启动的实例数（若有）。
- **利用率**：CPU、主机内存、GPU、GPU 内存的利用率。
- **队列深度**：异步流量系统中，入队等待处理的请求数。

这些指标相互依赖。延迟尖峰可能来自请求量，也可能来自长输入序列。一起看这些指标，推理工程师不仅能理解发生了什么，还能理解为什么。

出错时，推理工程师需要信息来修复问题。日志——服务器日志和显示推理服务更改的审计日志——实时交付这些信息。

可观测性不能孤立。为推理构建可观测性时，要深度集成进现有可观测性和告警工具——Grafana、Datadog、PagerDuty、Sentry——把推理信息放进应用其余部分的语境中。

## 7.5 客户端代码

推理工程借鉴许多技术，从 CUDA 到 Kubernetes。但优化延迟、为规模构建时，有一个常被忽视的关键领域：**客户端代码**。

调用推理服务有两端：

- **客户端（Client）**：给推理引擎发请求的浏览器、agent 或应用。
- **服务器（Server）**：处理客户端请求、返回模型结果的推理服务。

客户端代码的行业标准是 **OpenAI SDK**，它除 OpenAI 自己的模型外，还支持广泛的兼容提供商。LangChain、Vercel AI SDK、LiteLLM、LlamaIndex 以及几十个流行 AI 工程框架和库也可作客户端。

无论你用现有库还是自己代码，都有延迟开销或吞吐瓶颈的可能。对实时应用，你可能需要 HTTP 之外的协议，如 WebSocket，来交付持续连接。

> **图 7.16**：服务器端推理时间只是给定请求端到端延迟的一小部分。

### 7.5.1 客户端延迟开销

取决于客户端的网络连接和所用协议，客户端与服务器建立会话要几十毫秒。

在一个 P95 端到端延迟 SLA 为 300 毫秒的高性能系统中，TLS 握手在推理开始前就至少吃掉延迟预算的 10%。同一客户端的未来请求应通过复用现有会话来省时间。

会话复用绝不是新想法，OpenAI SDK 等工具在底层静默提供。然而，为非常规模态构建自己的客户端时，遵循会话复用等最佳实践。

### 7.5.2 异步推理

有些系统为吞吐而非延迟而建。批量文档处理、语料嵌入等用例对延迟不敏感，所以切到异步任务是合理的。

异步请求是执行推理的「发射后不管」方式。

普通同步推理请求有超时（通常几分钟），超时后请求失败。异步任务通过立即确认请求、稍后把异步任务结果返回到原始请求提供的 webhook 来解决。

异步任务仍有时间限制，但这些请求通常以小时而非分钟计。配合强大的服务器端排队，异步请求让高吞吐、延迟不敏感的系统更稳健、更高效。

### 7.5.3 流式与协议支持

流式让应用感觉即时。对语言模型，通过 HTTP 流式输出文本就够了。但对其它模态，尤其是实时语音和视频，输入和输出流都需要能携带更多数据。

> **图 7.17**：一次性 HTTP 请求和响应对文本聊天等用例合适，但对持续流式不合适。

两种最常见的双向流式客户端-服务器连接协议是：

- **WebSocket**：用于不需要强 schema 约束的流式用例。
- **gRPC**：用于定义良好的服务间通信。

WebSocket 对传输非结构化、实时数据（如音频）很有用，接收请求的服务器能解析它并下游处理。用 WebSocket，一个服务器最多支持固定、开发者可配置数量的客户端；达到并发时，新连接无法建立，必须等槽位空出或另一副本扩起来。

> **图 7.18**：WebSocket 为音频流等非结构化数据建立持续连接。

与 WebSocket 类似，gRPC 支持双向流式，但用于结构化数据。经 gRPC 传输的请求必须遵循预定义 schema，省去解析输入的负担。这个额外校验层让 gRPC 比 WebSocket 稍慢。
