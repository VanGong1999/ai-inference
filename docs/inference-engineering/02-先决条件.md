# 第 1 章 · 先决条件（Prerequisites）

> Inference Engineering — Philip Kiely · Chapter 1

推理工程通过优化生成式模型的生产服务，为 AI 产品带来速度和规模。

优化意味着在一系列选项中找出最佳方案。在优化模型性能、构建稳健基础设施之前，你需要先知道对你的产品而言「最佳」意味着什么——许多性能提升都来自在延迟、吞吐与质量之间做权衡。

实践中，优化往往是找到正确的平衡，而不是最大化单一因素。

NFL 球员又高又快又壮，但他们没有相扑选手那么壮、没有奥运短跑选手那么快、也没有冠军举重运动员那么有力。他们的身体和技能被优化来满足其位置在整个赛季中的特定需求。

> **图 1.1**：就像精英运动员一样，推理服务必须为其负载的需求而专业化。

同理，你的推理系统必须被优化来满足你的模型、你的产品和你的流量的特定需求。你能引入的约束越多，能取得的成果就越好。

你应该清楚自己的：

- **模型需求（Model requirements）**：你需要对哪个（些）模型做推理？
- **应用接口（Application interface）**：输入如何送达模型？输出期望以什么格式呈现？
- **延迟预算（Latency budget）**：端到端，你的产品需要对用户操作响应多快？
- **单位经济性（Unit economics）**：按每请求、每用户或每月计算，花多少是合理的？
- **使用模式（Usage patterns）**：你在服务多少并发用户？他们的使用有什么规律（如工作时间更活跃）？

在构建 AI 产品的早期，这些问题的答案可能还不清晰。在这个早期阶段，通常更好的做法是尽可能用现成的 API，而不是投资专用推理。随着产品规模化，需求变得清晰，推理工程才成为值得投入的事。

## 1.1 规模与专业化（Scale and Specialization）

有两种把 AI 模型加进产品的方式：

- **共享推理（Shared inference）**：把你的流量发到某个模型的公共 API 端点，按每百万 token 或其它消费指标付费。
- **专用部署（Dedicated deployments）**：租用 GPU，专门为你的应用搭建一个推理服务，按 GPU 时长付费（或本地购买并安装 GPU）。

共享与专用推理，并不完全等同于闭源与开源模型的对话——开源模型也有很多共享端点，许多模型实验室也为大客户提供某种形式的闭源模型专用部署。不过，采用开源模型的关键动机之一，正是它解锁了**不受限制的专用推理**。

大多数 AI 产品从按 token 付费的 API 起步，因为在寻找产品市场契合（PMF）或增长早期，这种权衡是合理的。

**共享推理的优缺点**

| 优点 | 缺点 |
|---|---|
| 零开销，只为消费付费 | 成本随使用线性增长 |
| 无冷启动时间，模型始终可用 | 提供商可用性封顶产品可用性；有「吵闹的邻居」 |
| 工程工作量极小，只需一个 API key | 对延迟、模型质量、速率限制没有控制 |

随着时间推移，把 AI 产品转向专用部署出于三个必要原因：

- **规模（Scale）**：你处理的流量已经大到按 GPU 付费比按每百万 token 付费更经济。
- **专业化（Specialization）**：你在跑定制或微调模型，或有特定的延迟或可用性要求。
- **编排（Orchestration）**：你的产品依赖多个模型和多步流水线，需要最小化网络延迟和部署复杂度。

转向专用部署让你负责自己的推理工程。这带来灵活性和控制力，但也增加了你的工程面，并抬高了你每月推理支出的下限。只有在有明确且即时的业务需求时才切换。

## 1.2 关于你的应用（About Your App）

你做的每一个推理工程决策，都下游于你的用例。

想象一位体育教练在学校招募队员。他想找哪些学生谈？这完全取决于他执教哪个项目——篮球教练想要班里最高的孩子，而体操教练会在最矮的学生里挑选。

同理，你的推理系统将被如何使用，决定了你如何构建它。

有两种情况，推理工程师需要在最高通用性上构建：

- **基础模型（Foundation models）**：你训练了自己的模型，将直接通过公共共享推理 API 售卖消费，需要支持多种使用模式。
- **推理平台（Inference platforms）**：你在构建推理平台（内部或作为产品），需要支持任意模型、任意用例。

但大多数 AI 原生应用是**垂直应用（vertical apps）**，如代码编辑器或客服代理，其中 AI 被用来创造某种新颖的用户体验。为垂直 AI 原生应用构建推理时，你要通过把用例具体化来尽可能多地引入约束。

### 1.2.1 AI 原生应用（AI-Native Applications）

生成式 AI 模型解锁了跨行业、跨领域的一类新应用。每类应用依赖不同的模型和模态，需要量身定制的推理。

| 类别 | 示例 | 考量 |
|---|---|---|
| 代理（Agents） | 销售团队的获客代理 | 一次用户操作触发多次推理调用 |
| 聊天（Chat） | 带 RAG 的一线客服聊天 | 首 token 时间让聊天感觉快 |
| 语音（Voice） | 语言间实时翻译 | 端到端延迟要支持自然对话 |
| 媒体（Media） | 服装、鞋、珠宝的虚拟试穿 | 在输出质量与速度之间平衡 |
| 搜索（Search） | 法律文档检索 | 离线语料填充 vs 在线用户请求 |
| 推荐（RecSys） | 电商商品推荐 | 高请求量下保持稳定延迟 |
| 补全（Completion） | IDE 中编码的 Tab 补全 | 以用户打字速度产出完整补全块 |
| 审核（Moderation） | 扫描用户生成内容的安全性 | 高吞吐以做经济高效的检查 |

这只是今天正在构建的 AI 原生应用的一小部分样本，但它展示了推理工程师遇到的考量之广。随着模型变得更快、更便宜、更聪明，今天甚至无法想象的新用例将会涌现。

### 1.2.2 在线与离线（Online versus Offline）

推理工程的主要权衡之一是**延迟 vs 吞吐**。更低的延迟让你的应用更快，但更高的吞吐让它在规模化时更便宜，因为同样数量的用户可以用更少的 GPU。

大多数 AI 应用——代码补全、聊天、语音代理——是**在线应用**，实时运行。每次 API 调用背后都有一个不耐烦的用户在等待，这些在线应用应当为延迟优化。

然而，一些应用有**离线批处理**推理需求。离线任务更适合由高吞吐的模型部署来服务——在那里，每个单独请求对良好用户体验来说都太慢，但系统整体每小时并行处理的请求多得多。

一些离线负载示例：

- **目录转写**：转写积压的播客、访谈或其它音频，使其可被搜索。
- **文档处理**：以固定节奏嵌入、转换或分析一组文档。
- **语料准备**：为模型训练清洗、嵌入或以其它方式准备海量数据语料。

一个模型可能同时用于在线和离线任务。Whisper（一个语音转文本模型）既能用于实时听写应用，也能用于批量转写任务。假设两个用例都有足够的量，为同一模型创建两个独立部署会更经济高效——一个为延迟优化，另一个为吞吐优化。

### 1.2.3 消费者与 B2B（Consumer versus B2B）

为消费者和企业构建的应用有不同的推理需求。

消费者应用通常对成本敏感得多，使用模式也更难预测。许多消费者 AI 应用为病毒式传播而设计，一次发布或营销活动就可能在一夜之间带来使用量的激增。

做消费者应用的推理工程师，应优先考虑边际成本和灵活性，同时把延迟和可用性保持在不错的标准。

B2B 产品往往利润率更好、使用更稳定，但要求高可用性和持续的低延迟。处于营收路径上的关键任务软件，被要求达到很高的性能和可靠性标准。

为企业构建的推理工程师必须优先考虑延迟和可用性，成本和规模是重要的次要考量。

在消费者和企业应用中，合规都可能限制基础设施选项，尤其是在受监管行业。一些关键考量包括：

- **数据主权（Data sovereignty）**：你的 GPU 是否位于允许你发送用户数据的地理区域？
- **用户隐私（User privacy）**：模型的输入输出是否保持私密和安全？
- **监管合规（Regulatory compliance）**：你和你的底层提供商是否符合所有相关法规？

推理工程师必须与安全和法务专家密切合作，确保他们运营的基础设施是合规的。

## 1.3 模型选择（Model Selection）

在其它条件相同——硬件、运行时、优化、架构——对参数量更少的小模型做推理，会比参数量更多的大模型更快、更便宜。

这就是为什么模型性能优化中最重要决策不是运行时引擎或投机算法，而是**你一开始选择使用哪个模型**。

在早期产品上迭代的 AI 工程师，应该直接用 Kimi、DeepSeek（甚至是 GPT、Gemini 这类闭源模型）等强大前沿模型的预构建按 token 付费 API。在产品市场契合之前，不值得花时间或金钱自己做推理。

但当需要规模化时，建议正好相反：**找到——或创造——足够聪明能处理手头任务的最小、最容易运行的模型。** 很多情况下，这仍然需要万亿参数的前沿模型。但始终值得检查一下，是否有更小、更便宜、更快的模型能完成任务。

你选的模型也影响你可用的推理优化。不同推理引擎对不同模型架构的支持深度不一。坚持使用流行的模型架构，以确保你能在整个性能工具生态中找到稳健的支持。

### 1.3.1 模型评估（Model Evaluation）

模型评估（evaluation，简称 **evals**）是系统化测量模型智能的实践。

高置信度的模型评估是推理工程的前提。Evals 帮助推理工程师：

- **明智地花时间**：在投入精力让模型变快之前，evals 确保模型是有用的。
- **建立基线**：某些性能优化技术有降低模型质量的风险，需要一条基线来对比。

与衡量模型在 MMLU、SWE-bench 等常见任务上能力的标准智能基准不同，evals 是**为特定产品、领域和任务量身定制**的。

智能基准对初筛模型很有用，但它们已经饱和、甚至被「刷分」。古德哈特定律（Goodhart's Law）说：「当一个度量变成目标，它就不再是一个好的度量。」这适用于前沿实验室在每次发布模型时都想展示新的世界纪录智能基准的强烈动机。

虽然还有更好的方式衡量模型的整体智能——比如与其它模型两两对战胜率得出的 Elo 评分——但没有任何东西能替代直接测量模型在你应用上的表现。

做有用的模型评估工作的一些建议：

- **看你的数据**：对照你对产品和问题空间的直觉来检查 eval 结果。
- **精确**：清楚模型需要解决的最难问题是什么，把评估聚焦在那里。
- **用工具**：不要在 AI 工程的一个基础问题上重复造轮子。

附录 B 包含关于 evals 的工具和进一步阅读的推荐。

### 1.3.2 面向领域质量的微调（Fine-Tuning）

微调（fine-tuning）是拿一个预训练基础模型，通过引入新数据把它适配到特定用例的实践。

> **图 1.2**：微调模型改变的是权重值，同时保持整体架构不变。

如果你能微调一个小模型通过你的 evals，你就为在推理上达成延迟和成本目标铺平了更容易的路。

微调有效的领域的一个好例子是「把英语翻译成 SQL」（一种用于查询数据库的语言）。

通用编程模型擅长写 SQL，但这些模型有数千亿参数。SQL 是相对受限的语言，所以对一个只需要从自然语言 prompt 生成 SQL 查询的应用，一个仅有几十亿参数的微调小模型就能在这个特定任务上达到相当的性能。

Text-to-SQL 是一个极端例子——许多领域不会支持如此大幅的模型缩小——但它展示了在一个范围清晰的领域、一套强评估标准和高质量标注数据用于微调时，什么是可能的。

### 1.3.3 蒸馏（Distillation）

如果能在几分之一的大小上保留大模型的大部分智能呢？这就是**蒸馏（distillation）**背后的想法。

> **图 1.3**：蒸馏在一个更小、更高效的模型中保留大模型的行为。

蒸馏是用一个大「教师（teacher）」模型训练一个更小「学生（student）」模型来模仿大模型行为的过程。与在合成数据上微调（模型在输入-输出对上训练）不同，蒸馏给学生模型看的是教师模型的**实际概率分布**，而不只是最终答案。

微调教模型在特定领域表现更好，蒸馏则教模型模仿大模型的行为——好的和坏的都模仿。

蒸馏在真实世界中的使用远少于微调。

当前沿实验室发布一族不同大小的模型时，小模型通常**不是**从大模型蒸馏来的。相反，这些模型是独立训练的，以防止大模型的偏见人为限制小模型。但如果实验室只训练了大模型，蒸馏可以让那个模型更易获取。

2025 年 1 月，开源模型研究实验室 DeepSeek 发布了他们当时的旗舰推理模型 DeepSeek-R1。由于该模型太大（671B 参数），他们还在当时最流行的开源模型架构（Llama 3 和 Qwen 2.5）之上发布了蒸馏版本。

这些蒸馏模型表现出与主 DeepSeek-R1 相似的推理行为，尽管智能基准分数更差，但蒸馏模型相对较小，可以复用 Llama 和 Qwen 架构已有的性能工作。

截至出版时，这些 DeepSeek-R1 蒸馏模型仍是 Hugging Face 上最受欢迎的蒸馏模型之一，同列的还有 Whisper 等音频转写模型的蒸馏版，以及一些图像生成模型。

## 1.4 测量延迟与吞吐（Measuring Latency and Throughput）

LLM 最常见的两个性能指标是 **TTFT（time to first token，首 token 时间）**和 **TPS（tokens per second，每秒 token 数）**。LLM 之外的模态特定指标见第 6 章。

| 首 token 时间（TTFT） | 每秒 token 数（TPS） |
|---|---|
| 流式输出下，用户看到第一个输出 token 要多久？ | 首 token 生成后，用户每秒收到多少个 token？ |
| 基于算力受限的 prefill | 基于带宽受限的 decode |
| 更低的 TTFT == 更好的延迟 | 更高的 TPS == 更好的延迟 |

虽然 TTFT 含义明确，TPS 却不那么精确。TPS 可以是一个延迟指标（每用户每秒 token 数），也可以是一个吞吐指标（整个推理服务每秒 token 数）。

大多数人用 TPS 表示每用户延迟指标。需要时，用更具体的术语：

- **感知 TPS（Perceived TPS）**：首 token 之后每用户每秒观察到的 token 数（延迟）。
- **总 TPS（Total TPS）**：推理服务每秒生成的总 token 数（吞吐）。
- **token 间延迟（Inter-token latency, ITL）**：相邻 token 之间的时间。10 毫秒的 ITL 相当于每用户每秒 100 token。

> **图 1.4**：TTFT 是生成第一个 token 所需的时间，而 TPS 衡量后续 token 生成的速度。

TTFT 和 TPS 最常用于面向用户的 LLM 系统，如聊天机器人，其中输出被流式传给用户。对于其它请求，如 agent 的工具调用，你改以**总响应时间**衡量延迟，因为单个 token 没有独立意义。

### 1.4.1 延迟百分位（Latency Percentiles）

讨论和对比指标时，一个重要区别是你在测量哪个**百分位（percentile）**。

> **图 1.5**：由于推理时间呈右偏分布中的离群值，平均延迟通常高于 P50 延迟。

天真的做法是直接看平均（均值）TTFT 或 TPS。但这不能说明全貌。LLM 的总响应时间通常是**右偏分布（right-skewed）**：大多数时间集中在众数附近，但离群值可能显著更长。

这些离群值会极大影响用户体验和对产品的信任。如果每十次交互就有一次要好几秒，那么大多数交互感觉敏捷是不够的。

因此，推理工程师用**百分位**来衡量延迟。

| 百分位 | 名称 | 含义 |
|---|---|---|
| P50 | 中位延迟 | 每 2 个请求中有 1 个更慢 |
| P90 | 90 分位延迟 | 每 10 个请求中有 1 个更慢 |
| P95 | 95 分位延迟 | 每 20 个请求中有 1 个更慢 |
| P99 | 99 分位延迟 | 每 100 个请求中有 1 个更慢 |

降低平均延迟固然重要，好的性能工作也会聚焦降低 P90/P99 延迟，以获得更可靠的用户体验。

### 1.4.2 端到端指标（End-to-End Metrics）

指标的另一个重要区别是：你测量的是**仅推理时间**——在 GPU 上生成 token 所需的时间——还是考虑了网络延迟和排队时间的**端到端（end-to-end）**测量。

仅推理时间和端到端指标都值得了解。推理时间告诉你模型性能工作的成效，而端到端指标揭示用户对你应用快慢的感知。当推理时间快、但端到端时间慢时，把注意力转向基础设施，而不是模型性能优化。
